Project 03 · Store audit

The M1 deliverable from Project 03. It records what the demo store looked like before the production work, how urgent each gap was, and where it was fixed.

P0 · not shippable without it P1 · you'll lose users or data without it P2 · polish

Gaps

#QuestionWhat the demo didPriorityFix (where it lives now)Status
1What happens on a 401?The request interceptor in src/shared/api/axios.ts was a commented-out stub, and there was no response interceptor.P0api/interceptors.ts: on a 401, refresh once and replay the request once; if the refresh fails, sign out. api/refreshCoordinator.ts: single-flight refresh. Both are installed on store-owned instances (api/client.ts), never on the shared one.Closed. __tests__/refresh.test.ts: six concurrent 401s cause one refresh.
2Where does the token live?Nowhere. useLogin returned the token and dropped it.P0auth/tokenStorage.ts: the refresh token is in expo-secure-store with WHEN_UNLOCKED_THIS_DEVICE_ONLY. The access token is read from memory by the interceptor and also saved to secure-store, so a cold start can skip a refresh. Neither token is ever written to AsyncStorage.Closed
3Is login actually gated?No. The splash redirected on a timer and nothing stopped a deep link going past it.P0src/app/projects/store/_layout.tsx: Stack.Protected guards for onboarding, (app) and (auth). The native splash stays up until the session resolves. The intent buffer (navigation/pendingIntent.ts) restores the page you were trying to reach after sign-in.Closed
4Are credentials hardcoded?Yes: constants/credentials.ts.P0File deleted. The sign-in screen has a dev-only "fill demo user" button instead.Closed
5Is the cart durable?No. In-memory Zustand, empty on every relaunch.P1stores/cartStore.ts is persisted with zustand + AsyncStorage. stores/cartSync.ts reconciles it with the server on sign-in using the mergeCarts rule (union by product, max quantity, server product data wins).Closed. __tests__/cartMath.test.ts
6Are query keys collision-safe?No. Flat keys like ["products"] and ["product", id] don't share a prefix.P1utils/queryKeys.ts is a nested factory under a "store" root, because one QueryClient is shared by every project in the app.Closed
7Is there a password in a query key?queryKeys.loginUser(credentials) existed, though nothing used it.P0Deleted. Login is a mutation.Closed
8How is the base URL chosen?Hardcoded https://fakestoreapi.com.P1app.config.ts sets extra.storeApiUrl per variant, read through src/shared/constants/env.ts. The shared axios instance has no base URL at all.Closed
9What does the orders screen do offline?Showed a spinner forever.P1query/storeQuery.ts: the query cache is persisted (store keys only), onlineManager is wired to expo-network, and an offline banner is shown with cached data instead of a spinner.Closed
10Is useOrders N+1?Yes: fetch the cart, then fetch every product one by one.P2hooks/useOrders.ts now resolves products from the cached catalogue (ensureQueryData), so it's one catalogue request instead of N detail requests. FakeStoreAPI has no join endpoint; a real backend should return order lines with product snapshots.Mitigated
11Does axios.ts belong to this project?No. It's shared infra, but it carried store-shaped comments and a base URL.P1It now holds only project-agnostic defaults (timeout and headers). The store derives its own instances and installs its interceptors from its own folder.Closed

Expo Deep-Dive Learning Path

Five projects that, together, cover essentially the whole Expo + React Native production surface — from managed-workflow basics to custom native modules and OTA release engineering.

Expo SDK 57 React Native 0.86 React 19.2 + Compiler Expo Router v7 New Architecture TypeScript

This is a curriculum, not a list of app ideas. Each project deliberately introduces a new capability tier and retires the training wheels of the previous one. Build them in order — the ordering is the point.

How to use these docs

Each project page contains: the learning objectives, a screen-by-screen UI breakdown with wireframes, the folder/architecture layout, data-flow diagrams, milestone-based build order with checkpoints, library hints with the exact package names, and a list of "things that will break" so you learn the failure modes too. There is no copy-pasteable implementation code — only API surface hints. You write the code; that is where the learning lives.

Before you start — the baseline

You already have this repo running. Get these three things in place first; every project assumes them.

1. A development build, not Expo Go

Expo Go is a fixed binary containing a fixed set of native modules. The moment Project 02 needs a library outside that set, Expo Go stops being an option. Learn the dev-client workflow now, while nothing depends on it.

npx expo install expo-dev-client
eas build --profile development --platform ios --local
# then: npx expo start --dev-client

This repo already has expo-dev-client and an eas.json. Confirm you can produce a build and connect to it.

2. Understand the three "workflow" myths

  • There is no "managed vs bare" split anymore in the old sense. There is Continuous Native Generation (CNG): android/ and ios/ are build artifacts generated by npx expo prebuild from app.json + config plugins.
  • This repo currently has a committed android/ folder. Decide deliberately: either treat it as generated (add to .gitignore, rely on plugins) or as hand-maintained. Project 04 will force this decision — make it early.
  • Native code does not mean "ejecting". You can add Swift/Kotlin via a local Expo Module and still regenerate projects freely.

Ground rules that apply to all five

  1. No implementation copy-paste. These docs give you the API surface and the shape. Reading docs.expo.dev for the exact signature is the exercise.
  2. Components stay dumb. Screens own state and hooks; components receive plain props and callbacks. Same rule as your Swift work — a component that imports a store is a component you can't reuse.
  3. One state tool per concern. Server data → TanStack Query. Ephemeral client state → Zustand or local state. Persisted domain data → SQLite. Do not mirror the same fact in two of them.
  4. Handle the four states, always. Every screen has loading / empty / error / content. Design the empty and error states before the happy path.
  5. Test on a real device early. Simulators lie about camera, GPS, background execution, audio interruptions, and battery behaviour — which is exactly what projects 02, 04 and 05 are about.
  6. Write down what broke. Keep a .agents/lessons/_learned.md per project. The failure modes are the durable knowledge.

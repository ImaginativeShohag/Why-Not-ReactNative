Expo Deep-Dive Learning Path

Five projects that, together, cover essentially the whole Expo + React Native production surface — from managed-workflow basics to custom native modules and OTA release engineering. Plus a launcher that holds them all and a side quest or two.

Expo SDK 57 React Native 0.86 React 19.2 + Compiler Expo Router v7 New Architecture TypeScript

This is a curriculum, not a list of app ideas. Each project deliberately introduces a new capability tier and retires the training wheels of the previous one. Build them in order — the ordering is the point.

How to use these docs

Each project page contains: the learning objectives, a screen-by-screen UI breakdown with wireframes, the folder/architecture layout for that project's slice, data-flow diagrams, milestone-based build order with checkpoints, library hints with the exact package names, and a list of "things that will break" so you learn the failure modes too. There is no copy-pasteable implementation code — only API surface hints. You write the code; that is where the learning lives.

Step 00 is done — Launcher & Multi-Project Restructure

Two rules the structure enforces, and one it can't

No cross-project imports — nothing in src/projects/camera-social/ may ever import from src/projects/store/. If two projects need the same thing, promote it to src/shared/ deliberately. Shared stays small — promote only when a second project actually needs it. And the one nothing enforces: a file under src/app/ is a reachable route whether or not you declare it in a Stack.Screen. A sheet body or list row parked there becomes a route that crashes when someone hits it directly. Put non-route code in a slice.

Before you start — the baseline

You already have this repo running. Get these three things in place first; every project assumes them.

1. A development build, not Expo Go

Expo Go is a fixed binary containing a fixed set of native modules. The moment Project 02 needs a library outside that set, Expo Go stops being an option. Learn the dev-client workflow now, while nothing depends on it.

npx expo install expo-dev-client
eas build --profile development --platform ios --local
# then: npx expo start --dev-client

This repo already has expo-dev-client and an eas.json. Confirm you can produce a build and connect to it.

2. Understand the three "workflow" myths

  • There is no "managed vs bare" split anymore in the old sense. There is Continuous Native Generation (CNG): android/ and ios/ are build artifacts generated by npx expo prebuild from app.json + config plugins.
  • This repo has already made the CNG choice — /ios and /android are both in .gitignore, so neither is tracked. Treat any local android/ folder as disposable output: if a change can't be expressed in app.json or a config plugin, it will be wiped on the next prebuild. Project 04 is where you feel this.
  • Native code does not mean "ejecting". You can add Swift/Kotlin via a local Expo Module and still regenerate projects freely.

Ground rules that apply to all five

  1. No implementation copy-paste. These docs give you the API surface and the shape. Reading docs.expo.dev for the exact signature is the exercise.
  2. Stay inside your slice. Routes go in src/app/projects/<slug>/, everything else in src/projects/<slug>/. Never import from another project's slice. Promote to src/shared/ only when a second project genuinely needs the thing.
  3. Components stay dumb. Screens own state and hooks; components receive plain props and callbacks. Same rule as your Swift work — a component that imports a store is a component you can't reuse.
  4. One state tool per concern. Server data → TanStack Query. Ephemeral client state → Zustand or local state. Persisted domain data → SQLite. Do not mirror the same fact in two of them.
  5. Own your query keys. Each project gets its own utils/queryKeys.ts inside its slice. There is no shared key file — two projects sharing a key namespace is a cache-collision bug waiting to happen.
  6. Handle the four states, always. Every screen has loading / empty / error / content. Design the empty and error states before the happy path.
  7. Test on a real device early. Simulators lie about camera, GPS, background execution, audio interruptions, and battery behaviour — which is exactly what projects 02, 04 and 05 are about.
  8. Write down what broke. Keep a .agents/lessons/_learned.md per project. The failure modes are the durable knowledge.

Starting a new project — the mechanical part

Same five steps every time, so none of the docs below repeat them.

  1. Replace the stub at src/app/projects/<slug>/index.tsx — it currently renders ComingSoonView.
  2. Create the slice: src/projects/<slug>/ with only the subfolders you actually need. Don't scaffold empty ones.
  3. Flip available: false → true for that entry in src/shared/config/projects.ts. The launcher reads the registry; it has no hardcoded knowledge of any project.
  4. Add a <Stack.Screen name="projects/<slug>/…"> per route in src/app/_layout.tsx. The name must match the path derived from the file tree exactly — verify against the tree, don't trust typed routes to catch a mismatch.
  5. Run npm run lint and npx tsc --noEmit before you call a milestone done.
Providers your project may need are not free

src/app/_layout.tsx mounts QueryProvider, SafeAreaProvider, GestureHandlerRootView and ThemeProvider once, globally. Anything narrower — SQLiteProvider (01), BottomSheetModalProvider, a playback host (05) — mounts in your project's layout, not the root. And never mount a second QueryProvider: two clients means two independent caches, and data fetched on one screen is invisible to the next.

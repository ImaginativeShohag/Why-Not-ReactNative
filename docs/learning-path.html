How it works

This is a curriculum, not a list of app ideas. Each project introduces a new capability tier and takes away the training wheels of the one before it, so build them in order.

Read the write-up

Learning objectives, screens and wireframes, the folder layout of the slice, data flow, library hints and the failure modes to expect.

Build milestone by milestone

Every milestone ends with a checkpoint you can demonstrate and a verify step you can run. Don't move on until both pass. Then compare with the finished code.

Check yourself

Each project has a quiz that points at the real files: open them, work out the answer, then read why. Spaced repetition brings back what you missed.

Before you start

Clone the repo, run npm install, then put these three things in place. Every project assumes them.

1A development build, not Expo Go

Expo Go is a fixed binary with a fixed set of native modules. As soon as Project 02 needs a library outside that set, Expo Go stops being an option. Learn the dev-client workflow now, while nothing depends on it.

npx expo install expo-dev-client
eas build --profile development --platform ios --local
npx expo start --dev-client

expo-dev-client and eas.json are already set up. Confirm you can produce a build and connect to it.

2Continuous Native Generation

  • There is no "managed versus bare" split. ios/ and android/ are build output, generated by npx expo prebuild from app.config.ts and config plugins.
  • Both are gitignored. If a change can't be expressed in app.config.ts or a config plugin, the next prebuild wipes it. Project 04 is where you feel this.
  • Native code doesn't mean "ejecting". You add Swift and Kotlin through a local Expo Module and keep regenerating freely.

Ground rules

These apply to every project.

Read the docs for signatures

The write-ups give you the shape and the API surface. Looking up the exact signature on docs.expo.dev is part of the exercise.

Stay inside your slice

Routes go in src/app/projects/<slug>/, everything else in src/projects/<slug>/. Never import from another project. Promote to src/shared/ only when a second project needs it.

Components stay dumb

Screens own state and hooks; components receive plain props and callbacks. A component that imports a store is a component you can't reuse.

One state tool per concern

Server data in TanStack Query, client state in Zustand or local state, persisted domain data in SQLite. Never mirror the same fact in two of them.

Own your query keys

Each project has its own utils/queryKeys.ts, rooted at its own prefix. One QueryClient serves every project, so a shared namespace is a cache collision waiting to happen.

Handle all four states

Every screen has loading, empty, error and content. Design the empty and error states before the happy path.

Test on a real device early

Simulators lie about the camera, GPS, background execution, audio interruptions and battery, which is exactly what Projects 02, 04 and 05 are about.

Write down what broke

Keep a notes file per project. The failure modes are the knowledge that lasts.

How the repo is organised

Two homes for non-route code, a project slice or shared, and no "misc" folder. Every project fills in the same two blanks.

Two rules the structure enforces, and one it can't

No cross-project imports: nothing in src/projects/camera-social/ may import from src/projects/store/. Shared stays small: promote only when a second project needs it. Lint enforces both. The one nothing enforces: a file under src/app/ is a reachable route whether or not a Stack.Screen declares it. A sheet body or list row parked there becomes a route that crashes when someone opens it directly.

Adding a project

The mechanical part is the same every time, so the write-ups don't repeat it.

  1. Add an entry to src/shared/config/projects.ts and a first route for it. The launcher reads the registry and knows no project by name.
  2. Create the slice, src/projects/<slug>/, with only the subfolders you need. Don't scaffold empty ones.
  3. Give the project its own src/app/projects/<slug>/_layout.tsx owning its inner Stack. The root layout generates one Stack.Screen per registry entry, so the root needs no edit.
  4. Import anything that must exist on a headless or cold launch (a TaskManager.defineTask, a notification-tap listener, a share-intent router) from the root layout. A project layout only loads when the user opens that project, so a task defined there finds nothing registered on a background launch.
  5. Give external URL shapes (universal links, share callbacks) a pure rewriter in your slice and register it in src/app/+native-intent.tsx.
  6. Before calling a milestone done, run npm run typecheck, npm run lint, npm test and npx expo export --platform ios. The bundle catches what tsc can't, such as a stray @react-navigation/* import.
Providers are not free

src/app/_layout.tsx mounts QueryProvider, SafeAreaProvider, GestureHandlerRootView and ThemeProvider once, for everyone. Anything narrower, such as SQLiteProvider (01), BottomSheetModalProvider or a playback host (05), mounts in your project's layout. Never mount a second QueryProvider: two clients means two caches, and data fetched on one screen is invisible on the next.

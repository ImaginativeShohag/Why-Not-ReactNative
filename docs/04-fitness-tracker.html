Learning objectives

You will build a workout recorder that keeps recording with the screen off and the app suspended, survives being killed mid-run, and shows live progress on the lock screen, in a notification and on the home screen. The finished system lives in four places: src/projects/fitness-tracker/ (the app slice), src/app/projects/fitness-tracker/ (routes), modules/live-activity/ (the local Expo Module) and plugins/ (the hand-written config plugin and the widget extension sources). Read this page top to bottom once, then build it milestone by milestone; every milestone ends with a checkpoint you can run.

Prerequisites: Projects 01–03 (Expo Router, SQLite, Zustand/TanStack basics), a Mac with Xcode for the iOS half, an Android device or emulator for the Android half, and at least one physical phone: simulators fake GPS and have no real sensors.

UI design & screens

Design language

  • Tone: high-contrast and glanceable. The active-workout screen must be readable at arm's length, in sunlight, while moving.
  • Numbers dominate. One hero metric (duration or distance) at 56–72pt, secondary metrics in a row beneath.
  • Big touch targets. Minimum 64pt for pause/stop — the user has sweaty hands and is out of breath.
  • Anti-mistap: "Stop" requires a long-press with a filling progress ring, never a plain tap.
  • Always-visible tracking state. If GPS is degraded, say so immediately — silent bad data is worse than no data.

Architecture

The core problem

Your JS runtime may be suspended or killed at any moment while a workout is running. So:

Rule: the background task must persist every point immediately.

Never accumulate points in a JS variable and "save at the end." A task invocation may be the last code that ever runs. Write to SQLite inside the task callback, and let the UI read from the database rather than from memory.

Why modules/ and plugins/ escape the slice rule

The slice rule governs app source. A local Expo Module is a package the autolinker discovers by convention at the project root, and a config plugin is build-time tooling that runs before any app code exists. Neither is importable app code, so neither belongs under src/. The thin TS wrapper that app code does import — liveactivity/index.ts — stays in the slice and is the only thing your screens touch.

Pure metrics, testable

Keep metrics.ts, filters.ts and autoPause.ts free of React, SQLite, and the location API: (points: Point[]) => Summary and (state, fix) => result. Because the filter state is a plain object, the background task can persist it between invocations and the tests can replay a recorded GPX (__tests__/fixtures/track.gpx) through it. This is the only realistic way to verify tracking correctness without going outside for every change.

Two rules that make the background path trustworthy

  • The session lives in SQLite. state.ts stores the whole Session (workout id, status, segment counter, pause bookkeeping, filter state, elevation reference, auto-pause timers) as JSON in a single-row table. The next task invocation may run in a fresh headless runtime and must find everything it needs in the database. Elapsed time is derived from persisted timestamps, never from an in-memory stopwatch.
  • Every mutation goes through enqueue(). A GPS batch, a pause tapped on the lock screen, a motion auto-pause and the crash-recovery check all read-modify-write the same session row. queue.ts is a promise chain (a mutex is enough because JS is single-threaded) so two cycles can never interleave and drop a pause or double-count a batch.

Pauses are modelled as segments: every resume increments segment, and distance, moving time, the speed gate, the smoother, the drawn polyline and the GPX export never bridge two segments. Without it, pausing and then taking a bus would count as running.

The native layer

Step 1 — Understand CNG

This repo takes the CNG decision for you: /ios and /android are both gitignored, so nothing native is tracked. Know what that commits you to:

ApproachMeaningTrade-off
CNG (what this repo does)ios/ and android/ are gitignored and regenerated by npx expo prebuild --clean.All native changes must be expressible as config plugins. Upgrades are trivial.
Committed nativeYou edit Xcode/Gradle directly.Full freedom, but SDK upgrades become manual merges and you lose the main reason to use Expo.

Stay on the CNG path. Anything you can't do with a plugin becomes the motivation to write one — and any local android/ folder on your disk is disposable output that the next prebuild will overwrite.

One source of truth, shared across processes

WorkoutAttributes.swift lives in the local module and is copied byte for byte into the widget extension by the plugin. ActivityKit pairs the app's activity with the extension's UI by type name and Codable shape, and two hand-maintained copies that drift fail silently (no error, just no Live Activity UI). For the same reason the file must not import ExpoModulesCore, which the extension does not link, and the App Group id is read from the WorkoutAppGroup Info.plist key that the plugin writes into both plists.

Testing the plugin in memory

A plugin you can only verify by running a 5-minute prebuild is a plugin you will stop verifying. __tests__/configPlugin.test.ts runs the mods with compileModsAsync(config, { projectRoot, introspect: true, platforms: ["ios", "android"] }) under @jest-environment node: plist, entitlement and manifest mods execute against Expo's templates and write their results back into the config for assertions; dangerous mods (file copies) are skipped. Use a fresh temp projectRoot so a leftover prebuilt ios/ cannot leak the real app's entitlements into the assertions. Test the unwrapped plugin twice to prove each mod is idempotent (the createRunOncePlugin wrapper would skip the second call), and assert the fail-fast path for a bad appGroup.

The JS side exposes one clean interface — startLiveActivity(attrs, state), updateLiveActivity(state), endLiveActivity(state, dismissImmediately), addActionListener, consumePendingAction, setWidgetData — and each platform implements it its own way. That asymmetry is the lesson. Load the native module with requireOptionalNativeModule so that Expo Go, web and Jest get null and every wrapper degrades to a no-op instead of throwing at import time.

Send a timerStart instant, not a per-second elapsedSec: Text(timerInterval:) on iOS and setUsesChronometer(true).setWhen(timerStart) on Android tick natively, so JS only pushes when distance, pace or status change.

Tracking pipeline & battery

Point processing

batch of raw fixes (sorted by timestamp; the session row is re-read from SQLite)
  → manually paused or no session → ignore the batch
  → auto-pause step (GPS speed): maybe pause / resume (resume starts a new segment)
  → reject if coordinates invalid (non-finite, out of range, or 0,0)
  → reject if accuracy > 25 m
  → reject if timestamp is not newer than the last accepted point
  → reject if implied speed > plausible max for the activity type
     (after the stale check, so the speed division always has dt > 0)
  → Kalman smooth lat/lng (accuracy as measurement noise; restarts on a new segment)
  → if smoothed point is < 5 m from the last ACCEPTED point → skip (anchor stays put)
  → accumulate distance, moving time, elevation (3 m hysteresis)
  → ONE transaction: insert points, add rolling totals, save session
  → (after commit) voice cue per km, then push to the Live Activity / notification
    (throttled to ~1 Hz, forced on status changes)

Rolling totals exist only for the live UI. stopWorkout recomputes distance, moving time, elevation, splits, calories and the thumbnail from the persisted points with the same pure functions the tests cover, so any drift in the incremental path never reaches history.

Platform reality check

  • iOS: background location works with the location background mode and Always permission. The blue status bar / indicator will show. Without the background permission the controller falls back to a foreground-only watchPositionAsync and the active screen says so.
  • Android: you must run a foreground service with a persistent notification, declare foregroundServiceType="location", and request background location as a separate, second prompt. On top of that, OEM battery managers (Xiaomi, Huawei, Samsung, OnePlus) kill background work aggressively — test on a real device from at least one of those vendors, and send the user to the battery-optimization settings (the permissions screen does, via android.settings.IGNORE_BATTERY_OPTIMIZATION_SETTINGS). Auto-pause uses GPS speed in the background (works while suspended) and DeviceMotion variance in the foreground (faster, but sensors are not delivered to JS while suspended).

Build order

M1 Go CNG

Goal: native projects become disposable.
  • Register the project: an entry with slug fitness-tracker in src/shared/config/projects.ts, a route folder src/app/projects/fitness-tracker/ with its own _layout.tsx Stack, and the slice src/projects/fitness-tracker/.
  • Confirm ios/ and android/ are gitignored; run npx expo prebuild --clean.
  • Confirm the app still builds and runs from a fully regenerated project.
  • Read the generated Info.plist and AndroidManifest and map each entry back to something in app.config.ts.
Checkpoint — rm -rf ios android && npx expo prebuild && npx expo run:ios works from clean. No manual Xcode steps. npm run typecheck and npm run lint pass.

M2 Foreground tracking

Goal: record a route with the app open.
  • Permission flow screen handling foreground → background → motion → notifications, in the right order.
  • watchPositionAsync feeding a pure processFix (accuracy, stale, speed, Kalman, jitter gates). This foreground path is kept in the final app as the fallback when background permission is denied.
  • SQLite schema for workouts, points, splits, prefs and the single-row session table; PRAGMA user_version migrations; WAL mode; one shared getDb() connection. Write every accepted point.
  • HoldButton for Stop (a plain tap never ends a workout).
  • Active screen with live metrics; keep the screen awake (expo-keep-awake).
  • Pure metrics module + unit tests against a recorded GPX.
Checkpoint — Walk 1 km with a measured route. Your distance is within ~3% of reality, and npx jest --no-watchman src/projects/fitness-tracker passes the metrics and filter tests, including "standing still for 300 noisy fixes records almost nothing".

M3 Background tracking

Goal: it keeps working with the screen off and the app backgrounded.
  • TaskManager.defineTask at module scope (guarded with isTaskDefined) in tracking/task.ts, imported from the root src/app/_layout.tsx so a headless relaunch defines it. startLocationUpdatesAsync with the shared task-name constant.
  • Move the live session into SQLite (state.ts) and every mutation through enqueue(); make startWorkout idempotent and save the session before starting updates.
  • Android foreground service config (foregroundService options) with a persistent notification.
  • iOS background modes + Always permission, added via your own config plugin (and the expo-location plugin flags).
  • Permission flow in order: foreground, background, motion, notifications; background is locked until foreground is granted.
  • Crash/kill recovery: on launch findRecoverable() detects an unfinished workout (discarding orphan rows) and the Today screen offers Resume / Finish / Discard.
  • Deferred updates for the battery-saver mode, and a stale-fix banner ("GPS signal lost") on the active screen.
Checkpoint — Start a workout, lock the phone, put it in a pocket, walk 30 minutes. The route has no gaps. Then force-kill the app mid-workout and confirm the recorded data up to that moment is intact and the recovery banner appears (unless Android's service kept recording).

M4 Maps & visualization

Goal: the route looks good and renders fast.
  • Map with a route polyline (react-native-maps); camera follows the user during the workout.
  • Pace-coloured polyline segments, merged by colour bucket so the map gets tens of <Polyline> views, not one per leg.
  • Douglas–Peucker simplification before rendering — 10,000 points must not be drawn raw.
  • Kilometre splits (interpolated boundaries) and a splits table.
  • Line and bar charts drawn with Skia for pace, elevation, heart rate and weekly distance.
  • Route thumbnails for the history list: a normalised, simplified path stored at finish and drawn with Skia, never a live MapView per row.
  • Live updates without polling: useLiveQuery subscribes with addDatabaseChangeListener (debounced, only while focused).
Checkpoint — Open a 3-hour hike with ~12k points. The detail screen renders in under a second and pans smoothly.

M5 Sensors

Goal: data beyond GPS.
  • Pedometer step count, live and historical.
  • Barometer-derived relative elevation (iOS gives relativeAltitude; Android derives it from pressure), shown next to GPS elevation.
  • Auto-pause as a pure state machine with asymmetric timings (pause after 8 s still, resume after 3 s moving), fed by GPS speed in the pipeline and by DeviceMotion variance in the foreground.
  • Historical steps exist on iOS only; on Android the Today ring counts from when watching began.
Checkpoint — Auto-pause triggers within 10 s of stopping and resumes within 5 s of moving. Walk to a traffic light and back, then tune the thresholds, because the first values will have false positives.

Failure modes to experience deliberately

  1. Task defined inside a component. It works in the foreground, then silently records nothing in the background. The single most common background-location bug.
  2. Points held in memory. Force-kill during a workout and lose the whole run. Persist in the task callback.
  3. Permission ordering. Request background location before foreground on Android — the prompt won't appear at all. Order matters and differs by OS version.
  4. Missing foreground service type. On modern Android, starting a location foreground service without declaring foregroundServiceType throws at runtime, not build time.
  5. OEM battery killer. Test on a Xiaomi or Samsung with default settings; your service gets killed after ~20 minutes. Detect it and educate the user.
  6. GPS drift while stationary. Stand still for five minutes with no accuracy filter and record 200 m of "distance". This is why the filter exists.
  7. Rendering raw polylines. Push 15,000 coordinates into a map polyline and watch the frame rate die.
  8. Live Activity update storm. Update at 10 Hz; iOS throttles or terminates the activity. Throttle to ~1 Hz.
  9. Hand-editing generated native code. Make a change in Xcode, then run prebuild --clean and watch it disappear. Feel it once; it's the lesson that makes plugins click.
  10. App Group mismatch. Widget shows no data because the app and the extension use different group identifiers. Silent and maddening. The final code derives both from one plugin prop and the WorkoutAppGroup Info.plist key.
  11. Racing session writers. A pause from the lock screen interleaves with a GPS batch and the pause silently disappears (or a batch is double-counted). Every mutation goes through enqueue(). A related race: crash recovery running between insertWorkout and saveSession of a start in flight deletes the new row as an "orphan", so recovery is queued too.
  12. Action tapped while JS is dead. End on the notification or lock screen is lost because nothing listens. The native side parks it (SharedPreferences / App Group) and startPendingActionReplay(), called from the root layout, replays it on launch and on every return to the foreground.
  13. Pause bridged by distance. Without a segment counter, the first fix after a resume is compared with the last one before the pause and a bus ride counts as running.
  14. Plugin order. expo-share-intent prepends the App Group without deduping; listed before it, your entitlement mod runs first and the duplicate comes back. List your plugin earlier so it runs later and collapses the array.
  15. Frozen "live" data. If the pipeline dies, an activity that never goes stale keeps showing old distance. The Live Activity sets a staleDate on every update and the active screen shows a "GPS signal lost" banner when no fix has arrived for 20 s.
  16. Foreground service killed on swipe. killServiceOnDestroy: true ends recording when the user swipes the app away; the final config keeps it false and relies on persisted state for the rest.

Restructuring notes

Decisions that look like clutter until a background launch breaks without them:

  • The task is defined from the root layout. A project layout only loads after the user opens the project, but the OS can relaunch the app headless to deliver locations. src/app/_layout.tsx imports tracking/task.ts (and calls startPendingActionReplay()) at module scope; the fitness _layout.tsx only builds the Stack. Journal and podcast follow the same rule for their own tasks.
  • Pending action replay is UI-free on purpose. handleAction only calls the controller's queued entry points (SQLite, location updates, Live Activity), so it is safe to run on a launch with no screen mounted.
  • SQLite without a provider. Journal and camera use SQLiteProvider; fitness opens a module-scope shared connection because the task has no React tree, and change events only fire for writes on the connection that enabled them. The UI therefore updates live from background writes.
  • Native tooling sits at the repo root. modules/ and plugins/ are found by autolinking and prebuild; app code touches only the thin liveactivity/index.ts wrapper.
  • The App Group is shared. Fitness widgets and the camera project's share extension use one group id; withWorkoutCapabilities is ordered after expo-share-intent's mods so the entitlement array ends clean.
  • Platform splits use file extensions (sync.ios.ts / sync.android.ts), so each bundle only contains its own health library.
  • Components stay dumb. PermissionFlow, RecoveryBanner, HoldButton, charts and map components take plain data and callbacks; the screens own the hooks.
  • Notification handling is project-scoped. Fitness uses its own Android notification channel (workout_live) and never asks for push permission at the root.

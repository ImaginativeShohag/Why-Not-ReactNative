04 · Background Fitness Tracker

The project that pushes you past the JavaScript boundary: background geolocation, sensors, Android foreground services, a hand-written config plugin, a local Expo Module in Swift and Kotlin, an iOS Live Activity, and home-screen widgets.

Native tier Physical devices required ~4–6 weeks Core skill: CNG, config plugins, native modules
Why this one fourth — and why it's the most valuable

Everything so far stayed inside the JS sandbox. This project cannot. Reliable background tracking needs platform capabilities, entitlements, foreground-service declarations, and eventually your own native code. This is where you learn what npx expo prebuild actually does, how a config plugin mutates the native project, and how to write an Expo Module — the skills that separate "I use Expo" from "I understand Expo".

UI design & screens

Design language

  • Tone: high-contrast and glanceable. The active-workout screen must be readable at arm's length, in sunlight, while moving.
  • Numbers dominate. One hero metric (duration or distance) at 56–72pt, secondary metrics in a row beneath.
  • Big touch targets. Minimum 64pt for pause/stop — the user has sweaty hands and is out of breath.
  • Anti-mistap: "Stop" requires a long-press with a filling progress ring, never a plain tap.
  • Always-visible tracking state. If GPS is degraded, say so immediately — silent bad data is worse than no data.

Architecture

The core problem

Your JS runtime may be suspended or killed at any moment while a workout is running. So:

Rule: the background task must persist every point immediately.

Never accumulate points in a JS variable and "save at the end." A task invocation may be the last code that ever runs. Write to SQLite inside the task callback, and let the UI read from the database rather than from memory.

Pure metrics, testable

Keep metrics.ts free of React, SQLite, and the location API: (points: Point[]) => Summary. Then you can feed it a recorded GPX from a real run and unit-test distance and pace against known values. This is the only realistic way to verify tracking correctness without going outside for every change.

The native layer

Step 1 — Understand CNG

This repo currently commits an android/ directory. Decide now:

ApproachMeaningTrade-off
CNG (recommended)ios/ and android/ are gitignored and regenerated by npx expo prebuild --clean.All native changes must be expressible as config plugins. Upgrades are trivial.
Committed nativeYou edit Xcode/Gradle directly.Full freedom, but SDK upgrades become manual merges and you lose the main reason to use Expo.

Take the CNG path. Anything you can't do with a plugin becomes the motivation to write one.

Step 2 — Write a config plugin by hand

Don't just install someone's plugin — author one. A plugin is a function (config) => config composed of mods:

ModWhat it editsUse it here for
withInfoPlistios/…/Info.plistNSLocationAlwaysAndWhenInUseUsageDescription, UIBackgroundModes: [location], NSSupportsLiveActivities, NSMotionUsageDescription
withEntitlementsPlistios entitlementsApp Group for widget/app data sharing, HealthKit entitlement
withAndroidManifestAndroidManifest.xmlACCESS_BACKGROUND_LOCATION, FOREGROUND_SERVICE_LOCATION, ACTIVITY_RECOGNITION, service declaration with foregroundServiceType
withAppBuildGradle / withProjectBuildGradleGradle filesAdd a dependency, bump minSdk, add the Glance widget module
withXcodeProjectproject.pbxprojAdd a widget-extension target and its build phases
withDangerousModarbitrary filesystemCopy Swift widget sources into the generated project. Use sparingly — it's the escape hatch.
 
// shape of your plugin — not the implementation
withWorkoutCapabilities(config, { appGroup })
  → withInfoPlist        add background modes + usage strings + LiveActivities
  → withEntitlementsPlist add App Group
  → withAndroidManifest   add permissions + foreground service
  → withDangerousMod      copy ios/WorkoutWidget/*.swift into the project
  → withXcodeProject      register the widget extension target

Test loop:
  npx expo prebuild --clean --platform ios
  → diff the generated ios/ to confirm your mods landed
  → open in Xcode only to VERIFY, never to edit

Step 3 — Write a local Expo Module

npx create-expo-module --local live-activity

Then implement:

ConceptSwift sideKotlin side

The JS side exposes one clean interface — startLiveActivity(attrs), updateLiveActivity(state), endLiveActivity() — and each platform implements it its own way. That asymmetry is the lesson.

Tracking pipeline & battery

Point processing

raw fix
  → reject if accuracy > 25 m
  → reject if implied speed > plausible max for the activity type
  → reject if timestamp is older than the last accepted point
  → smooth (moving average or a simple Kalman filter on lat/lng)
  → if distance from last accepted point < 5 m and not paused → skip
  → persist to SQLite
  → recompute rolling metrics (distance, pace, elevation)
  → push an update to the Live Activity / notification (throttled to ~1 Hz)

Run the same 30-minute route in both modes, record battery delta and route quality, and put the numbers in your lessons file. That measurement is the deliverable for this section.

Platform reality check

  • iOS: background location works with the location background mode and Always permission. The blue status bar / indicator will show. iOS may still throttle you; significant-change monitoring is the low-power fallback.
  • Android: you must run a foreground service with a persistent notification, declare foregroundServiceType="location", and request background location as a separate, second prompt. On top of that, OEM battery managers (Xiaomi, Huawei, Samsung, OnePlus) kill background work aggressively — test on a real device from at least one of those vendors, and add a "disable battery optimization" prompt.

Build order

M1 Go CNG

Goal: native projects become disposable.
  • Gitignore ios/ and android/; run npx expo prebuild --clean.
  • Confirm the app still builds and runs from a fully regenerated project.
  • Read the generated Info.plist and AndroidManifest and map each entry back to something in app.config.ts.
Checkpoint — rm -rf ios android && npx expo prebuild && npx expo run:ios works from clean. No manual Xcode steps.

M2 Foreground tracking

Goal: record a route with the app open.
  • Permission flow screen handling foreground → background → motion → notifications, in the right order.
  • watchPositionAsync with an accuracy filter.
  • SQLite schema for workouts and points; write every point.
  • Active screen with live metrics; keep the screen awake (expo-keep-awake).
  • Pure metrics module + unit tests against a recorded GPX.
Checkpoint — Walk 1 km with a measured route. Your distance is within ~3% of reality.

M3 Background tracking

Goal: it keeps working with the screen off and the app backgrounded.
  • TaskManager.defineTask at module scope; startLocationUpdatesAsync with the task name.
  • Android foreground service config with a persistent notification.
  • iOS background modes + Always permission, added via your own config plugin.
  • Crash/kill recovery: on launch, detect an unfinished workout and offer to resume.
  • Deferred updates for the battery-saver mode.
Checkpoint — Start a workout, lock the phone, put it in a pocket, walk 30 minutes. The route has no gaps. Then force-kill the app mid-workout and confirm the recorded data up to that moment is intact.

M4 Maps & visualization

Goal: the route looks good and renders fast.
  • Map with a route polyline; camera follows the user during the workout.
  • Pace-coloured polyline segments.
  • Douglas–Peucker simplification before rendering — 10,000 points must not be drawn raw.
  • Kilometre split markers and a splits table.
  • Charts for pace, elevation, and heart rate.
  • Static route thumbnails for the history list.
Checkpoint — Open a 3-hour hike with ~12k points. The detail screen renders in under a second and pans smoothly.

M5 Sensors

Goal: data beyond GPS.
  • Pedometer step count, live and historical.
  • Barometer-derived elevation, cross-checked against GPS altitude.
  • Device motion for auto-pause detection (stopped for N seconds → pause).
  • Activity-type inference as a stretch (walk vs run vs cycle from cadence).
Checkpoint — Auto-pause triggers within 10 s of stopping and resumes within 5 s of moving, with no false positives at a traffic light… then tune it, because it will have false positives.

M6 Your first local native module

Goal: Swift and Kotlin you wrote, called from JS.
  • npx create-expo-module --local live-activity.
  • Swift: ActivityKit attributes + start/update/end; a SwiftUI Live Activity view and Dynamic Island layouts.
  • Kotlin: an ongoing notification with pause/end actions as the Android counterpart.
  • Typed TS interface; events from native back to JS for the action buttons.
  • Wire it into the tracking pipeline, throttled to about one update per second.
Checkpoint — Lock the phone during a run. The Live Activity ticks on the lock screen and in the Dynamic Island, and its Pause button actually pauses the workout.

M7 Widgets

Goal: presence on the home screen.
  • iOS: a WidgetKit extension target added by your config plugin; share data through an App Group.
  • Android: a Glance widget; share via SharedPreferences/DataStore.
  • Small and medium sizes: today's steps, distance, and streak.
  • Widget timeline refresh policy — understand why you can't update it every second.
Checkpoint — expo prebuild --clean regenerates everything including the widget target. If it doesn't, your plugin is incomplete.

M8 Health sync & export

Goal: interoperate with the platform's health store.
  • Write workouts to HealthKit (iOS) and Health Connect (Android).
  • Read heart-rate samples back for the detail charts.
  • GPX export and share.
  • A shareable summary card rendered offscreen and exported as an image.
Checkpoint — A workout recorded in your app appears correctly in Apple Health / Health Connect with the right type, duration, distance, and route.

Expo Go cannot run this project at all

Background location, custom native modules, Live Activities, and widgets all require a development build. Budget for build times: a clean iOS build is several minutes locally, longer on EAS free tier. Set up --local builds early so your iteration loop isn't network-bound.

Failure modes to experience deliberately

  1. Task defined inside a component. It works in the foreground, then silently records nothing in the background. The single most common background-location bug.
  2. Points held in memory. Force-kill during a workout and lose the whole run. Persist in the task callback.
  3. Permission ordering. Request background location before foreground on Android — the prompt won't appear at all. Order matters and differs by OS version.
  4. Missing foreground service type. On modern Android, starting a location foreground service without declaring foregroundServiceType throws at runtime, not build time.
  5. OEM battery killer. Test on a Xiaomi or Samsung with default settings; your service gets killed after ~20 minutes. Detect it and educate the user.
  6. GPS drift while stationary. Stand still for five minutes with no accuracy filter and record 200 m of "distance". This is why the filter exists.
  7. Rendering raw polylines. Push 15,000 coordinates into a map polyline and watch the frame rate die.
  8. Live Activity update storm. Update at 10 Hz; iOS throttles or terminates the activity. Throttle to ~1 Hz.
  9. Hand-editing generated native code. Make a change in Xcode, then run prebuild --clean and watch it disappear. Feel it once; it's the lesson that makes plugins click.
  10. App Group mismatch. Widget shows no data because the app and the extension use different group identifiers. Silent and maddening.

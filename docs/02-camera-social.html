UI design & screens

Design language

  • Tone: media-first and dark by default. Chrome is translucent (blur) and floats over content; the photo is never letterboxed by UI.
  • Camera screen owns the full display including under the status bar. Controls sit in safe-area-aware overlays.
  • Immediate feedback: shutter → haptic + flash animation + thumbnail fly-to-corner. Latency perception matters more than actual latency here, which is why the shutter waits only for the sensor and never for disk (see the media pipeline).
  • Gestures over buttons where natural: pinch to zoom, single tap to focus, double-tap to flip, swipe up for the Library tab, swipe left/right between modes. Only the X button closes the camera.

Deep links carry the project prefix

The custom-scheme link for a post is whynotreactnative://projects/camera-social/post/<id>, not ://post/<id>, because the launcher owns the root and every project's routes are namespaced. The public https form stays short, https://<linkDomain>/post/<id>, and a pure rewriter in +native-intent maps it onto the namespaced route. Decide your link shape before M6: changing it after you have configured intent filters and associated domains is the expensive kind of change.

Interaction details worth building properly

  • Shutter feedback chain: haptic impact → white flash overlay (150 ms) → captured thumbnail scales down and flies to the corner button. All on the UI thread via Reanimated.
  • Pinch-to-zoom on the camera mapped to the camera's zoom range with a logarithmic curve (utils/zoom.ts) — a linear mapping feels sluggish wide and twitchy at tele. Zoom is a Reanimated shared value fed to the native view through useAnimatedProps, so a pinch never re-renders React.
  • Tap-to-focus with a shrinking ring at the tap point that fades after ~1s. expo-camera has no point-of-interest API, so the ring is visual and the code nudges a refocus by toggling the autofocus prop off and on 60 ms later.
  • Mode strip that snaps between Photo/Video/Scan, with the shutter morphing shape per mode (circle → red rounded square → hidden) and a Skia progress ring while recording.
  • Zoom transition from the grid thumbnail into the full viewer. Expo Router's Link.AppleZoom provides it on iOS 18+; every other platform and version gets a transparent modal with a cross-fade and the app's own drag-to-dismiss (utils/platform.ts decides which).
  • Swipe-down-to-dismiss the viewer with the background opacity tracking the drag distance. Three gesture owners (pager, pinch-zoom, dismiss) share the screen; state decides who owns the touch (see failure mode 6).
  • Crop overlay: simultaneous pinch + pan + rotate composed with Gesture Handler's Gesture.Simultaneous, with clamping so the image can never leave the crop frame, momentum via withDecay, and a 90-degree snap when the rotation passes 45 degrees. Only a normalized 0..1 rect ever leaves the component.

How it sits in the launcher

This project is one vertical slice inside a launcher app that holds six isolated sample projects. Nothing in the launcher knows about camera features, and nothing here reaches into another project. The rules that shape the code:

ConcernWhere it livesWhy
RegistryAn entry with slug camera-social in src/shared/config/projects.tsThe launcher list and the root Stack.Screen (projects/camera-social, headerShown: false) are generated from it.
Routessrc/app/projects/camera-social/Expo Router owns this tree: any file under it is a reachable route, so only screens and layouts go here.
Everything elsesrc/projects/camera-social/Hooks, components, editor math, media, db, models, stores, utils and __tests__/. Unit tests never live under src/app/, or they would become routes.
Project layout_layout.tsx owns the inner Stack, the SQLiteProvider and the dark themeThe root layout already mounts the query client, safe area, gesture root and theme. This layout adds only what is yours.
Own databasecamera-social.dbProjects never share a database file, and each runs its own migrations.
Share intentShareIntentProvider and useInboundShareRouting in the root src/app/_layout.tsxThe OS can hand the app shared media while the user is in the launcher or another project, before this project's layout has ever mounted.
External URLssrc/app/+native-intent.tsx calls the pure rewriteCameraSocialPathThe launcher owns the root, so every project supplies a pure rewriter and the first match wins.
IsolationESLint no-restricted-importsNo imports from other projects. The root layout and +native-intent are the composition root and may import one entry point per project.

Two consequences for you as the builder. First, useInboundShareRouting is the one piece of this project that is mounted outside its layout, so it must depend on nothing the layout provides (no useSQLiteContext). Second, the Profile tab stays mounted underneath the camera modal, so any state both screens read must be shared, not per-hook (this is why settings live in a Zustand store).

The one thing here that might belong in shared/

PermissionGate (below) is written to be project-agnostic and other projects may want it. Keep it in this slice and promote it to src/shared/ only when a second project actually reaches for it. Premature promotion is how a "shared" folder turns into a junk drawer, and the ESLint isolation rule would stop other projects importing it from here anyway.

Key architectural decision: the editor as an operation list

Do not mutate the image on every gesture. Instead the editor appends plain descriptors (models/Asset.ts) and derives everything from the list:

type Op =
  | { type: "crop";   rect: NormRect; aspect: AspectPreset }   // rect is 0..1, in the image AS DISPLAYED at that point
  | { type: "rotate"; degrees: 90 | -90 }
  | { type: "flip";   axis: "horizontal" | "vertical" }
  | { type: "filter"; name: FilterName; intensity: number }
  | { type: "adjust"; values: { brightness; contrast; saturation } }   // each -1..1

EditorState = { sourceUri, operations: Op[], cursor }      // cursor = undo/redo position

resolveOperations(ops.slice(0, cursor)) -> ResolvedEdit      // ONE canonical edit:
        output = crop(flip(rotate(source))) + one colour matrix

Preview -> Skia canvas draws a 1600px proxy with previewSteps (a Group transform) and one <ColorMatrix>
Commit  -> applyOperations: manipulator rotate -> flip -> crop (full resolution), then
           one Skia colour pass if the matrix is not the identity

Three details make this hold up. The crop is normalized (0..1), so the 1600 px proxy and the 12 to 48 MP original map onto it identically and pixels are only computed at export (cropToPixels). Filter and adjustments compose into one 4x5 matrix (buildColorMatrix), so the GPU does a single pass in both the preview and the export. And the history reducer merges consecutive drags of the same slider or filter into one undo step, so a continuous control commits once on release while a draft value drives the live preview.

This gives you free undo/redo, a cheap preview, non-destructive editing, one obvious place to unit-test, and re-editing without generation loss: an edited row stores source_id and the operations JSON, and reopening it starts from the untouched original with those ops back on the undo stack (pickEditBase).

Data model

src/projects/camera-social/db/schema.tssql

CREATE INDEX idx_captures_timeline ON captures (created_at DESC);

CREATE TABLE settings (key TEXT PRIMARY KEY NOT NULL, value TEXT NOT NULL);
  • PRAGMA journal_mode = WAL lets the feed read while ingest writes. Migrations are keyed by PRAGMA user_version: each step and its version bump run in the same transaction, so a crash leaves neither half behind. Adding a column later means appending MIGRATIONS[2] and bumping SCHEMA_VERSION.
  • Paths are stored relative to the Documents directory and resolved on read (media/paths.ts), because the iOS container path can change across reinstalls and restores.
  • Trim is metadata (trim_start_ms, trim_end_ms); the original video file is never rewritten. A null end means "to the end of the clip".
  • The app has no TanStack Query keys: local SQLite is the source of truth. useCaptures.ts loads once, subscribes with addDatabaseChangeListener (enabled by options={{ enableChangeListener: true }} on the provider), ignores events from other projects' database files, and reloads with a short debounce so a burst of inserts costs one query.
  • Settings are one JSON row, hydrated once into a Zustand store (settingsStore.ts) with pure parseSettings / patchSettings / hydrateSettings helpers. One shared copy matters because the Profile tab stays mounted under the camera modal.

Permission state machine

            ┌──────────────┐
            │  undetermined│
            └──────┬───────┘
       show rationale screen
                   │ user taps "Allow"
            ┌──────▼───────┐
            │ system prompt│
            └───┬──────┬───┘
        granted │      │ denied
            ┌───▼──┐ ┌─▼─────────────────┐
            │ USE  │ │ blocked screen    │
            └──────┘ │ "Open Settings" → │
                     │ Linking.openSettings()
                     └───────────────────┘
   iOS extra branch: media library → "limited"
        → show banner + MediaLibrary.presentPermissionsPicker()

Build this once as a reusable <PermissionGate> component in src/projects/camera-social/components/PermissionGate.tsx. It is dumb: it receives the permission response, an onRequest callback, an onRecheck callback and copy strings, and a pure gateState() maps the response to loading | rationale | blocked | granted. The key rule is that blocked means status === "denied" && !canAskAgain: the OS will never show its prompt again, so calling requestPermission() is a silent no-op and the only exit is Linking.openSettings(). Coming back from Settings does not re-render by itself, so the gate listens for AppState becoming active and calls onRecheck.

Permissions are granular on purpose. The camera is a hard dependency and sits behind the gate. The microphone is a soft dependency: if it is denied, video still records with mute set and a banner offers to ask or open Settings. Saving to the gallery asks for write-only media-library access (requestPermissionsAsync(true)), a far less alarming prompt than full read access, which only the Library tab requests.

The media pipeline

CAPTURE   (useCapture.ts)
  CameraView.takePictureAsync({ quality: 0.9, exif, shutterSound })
     └─► temp file in the cache directory (the OS may evict it)
  Calls are chained on one promise queue: the native session rejects overlapping
  captures. The returned promise resolves when the SENSOR has the frame, so the
  shutter UI never waits for disk. Each link ends in .catch so one failure does
  not poison later captures.

INGEST    (media/ingest.ts) - Nothing downstream ever sees a cache-dir URI
  1. if EXIF Orientation != 1: bake it into the pixels (manipulator re-encode, JPEG q0.95)
     and rewrite the stored EXIF to Orientation 1
  2. move (if we own the temp file) or copy the file into Documents/camera-social/originals
  3. measure width/height if the source (library, share) did not supply them
  4. thumbnail: manipulator resize to a ~400px short edge, JPEG q0.7, into .../thumbs
     (if this fails, delete the copied original so no orphan is left)
  5. insert the captures row with RELATIVE paths and the file size

EDIT      (editor/applyOperations.ts)
  ops[] -> resolveOperations -> rotate -> flip -> crop (full-res) -> save JPEG q0.92
  -> ONE Skia colour pass if the matrix is not the identity (long edge capped at 4096)
  -> ingest the result as a NEW row (origin "edit", source_id, operations); original kept

EXPORT    (utils/shareOut.ts)
  share:    expo-sharing shareAsync(uri, { mimeType, dialogTitle, UTI })
  gallery:  write-only permission -> Album.get("Why Not RN") or create it -> Asset.create(uri, album)
  clipboard: link via setStringAsync; image via a 1600px manipulator copy whose base64 is produced natively

Video follows the same shape with different details: recordAsync({ maxDuration }) returns only a URI, so the real duration is read from the file by a throwaway expo-video player (media/videoInfo.ts), the poster frame comes from expo-video-thumbnails, and the file is copied (not moved) into originals. Backgrounding the app mid-recording calls stopRecording() so the partial clip is kept.

Who owns the file? ownsFile: true means ingest moves the temp file. After that the caller's URI is stale, so anything later (for example saving to the gallery) must read the stored location back from the row, not reuse the temp URI.

Never move pixels through JS

Reading image bytes into a JS array to "apply a filter" will kill you on a 12MP photo. Filters belong on the GPU (Skia shaders / color matrices) or in a native manipulator call. The only bytes that cross into JS in this project are the encoded JPEG on its way to disk. If you find yourself writing a per-pixel loop in JS, stop.

M3 Media library

Goal: browse the device's photos properly.
  • useAssets built on the SDK 57 object API of expo-media-library: a MediaLibrary.Query chained with .within(AssetField.MEDIA_TYPE, [...]), .orderBy(...), .limit(90), .offset(n) and an optional .album(new Album(id)), executed with exeForMetadata() (cheap fields only, no file resolution). Guard overlapping pages with refs and a generation counter.
  • Grid cells use ph://<id> on iOS (PhotoKit serves a sized thumbnail) and the id itself on Android. Resolve a real file (resolveLibraryAsset) only when the user taps Edit, Add or Share.
  • Album picker sheet, multi-select with a selection bar, and extraData so recycled cells re-render on selection changes.
  • iOS limited access: detect permission.accessPrivileges === "limited", show the banner, call MediaLibrary.presentPermissionsPicker(), and refresh when the selection changes.
  • Video assets show a duration badge.
Checkpoint — Test on a device with 5,000+ photos. Scrolling stays smooth and memory is flat. Switch albums while a page is loading: the late page never appears in the new album. On iOS choose "Select photos" and confirm the banner and picker work.

M4 The editor

Goal: a crop/rotate/filter/adjust editor with undo, whose output matches its preview.
  • Pure first, with tests: operations.ts (resolveOperations, previewSteps), history.ts (push, undo, redo, merge rules), cropMath.ts, colorMatrix.ts. Write the tests before the UI.
  • Crop overlay: Gesture.Simultaneous(pinch, pan, rotation) with worklet clamping, withDecay momentum, aspect presets (free, 1:1, 4:5, 16:9) and a resize handle for free-form crops. Emit only a normalized rect, and only when a gesture ends.
  • Live preview: a Skia <Canvas> drawing a ≤1600 px proxy inside a <Group transform> with a single <ColorMatrix>. No re-encoding per frame.
  • Filter strip and adjust sliders. Sliders update a draft for the preview and push one history op on release.
  • Commit: applyOperations(source, ops, deps) with the native calls injected (nativeDeps.ts), then ingest the result as a new row with sourceId and operations. Re-opening an edited row uses pickEditBase.
Checkpoint — Apply crop → rotate → filter, undo all three, redo all three, save. The output matches the preview exactly. Preview/output mismatch is the classic editor bug. Drag Brightness then Contrast and undo once: only Contrast reverts. Re-open the saved edit: the ops are back on the undo stack and the base is the original. npx jest --no-watchman passes the operations, history, cropMath, applyOperations and editBase suites.

M5 Viewer & transitions

Goal: the polish layer.
  • Horizontal pager (a FlatList with pagingEnabled, getItemLayout and initialScrollIndex from the deep-linked id) of ZoomableImage pages.
  • ZoomableImage: pinch, pan-when-zoomed and double-tap composed with Gesture.Simultaneous and Gesture.Exclusive; the pan uses manualActivation(true) so it only claims touches once zoomed.

M7 Video

Goal: the second media type, which breaks half your assumptions.
  • Record with recordAsync({ maxDuration }), a stop button, and a progress ring (a Skia path whose end is a derived value). Keep the elapsed label to whole seconds so React skips redundant renders.
  • Microphone permission is separate from camera: soft-fail with mute and a banner.
  • Playback with expo-video: useVideoPlayer(source, setup) and <VideoView player={player} />. Read the true duration with a throwaway createVideoPlayer, and release it.
  • Thumbnail from expo-video-thumbnails getThumbnailAsync(uri, { time }), resized with the same manipulator helper as photos.
  • Trim UI with a scrubbable filmstrip that stores trim_start_ms / trim_end_ms; the player loops inside the window (utils/trim.ts's pure trimLoopSeek) using timeUpdate and playToEnd listeners and seekBy, never by mutating player.currentTime outside the setup callback.
Checkpoint — Record 60 s, background the app mid-recording, return. You handle it (this project stops cleanly and keeps the clip) rather than crashing. Trim only the start of a clip and watch it loop: every loop begins at the trim start, not at 0:00.

Failure modes to experience deliberately

Reproduce each one on purpose, see how it shows up, then see how the finished code prevents it.

  1. The permission dead-end. Shows up as: deny camera access, then open the camera screen and get a black view with no explanation — or tapping "Allow" does nothing because the OS will not prompt again. Final code: gateState() returns blocked only when denied and canAskAgain is false, then offers Linking.openSettings() and re-checks on AppState active. A denied microphone degrades to muted video instead of blocking.
  2. Camera not released. Shows up as: battery drain, and a frozen preview when you return from the post viewer pushed on top of the camera. Final code: useIsFocused() drives active on iOS and gates mounting on Android, where the prop does not exist.
  3. Cache directory eviction. Shows up as: a capture's uri from the cache directory is saved in your DB, and a week later the file is gone. Final code: ingest always lands files in Documents, and the DB stores paths relative to it, resolved on every read, because the iOS container path can also change across reinstalls and restores.
  4. Orientation/EXIF rotation. Shows up as: a photo shot in landscape displays sideways after manipulation because EXIF orientation was dropped. Final code: ingest bakes a non-1 orientation into the pixels and rewrites the stored EXIF to 1, so viewers do not rotate it twice.
  5. OOM on large images. Shows up as: ten 48MP originals in a grid at full resolution kill the app. Final code: ~400 px thumbnails for the feed, ph:// sized thumbnails in the library grid, allowDownscaling and recyclingKey on cells, and a 4096 px cap on the Skia colour pass.
  6. Gesture conflicts. Shows up as: the pager swipes while you pan a zoomed photo, or a dismiss drag steals a pinch; one gesture wins and the UX feels broken. Final code: state decides ownership: the image pan uses manualActivation and only activates when zoomed, the pager gets scrollEnabled={!zoomed}, and the dismiss container is disabled while zoomed and uses offset thresholds. Gesture.Race / Exclusive keep taps from double-firing.
  7. Preview ≠ output. Shows up as: the saved crop is offset from what you saw, because the preview used screen coordinates and the manipulator uses source pixels. Final code: one normalized rect and one ResolvedEdit feed both renderers, rotation changes the crop's coordinate space explicitly (orientedSize), and tests pin the call order and the corner mapping.
  8. Overlapping captures and poisoned queues. Shows up as: rapid taps reject with a native error, or one failed capture stops all later ones. Final code: sensor calls are chained on a queue whose link swallows rejections, and each failure decrements the pending counter so the spinner stops.
  9. Stale async results. Shows up as: switching albums mid-load shows photos from the previous album. Final code: a generation counter in useAssets; only the current generation may write state or clear the in-flight flag.
  10. Stale shared state. Shows up as: toggling a camera setting, then a Profile toggle, silently reverts the first. Final code: one Zustand settings store and per-key patches, with the write performed outside the state updater and held back until hydration.
  11. Lost inbound shares. Shows up as: sharing from another app while the launcher is open does nothing, or the inbound screen re-opens on every navigation. Final code: provider and routing hook at the root; resetOnBackground: false keeps the payload until imported; reset() clears it afterwards.
  12. Android scoped storage. Writing to the gallery behaves differently across Android versions. Final code: the gallery write goes through expo-media-library into a dedicated album. Test on both an older and a newer device or emulator.

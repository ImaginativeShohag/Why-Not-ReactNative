01 · Offline-First Journal

A private, encrypted-at-rest journaling app that is fully functional with the network permanently off — and reconciles correctly when it comes back.

Foundation tier Runs in Expo Go ~2 weeks Core skill: local-first data
Why this one first

Almost every RN tutorial starts by fetching from an API, which teaches you to treat the network as the source of truth. That habit produces apps that spin forever in a tunnel. Starting local-first inverts the model: the device is the source of truth, and the server is a replica you reconcile with. Everything else in this path is easier once you think that way.

UI design & screens

Design language

  • Tone: calm, paper-like, content-forward. Generous whitespace, one accent colour, serif for entry body text and sans for chrome.
  • Density: the timeline is the app. Everything else is a modal or a sheet over it.
  • Themes: full light/dark support driven by useColorScheme, plus a user override stored locally (system / light / dark) — this repo's themed-text / themed-view pattern already gives you the base.
  • Motion: subtle only. Entry insert/delete uses layout animation; nothing bounces.

Interaction details worth building properly

  • Autosave: debounce ~800 ms, write to the drafts row, show a quiet "Saved HH:MM ✓". Never a spinner.
  • Swipe to delete on a timeline row, using Gesture Handler's swipeable — with an undo snackbar rather than a confirm dialog.
  • Sticky day headers in FlashList, driven by section data rather than a separate SectionList.
  • Optimistic delete: the row animates out immediately; the DB delete happens after the undo window expires.
  • Keyboard handling: the compose toolbar must sit on the keyboard, not behind it. Use KeyboardAvoidingView plus react-native-keyboard-controller if you want it smooth.
  • Empty states: first launch, no search results, and a filtered day with nothing in it are three different empty states with three different messages.

Layer rules

  • db/queries/* are pure functions of the db handle. No React, no stores. This makes them unit-testable without a renderer.
  • features/*/hooks are the only place that binds queries to React (via a live-query hook or TanStack Query with a local query function).
  • components/ui never imports a store or a db module. Props and callbacks only — same discipline you apply to SwiftUI subviews.
  • The sync task is defined at module scope, imported from the root layout. If you define it inside a component it will never run in the background.

Write path

User taps Save
   │
   ├─► BEGIN TRANSACTION
   │     UPDATE entries  SET …, dirty = 1, updated_at = now
   │     INSERT INTO outbox (op='update', entity_id=…, payload=…)
   │   COMMIT
   │
   ├─► UI re-renders from the local read (instant, no network)
   │
   └─► syncEngine.kick()  ── if online ──► POST /entries
                                             │
                                    2xx ─────┤─► mark row clean,
                                             │   delete outbox item
                                    4xx ─────┤─► move to dead-letter,
                                             │   surface in Settings
                                    5xx/net ─┴─► leave in outbox,
                                                 backoff, retry later

The transaction is non-negotiable: the row change and the outbox entry must land together or not at all.

Read path

Two viable designs — build the first, then try the second and compare:

  1. Live query. A hook that subscribes to DB change events and re-runs its query. Simplest mental model; you can build it yourself on top of addDatabaseChangeListener, or use Drizzle's live-query helper.
  2. TanStack Query over local reads. Query function reads SQLite, mutations invalidate keys. More boilerplate but a uniform API for local and remote — and it's the same pattern you'll use in Project 03.

Sync semantics to decide (and write down)

  • Conflict rule: last-write-wins by updated_at? Or field-level merge? LWW is fine here — but state it explicitly.
  • Idempotency: the client-generated ULID is the idempotency key. The server must upsert on it.
  • Backoff: exponential with jitter, capped. Cap the attempt count and dead-letter after N.
  • Clock skew: never trust the device clock for ordering across devices. Use a server-assigned version/lamport counter if you go multi-device.
No backend? Good.

Fake it. Point the sync engine at a tiny mock server (a local JSON server, a Cloudflare Worker, or Supabase's REST endpoint). The point is exercising the queue, retries, and reconciliation — not the server code. Add an artificial-latency and artificial-failure toggle in Settings so you can test 5xx paths on demand.

Build order

M1 Skeleton & database

Goal: a tab shell with a real SQLite database behind it.
  • Create the route tree: tabs, entry detail, compose modal.
  • Install expo-sqlite; wire SQLiteProvider with an onInit migration function.
  • Write migration v1: entries table + PRAGMA journal_mode = 'wal'.
  • Seed 30 fake entries on first launch so the list has substance.
  • Hook up the Drizzle Studio dev plugin and confirm you can see rows.
Checkpoint — Delete the app, reinstall, and confirm the migration runs exactly once and user_version reads 1.

M2 CRUD + timeline

Goal: create, read, update, delete entries with a list that never stutters.
  • Timeline with FlashList, grouped by day, sticky headers.
  • Compose modal with debounced autosave.
  • Swipe-to-delete with soft delete + undo snackbar.
  • Live-query hook so the list updates without a manual refetch.
  • Mood picker and tag chips (many-to-many join).
Checkpoint — 500 seeded entries, scroll to the bottom fast. Frame rate holds. If it doesn't, fix the row component before moving on.

M3 Search & migration #2

Goal: FTS5 search, added via a real schema migration on top of existing data.
  • Write migration v2 that creates entries_fts and backfills it from existing rows.
  • Add triggers to keep FTS in sync on insert/update/delete.
  • Search screen with debounced input, snippet highlighting, and filter chips.
  • Compare timings against a naive LIKE query over the same data — note the numbers.
Checkpoint — Install v1, add entries, then upgrade to v2. All pre-existing entries are searchable. This is the migration lesson.

M4 Attachments & filesystem

Goal: photos attached to entries, stored on disk, cleaned up on delete.
  • expo-image-picker to select; copy the asset into your app's document directory with the new File/Directory API.
  • Generate and cache thumbnails with expo-image-manipulator.
  • Render with expo-image (this repo already has it) and its blurhash placeholder.
  • On hard delete, remove orphaned files. Write a "sweep orphans" maintenance function.
Checkpoint — Attach 10 photos, delete the entries, confirm the document directory is empty and the DB has no dangling rows.

M5 Reminders

Goal: a daily notification that opens the compose screen.
  • Set a notification handler at module scope; request permissions with a proper pre-prompt rationale screen.
  • Android: create a notification channel before requesting permission.
  • Schedule with a daily calendar trigger; reschedule when the user changes the time; cancel on toggle-off.
  • Handle the response listener → route to /entry/compose. Also handle the cold start case via the last-response API.
Checkpoint — Force-quit the app, tap a delivered notification, land directly on the compose screen. Cold-start routing is the part everyone gets wrong.

M6 Sync engine

Goal: the outbox drains reliably and exactly once.
  • Outbox table + transactional writes.
  • Sync engine: pull (since cursor) → merge → push (drain outbox) → update cursor.
  • Trigger on: app foreground, network regained (expo-network state listener), manual button, and a periodic background task.
  • Register a background task with expo-background-task; log every invocation so you can see how rarely iOS actually runs it.
  • Sync status UI: idle / syncing / N pending / error, in Settings and as a subtle timeline header state.
Checkpoint — Airplane mode, create/edit/delete 20 entries, force-quit, reopen, disable airplane mode. Server ends up with exactly the right 20 operations. No duplicates.

M7 Lock, export, polish

Goal: shippable feel.
  • Biometric lock with expo-local-authentication; re-lock when the app goes to background past a threshold (AppState listener).
  • Export to JSON and Markdown; save via expo-sharing.
  • Onboarding flow, gated by a persisted flag.
  • Haptics on save/delete (this repo already has expo-haptics).
  • App icon, splash, and a real name.
Checkpoint — Hand the phone to someone else with the app locked. They can't read a single entry, including from the app switcher preview (hide content on background).

SDK 57 note

expo-file-system now exposes the object-oriented File/Directory API by default; the old function-based API moved to a legacy import path. Similarly expo-background-fetch is superseded by expo-background-task. Read the current SDK 57 page for each module rather than an older blog post.

Failure modes to experience deliberately

  1. Migration that drops data. Write a bad v2 migration (a table recreate without a backfill), run it against real data, watch entries vanish. Then write the correct one. This teaches you why user_version gating and backfills matter more than any ORM feature.
  2. FTS drift. Update a row without the trigger in place; search returns the stale text. Learn to rebuild the FTS index.
  3. Duplicate sync. Kick the sync engine twice concurrently with no mutex. Watch the server get two copies. Add a run-lock.
  4. Background task that never fires. Register on iOS, wait a day, note it fired zero or once. Understand that background execution is a hint, not a schedule — your app must still work if it never runs.
  5. Notification permission denied. Deny it, then try to schedule. Handle it gracefully with a "open Settings" path via Linking.
  6. Blocked JS thread. Run a large synchronous query on the JS thread during a scroll; watch FPS collapse. Move it to an async call or paginate.
  7. App switcher leak. Lock the app but forget to blur the snapshot — the journal is readable in the task switcher. Fix it.

Stretch goals

  • SQLCipher-style encryption — store the DB key in expo-secure-store, gate it behind biometrics.
  • Multi-device sync with real conflicts — two simulators, same account, edit the same entry offline on both. Now LWW hurts; try a CRDT or field-level merge.
  • Widgets — a "today's entry" home-screen widget (this is really Project 04 territory; a good preview).
  • Web target — the app already builds for web via react-native-web. Swap SQLite for IndexedDB behind the same query interface and see how well your layering held up.
  • Statistics screen — mood over time, writing streaks, word counts. A good excuse to learn victory-native or Skia charts.

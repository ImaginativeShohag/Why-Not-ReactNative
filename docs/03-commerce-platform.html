03 · Production Commerce App

Take the store already in this repo and make it production-shaped: real auth with token refresh, secure storage, push notifications, payments, universal links, environments, analytics, crash reporting, and tests.

Production tier Dev build + a backend ~4 weeks Core skill: everything around the features
Why this one third

You already have the fun part — screens, a cart, product lists. What's missing is everything that makes an app shippable: what happens when the token expires mid-checkout, when a push arrives during a cold start, when the API returns 500, when a user has two devices, when you need a staging build alongside production. This project is entirely about that layer.

UI design & screens

Design language

  • Tone: commercial and trustworthy. Product imagery leads; typography is quiet; the primary CTA is the only saturated element on screen.
  • Skeletons, not spinners for anything that has a known shape. Spinners only for indeterminate actions like payment authorization.
  • Every price is formatted through one function using Intl.NumberFormat with the user's locale and the store's currency. Never string-concatenate a currency symbol.
  • Checkout is a linear, interruption-safe flow — the user can background the app at any step and come back to the same state.

Auth & token refresh

The state machine

          ┌──────────┐
          │ loading  │  (reading keychain on boot)
          └────┬─────┘
       token?  │  no token
     ┌─────────┴─────────┐
     ▼                   ▼
┌──────────┐        ┌──────────┐
│  signed  │◄──────►│  signed  │
│    in    │ logout │   out    │
└────┬─────┘        └──────────┘
     │ 401 from any request
     ▼
┌──────────────┐   success   ┌──────────┐
│  refreshing  │────────────►│ signed in│
└──────┬───────┘             └──────────┘
       │ refresh fails (401/invalid)
       ▼
  clear tokens → signed out → route to /sign-in

Single-flight refresh — the part everyone gets wrong

Five requests fire in parallel. All five get a 401. A naive interceptor performs five refreshes; four of them invalidate the token the fifth just obtained, and the user is logged out for no reason.

refreshCoordinator:
  if (inFlightPromise) return inFlightPromise      ← the whole trick
  inFlightPromise = doRefresh()
    .finally(() => inFlightPromise = null)
  return inFlightPromise

axios response interceptor on 401:
  if (request.isRetry) → give up, sign out
  newToken = await refreshCoordinator.get()
  retry original request once with newToken

Verify it: add an artificial-401 toggle in a dev menu, fire six requests at once, and assert exactly one refresh call hits the network.

Push & deep-link routing

REGISTRATION
  request permission (with rationale first)
  Android: create channels BEFORE requesting
  getExpoPushTokenAsync({ projectId })      ← projectId from Constants
  POST token + deviceId to your backend, tied to the user
  re-register on: login, token change, app update

DELIVERY  (three very different cases)
  1. Foreground → setNotificationHandler decides banner/sound/list
  2. Background, app alive → response listener fires on tap
  3. Cold start → getLastNotificationResponseAsync() on boot

ROUTING
  notification.data = { type: 'order', orderId: '10482' }
       │
       ├─ parse into a route:  /order/10482
       ├─ ensure auth is resolved FIRST (else the guard bounces you to sign-in)
       └─ router.push after the navigation tree is mounted

TEARDOWN
  remove listeners on unmount; unregister token on logout
The cold-start race

On a cold start from a push, three things race: reading the token from the keychain, mounting the router, and handling the notification response. Get the order wrong and the user lands on the sign-in screen instead of their order. Solution: hold the splash screen until the session resolves, buffer the pending route, and replay it once the navigator is ready. Build this deliberately — it's the single most valuable thing in this project.

Build order

M1 Audit & foundations

Goal: know what you have, and make config real.
  • Write the audit doc.
  • Migrate app.json → app.config.ts with three variants.
  • Typed env access module; base URL from config.
  • Normalize API errors into one ApiError shape with a user-facing message.
  • Upgrade the query-key file into a factory.
Checkpoint — Dev, preview, and production builds installed side-by-side on one device, each hitting a different API.

M2 Auth

Goal: a session that survives everything.
  • SessionProvider + useSession; splash held until the session resolves.
  • Secure token storage; sign-in / sign-up / sign-out.
  • Stack.Protected guards for the (app) and (auth) groups.
  • Redirect-after-login: deep-link to a protected route while signed out → sign in → land on the original destination.
  • Refresh coordinator + axios interceptors.
  • Optional biometric unlock for returning users.
Checkpoint — Six concurrent requests with an expired token trigger exactly one refresh and zero spurious logouts.

M3 Social sign-in

Goal: OAuth without a WebView hack.
  • Sign in with Apple (required by App Store rules if you offer other social logins).
  • Google via expo-auth-session with PKCE and a proper redirect URI.
  • WebBrowser.maybeCompleteAuthSession() and the redirect plumbing.
  • Account linking: same email arriving via two providers.
Checkpoint — Cancel the OAuth sheet mid-flow. The app returns to a clean state, not a stuck spinner.

M4 Catalog & query mastery

Goal: data layer that feels instant.
  • Infinite scroll on product lists with useInfiniteQuery.
  • Prefetch product detail on list-item press-in.
  • Search with debounce, placeholderData to keep previous results, and recents.
  • Wishlist with optimistic toggle + rollback on failure.
  • Cache persistence so a cold start shows last-known data immediately.
  • Wire focusManager to AppState and onlineManager to expo-network.
Checkpoint — Airplane mode cold start shows cached products with a "showing offline data" banner, not an error screen.

M5 Cart & checkout

Goal: an interruption-safe purchase flow.
  • Cart persistence + merge with the server cart on login (decide the merge rule and write it down).
  • Multi-step checkout with per-step validation and a resumable state.
  • Address form with correct textContentType/autoComplete so OS autofill works.
  • Promo codes, shipping options, tax recalculation.
  • Order placement with an idempotency key — a double-tap must not create two orders.
Checkpoint — Force-quit at the payment step and relaunch. The user resumes where they were, with the cart intact.

M6 Payments

Goal: money actually moves (in test mode).
  • Stripe payment sheet (or your provider's equivalent) with a server-created payment intent.
  • Apple Pay / Google Pay.
  • 3DS / SCA challenge handling.
  • Failure paths: declined card, network drop mid-confirm, app killed after charge but before your server callback.
  • Understand the store rules: physical goods → external payments fine; digital content → in-app purchase required.
Checkpoint — Kill the app immediately after confirming payment. On relaunch, the order state is correct — the server, not the client, is the source of truth.

M7 Push & universal links

Goal: the app can be entered from outside.
  • Push registration, backend association, permission rationale.
  • Notification categories with actions ("Track", "Reorder").
  • Badge count management.
  • Routing from a tap in all three delivery states, including cold start.
  • Universal links: host an AASA file and assetlinks.json, configure associatedDomains and Android intent filters.
Checkpoint — Tap https://yourdomain/p/42 in Messages on a device with the app installed. It opens the product screen directly, no browser bounce.

M8 Observability & tests

Goal: you'd find out about a bug before your users tell you.
  • Crash reporting with uploaded source maps — verify a stack trace is readable in the dashboard.
  • Analytics facade with a typed event catalogue (view_product, add_to_cart, begin_checkout, purchase).
  • Error boundaries per route group with a real recovery action.
  • Unit tests for the refresh coordinator, cart math, and money formatting.
  • MSW-mocked tests for the key hooks.
  • One Maestro flow: sign in → add to cart → checkout.
  • Accessibility pass: labels, roles, dynamic type, contrast; then run it with VoiceOver/TalkBack.
Checkpoint — Deliberately throw in production-mode code and read the symbolicated stack trace in your dashboard.

Backend options if you don't want to write one

Supabase (auth + Postgres + realtime, generous free tier), Medusa or Saleor (real commerce backends), or a small Hono/Express service on a free host. FakeStoreAPI — what this repo uses now — has no auth and no persistence, so it can't take you past M3. Plan to replace it.

Failure modes to experience deliberately

  1. The refresh stampede. Described above. Reproduce it before you fix it, so you recognise the symptom (random logouts) in the wild.
  2. Token in AsyncStorage. Put one there, then read it off a jailbroken/rooted device or an emulator's file system. Now you'll never do it again.
  3. Guard flicker. Render the protected tree before the session finishes loading, and users see the sign-in screen flash on every cold start. Fix by holding the splash.
  4. Double order. Ship without an idempotency key, then double-tap "Place order" on a slow network.
  5. Optimistic update without rollback. Toggle a wishlist item offline; the server rejects it; the UI now lies permanently.
  6. Cached PII. Persist the query cache including the user profile, then log out. The next user on the device sees the previous person's data. Clear the cache on logout.
  7. Deep link to a protected route while signed out. Without an intent buffer, the user signs in and lands on Home, having lost what they clicked.
  8. Unsymbolicated crashes. Ship without source maps and try to read index.android.bundle:1:284736.
  9. Hardcoded currency. Test with a locale where the symbol goes after the number and the decimal separator is a comma.

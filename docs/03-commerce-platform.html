Why this one third

Screens, a cart and product lists are the fun part, and the easy part. What makes an app shippable is everything around them: what happens when the token expires mid-checkout, when a push arrives during a cold start, when the API returns 500, when a user has two devices, when you need a staging build alongside production. This project is entirely about that layer.

Work through the milestones in order. After each one, open the matching files in the finished code, and use the quiz bank (docs/training/, project 03) to test whether you can find and explain what you built.

Production-readiness checklist

"Is this production-ready?" is too vague to answer. Break it into concrete questions, find the evidence for each one in the code, then rank the gaps. You can reuse this method on any codebase.

The method

  1. Start from a failure, not a file. Pick something that will happen in production (the token expires, the user opens a deep link while signed out, the app is killed mid-payment) and ask what the code does.
  2. Find the evidence. Open the file that would handle it, or grep for it (grep -rn "interceptors" src/, grep -rn "AsyncStorage" src/ | grep -i token). If nothing handles it, that's the finding.
  3. Rank the gap: P0 means not shippable, P1 means you lose users or data, P2 is polish. Note which milestone closes it.
  4. Check ownership. In a repo that holds several projects, ask whether each fix belongs to the slice or to src/shared/.

UI design & screens

Design language

  • Tone: commercial and trustworthy. Product imagery leads; typography is quiet; the primary CTA is the only saturated element on screen.
  • Skeletons, not spinners for anything that has a known shape. Spinners only for indeterminate actions like payment authorization.
  • Every price is formatted through one function using Intl.NumberFormat with the user's locale and the store's currency. Never string-concatenate a currency symbol.
  • Checkout is a linear, interruption-safe flow — the user can background the app at any step and come back to the same state.

Architecture

Three layers, each with one job. Routes (src/app/projects/store/) only compose screens and declare guards. The slice (src/projects/store/) holds everything else: API, auth, stores, hooks, components. Shared infra (src/shared/) is project-agnostic defaults used by more than one project. Dependencies point one way: routes import the slice, the slice imports shared, never the reverse and never a sibling project (ESLint enforces it).

Route groups

A flat list of routes (splash, login, main tabs, orders, place-order, product details) can't express "signed in" versus "signed out". The target shape groups routes by who may see them:

src/app/projects/store/
├── _layout.tsx              providers + Stack.Protected guards (project-level, not root)
├── onboarding.tsx           shown only until the per-device flag is set
├── (auth)/
│   ├── _layout.tsx          error boundary, initialRouteName "sign-in"
│   ├── sign-in.tsx
│   ├── sign-up.tsx
│   └── forgot.tsx
└── (app)/
    ├── _layout.tsx          intent replay, pending-checkout reconcile, inner guard
    ├── (tab)/{index,categories,search,bag,account}.tsx
    ├── product/[id].tsx
    ├── products/[categoryId].tsx
    ├── checkout/{address,shipping,payment,review}.tsx
    ├── order/[id].tsx
    ├── orders.tsx
    └── wishlist.tsx

There are two guard layers. The store layout guards the three top-level branches: onboarding while !onboarded, (app) while onboarded && (signedIn || guest), and (auth) while onboarded && !signedIn. The (app) layout adds a second Stack.Protected guard={signedIn} around checkout/*, order/[id] and orders, so guests can browse but not buy. (app) is declared before (auth) on purpose: a guest passes both guards, and the first available screen is where the bare store URL lands.

Every Stack.Screen name= must be re-derived, not guessed

Route names come from the file tree. Adding (auth) and (app) changes what every store route resolves to, and a stale name= doesn't fail the build and typed routes don't check it: the screen just gets a path-derived header title. After any move, grep name=" in the store layout and the (app) layout and check each hit against the tree. The root src/app/_layout.tsx declares only one Stack.Screen per project (projects/store); everything inside belongs to the store's own layouts.

What goes to src/shared/ and what doesn't

src/shared/api/axios.ts is shared and every project's endpoint files import it. Auth interceptors are not generic: the journal and podcast projects have no session concept. Keep the axios instance dumb and have the store install its own interceptors from its slice. Note what create() does: it merges defaults (timeout, headers) into a new instance but gives it its own interceptor chain. The genuinely generic new piece is env.ts (typed access to Constants.expoConfig.extra), which lives in src/shared/constants/ because every project reads its API URL the same way. The one QueryClient and its focusManager / onlineManager wiring live in src/shared/providers/QueryProvider.tsx, because those managers are process-global.

Components stay dumb

Components in components/ take plain data and callbacks. They never import a store, a session hook or a view model; routes (the "screens") own state through hooks and pass it down. This is what makes QuantityStepper, ProductGrid or TotalsView reusable and testable in isolation. The same rule applies to alerts and sheets' children.

Auth & token refresh

The state machine

SessionProvider is the only owner of session state and the only code that touches the keychain. Its status is one of loading, signedIn, guest, signedOut; a separate locked flag covers biometric re-entry.

          ┌──────────┐
          │ loading  │  (reading keychain + flags on boot)
          └────┬─────┘
 tokens+user?  │  no (guest flag? → guest)
     ┌─────────┴──────────────────┐
     ▼                            ▼
┌──────────┐   signOut()    ┌──────────┐ continueAsGuest() ┌───────┐
│  signed  │───────────────►│  signed  │──────────────────►│ guest │
│    in    │◄───────────────│   out    │                   │       │
└────┬─────┘  signIn/signUp └──────────┘                   └───┬───┘
              /social (also from guest) ◄────────────────┘
     │ 401 from any store request
     ▼
┌──────────────┐  new token   ┌──────────────────────┐
│  refreshing  │─────────────►│ replay request once  │
└──────┬───────┘              └──────────┬───────────┘
       │ refresh fails                   │ replay still 401
       ▼                                 ▼
  onAuthFailure() → signOut("expired") → clear tokens, caches, cart → status "signedOut"
  → Stack.Protected swaps (app) for (auth). No imperative navigation.

Refreshing isn't a status in React state; it's the pending promise inside the coordinator. Keeping it out of state means a refresh never re-renders the tree.

Single-flight refresh — the part everyone gets wrong

Five requests fire in parallel. All five get a 401. A naive interceptor performs five refreshes; with rotating refresh tokens, four of them present a token that was already rotated away (or invalidate the pair the fifth just stored), and the user is logged out for no reason.

refreshCoordinator.refresh():
  if (inFlight) return inFlight                   ← the whole trick
  inFlight = refreshFn().finally(() => inFlight = null)   ← finally, not then
  return inFlight

response interceptor on a rejected request (installed on storeApi + backendApi only):
  error → ApiError  (toApiError)
  if not "unauthorized", or config.skipAuthRefresh → rethrow
  if config._isRetry → onAuthFailure(); rethrow       ← replayed once already
  token = await coordinator.refresh()                ← concurrent 401s share this
  replay { ...config, _isRetry: true } with the new bearer

Two more details keep it correct. The refresh call itself goes through authBackendApi/authApi, which have no interceptors, and login/refresh pass skipAuthRefresh: true, so a failing refresh can never wait on itself. And the refresh function persists the rotated tokens before its promise resolves, so every queued request replays with the new token.

Verify it two ways. Automated: __tests__/refresh.test.ts drives six concurrent requests through a fake axios adapter and asserts one refresh and zero sign-outs. By hand: on the Account tab (non-production builds) turn on "Force 401 on first attempt" and tap "Fire 6 requests at once"; the result line reports how many refreshes hit the network.

If you later need synchronous storage (no hydration flash), react-native-mmkv is a drop-in adapter for Zustand persist. This project instead waits for hydration at boot (stores/hydration.ts), which is what you will meet in the cold-start section below.

Sign-out is a wipe, not a flag flip

signOut() runs once (a ref guards against concurrent auth failures), revokes the session and unregisters the push token best-effort with Promise.allSettled so a dead connection can't block it, then clears tokens and profile, removes user-scoped queries (orders, wishlist, user), empties the bag, resets the checkout machine, and only then sets status: "signedOut". By the time the UI re-renders there is nothing left to leak to the next person on the device. The product catalogue is deliberately kept: it is the same for every user.

Push & deep-link routing

Everything that enters the app from outside (a tapped push, a universal link, a custom-scheme URL) goes through the same three steps: validate it into a store href built from typed ids, buffer the href, and replay it once the session has resolved and the navigator is mounted.

REGISTRATION   (notifications/registerForPush.ts, only for a signed-in store session)

  getExpoPushTokenAsync({ projectId })      ← env.easProjectId from app.config extra

       └─ (app) layout: useIntentReplay waits for session != loading AND a navigation key,
            then pushes the href on the next animation frame

TEARDOWN
  sign-out: unregister the token on the backend, clear the badge
  foreground: clear the badge each time the app becomes active

Universal links and the namespaced router

Because the launcher owns the root, a link like https://<linkDomain>/p/42 would match nothing. src/app/+native-intent.tsx runs each project's pure rewriter before the router resolves the URL; the store's rewriteStoreSystemPath maps /p/<digits> to /projects/store/product/<id> and /order/<id> to the order screen, and returns null for foreign hosts and malformed ids. Custom-scheme links are already namespaced (whynotreactnative://projects/store/…). The AASA and assetlinks.json templates are in docs/well-known/; app.config.ts sets associatedDomains and Android intentFilters with autoVerify.

The intent buffer

Stack.Protected only blocks. A signed-out user who opens whynotreactnative://projects/store/order/7 is bounced to sign-in and the router forgets where they were going. The store layout captures the URL (Linking.useLinkingURL), and if it points behind the guard, parks it with setPendingIntent. Pushes, deep links and a guest tapping "Check out" all use the same buffer. A guest who needs an account (requiresAccount) is sent to sign-in with the intent kept, and the replay effect runs again when the status flips.

The cold-start race

On a cold start from a push, four things race: reading the token from the keychain, restoring persisted stores and the query cache, mounting the router, and handling the notification response. Get the order wrong and the user lands on the sign-in screen or Home instead of their order. The finished code resolves it in three moves. The tap listener starts from the root layout (a project layout hasn't loaded on a cold start, so a tap would be lost) but only buffers an href. The store layout keeps the native splash up (SplashScreen.preventAutoHideAsync) until the session resolves and the persisted state is restored, with a 1.5 s cap so disk I/O can't brick boot. And useIntentReplay replays only after useRootNavigationState()?.key exists and the status isn't loading. Build this deliberately: it's the single most valuable thing in this project.

Push is store-specific, not global

Register for push from the store's session lifecycle (usePushLifecycle(signedIn) in the store layout), not from src/app/_layout.tsx. A user who only ever opens Tic-Tac-Toe should never see a push permission prompt. The one exception is the response listener, which must start at the root so a cold-start tap isn't lost; it never requests permission. And because setNotificationHandler is process-global and last-writer-wins, the store's handler is deliberately neutral for payloads that aren't its own (banner and list, no sound, no badge), so another project's reminders still show in the foreground.

Build order

Each milestone ends with a checkpoint you can demonstrate and a verify step you can run. Don't move on until both pass. After every milestone run npm run typecheck, npm run lint and npx jest --no-watchman; after M1, M2 and M7 also run npx expo export --platform ios --output-dir /tmp/out, because the bundler catches route and import mistakes that tsc can't.

M5 Cart & checkout

Goal: an interruption-safe purchase flow.
  • Cart persistence plus a merge with the server cart on sign-in. Decide the rule and write it down; the finished one is union by product, max (not sum) quantity, unresolvable server lines dropped. Await persist.rehydrate() before merging.
  • A pure checkout state machine (steps address → shipping → payment → review, phases editing → awaiting_payment → completed), persisted, so the flow resumes after a force-quit.
  • Per-step validation and an address form with textContentType / autoComplete so OS autofill works.
  • Promo codes, shipping options and tax computed in integer cents (checkout/pricing.ts, utils/money.ts); the client only previews, the server prices.
  • Order placement with one idempotency key per checkout attempt, sent as an Idempotency-Key header: a double tap must not create two orders.
Checkpoint — Force-quit at the payment step and relaunch. The user resumes where they were, with the cart intact.

Verify — __tests__/cartMath.test.ts (including idempotence of the merge) and __tests__/checkout.test.ts (resume keeps the same key; locked after placement).

M6 Payments

Goal: money actually moves (in test mode).
  • Stripe payment sheet with a server-created PaymentIntent for an existing order; the client never says what to charge. Mount StripeProvider only when a publishable key exists.
  • Apple Pay / Google Pay through the payment sheet's applePay / googlePay options, and a returnURL for 3DS / bank redirects.
  • A clearly labelled simulated processor and a persisted on-device mock backend (api/mockServer.ts), so the whole flow, including idempotency and server-owned status, is exercisable without Stripe or a server.
  • Failure paths: declined card, network drop mid-confirm, app killed after charge but before your server callback. After any outcome, re-read the order from the server before declaring success.
  • On launch, reconcile a persisted awaiting_payment checkout against the server (useReconcilePendingCheckout).
  • Understand the store rules: physical goods, external payments are fine; digital content, in-app purchase is required.
Checkpoint — Kill the app immediately after confirming payment. On relaunch, the order state is correct; the server, not the client, is the source of truth.

Verify — In the dev menu set the simulated outcome to network_drop and place an order: the client reports a failure, yet the order ends up paid.

Backend options if you don't want to write one

FakeStoreAPI has no refresh endpoint, no persistent cart and no orders, so it can't take you past the catalogue and sign-in. The finished code bridges the gap two ways: a persisted on-device mock backend (api/mockServer.ts, used when EXPO_PUBLIC_STORE_BACKEND_URL is empty) that implements idempotency keys and server-owned order status, and a typed contract (auth/login, auth/refresh, orders, payments/intents, push registration) that a real server can satisfy. For a real one: Supabase (auth + Postgres + realtime), Medusa or Saleor (commerce), or a small Hono/Express service on a free host.

Route structure rules

These rules shape the store's route tree behind its guards. Each one prevents a specific bug.

  1. Group routes by who may see them. (auth) holds sign-in, sign-up and forgot-password; (app) holds everything else. A screen is <folder>/index.tsx or a named file, and parameter names follow the file name (product/[id] is read with useLocalSearchParams<{ id: string }>()).
  2. The guards live one level down. The store layout (not the root) owns Stack.Protected, so the root only knows "there is a project called store". Each group has its own _layout.tsx with its own ErrorBoundary and unstable_settings.initialRouteName.
  3. URLs lose group segments. (app)/(tab)/bag is /projects/store/bag. Every hardcoded href, notification payload mapping and link rewriter must target the namespaced URL.
  4. Declaration order matters. The bare URL lands on the first available group, so (app) goes before (auth) and a guest can reach both.
  5. Session state stays out of screens. No splash timer and no per-screen redirects: SessionProvider plus guards decide what is reachable. Signing out changes state; it never calls router.replace.
  6. Shared code stays project-agnostic. Anything the store needs that the journal can't use (interceptors, session) stays in the slice and is installed from there. Only genuinely cross-project pieces (typed env, the single QueryClient and its managers) live in src/shared/.
  7. Prefix before you share. One QueryClient serves every project, so every key is rooted at "store" before persistence or defaults are added. Otherwise they leak onto other projects.
  8. Verify mechanically. After any change to the route tree, run typecheck, lint, tests and npx expo export for both platforms, and check that every Stack.Screen name= matches a file.

Why a game, at the end of the path

Projects 01 to 05 spend most of their effort on the platform: databases, cameras, payments, background tasks and release pipelines. Tic-tac-toe has none of that, so the interesting parts are the ones every app has: where the rules live, what state is stored and what is derived, how a timer is cleaned up, how an animation stays on the UI thread, and how a screen reader hears the board. It is small enough to read in one sitting and strict enough to be worth reading.

SDK 58 migration: Timeline refs use ScrollViewInstance under React Native’s strict TypeScript API. The game header explicitly remains opaque.

1 · What you'll build

One screen, reachable from the launcher as Tic-Tac-Toe. From top to bottom:

  • Mode button (header, top right): an icon that toggles between 2 players (both on one device, two people) and vs CPU (a computer). Against the computer you are always X and you always move first; the CPU is O.
  • Difficulty button (header, vs CPU only): signal-strength bars that cycle Easy → Medium → Hard with each tap. Easy plays at random, Medium wins if it can and otherwise blocks, Hard runs minimax and never loses.
  • Scoreboard: X wins, draws and O wins, kept separately for each mode (a two-player win isn't a win against the CPU) and persisted across launches. The tile of the player to move is highlighted, and a count bumps when it changes. Reset scores clears the current mode's tally only, and asks before it does (on native).
  • Status banner: "Your turn", "Computer is thinking…" (with bouncing dots), "X wins!", "It's a draw". Screen readers announce each change.
  • Board: X and O are SVG strokes that draw themselves on; the winning line draws across the three cells and the losing marks fade back.
  • Action bar: Undo, New round (which pulses as Play again once there is a result) and a haptics toggle (hidden on web).
  • Move timeline: one chip per move ("3 · X B2"). Tap a chip to travel back to it; play from there and the old future is thrown away.

Undo and the timeline lock once the round has a result, so a counted win can never be rewound and replayed. The whole game (board, history, mode, difficulty, both score tallies and the haptics setting) survives an app restart. The board takes the height that is left between the controls, so a whole round fits on one screen and the timeline stays clear of the home indicator.

Learning objectives

  • Split a feature into pure rules, one store, a couple of hooks and dumb components, and say why each piece lives where it does.
  • Type a Zustand store by inference with combine, persist only its data with persist + partialize, change the stored shape safely with version + migrate, and know when it has hydrated.
  • Store the minimum (history and currentMove) and derive everything else during render.
  • Write a minimax search that is provably unbeatable, and an injectable source of randomness that makes it testable.
  • Drive SVG and view animations with Reanimated 4 shared values, animated props and layout animations, and switch all of it off for Reduce Motion.
  • Give a game board real accessibility: labels, roles, states and a live region.
  • Size a view from the space a flex layout leaves for it (onLayout plus an absolute overlay), and keep content clear of the home indicator with safe-area insets.

The route stays thin

Anything under src/app/ is a reachable route, so the route file holds the screen and nothing else. It subscribes to each piece of store state with its own selector, runs the two hooks, and derives the rest:

  // below it, so a whole round fits on one screen. Only when that is too small

  const boardSize = Math.max(MIN_BOARD, Math.min(columnWidth, boardArea));

  const cpuTurn = mode === "cpu" && (thinking || view.next === CPU);

Notice what is not here: no game logic, no effect, and no game state in useState. The one useState, boardArea, holds a measured height, a layout fact rather than game data (see Sizing the board below). view is recomputed on every render from history and currentMove; that is cheap for nine squares and it means there is nothing to keep in sync. The board is disabled for three reasons, each derived: the saved game hasn't loaded, the round is over, or it is the computer's move.

Dumb components

Every file in components/ takes plain data and callbacks. None of them imports the store or a hook from the slice. Board receives squares, win, disabled and onPress; it doesn't know whether it is a two-player game, or that a computer exists:

Sizing the board from the space that's left

The first version sized the board from the window width alone, Math.min(width - 32, 380), so a 380-point board plus the controls was taller than many screens and a round didn't fit. The next attempt took the window height minus a fixed guess for the controls. That guess is wrong as soon as anything changes: the header, the insets, the phone and the orientation (and, at the time, whether the difficulty row was showing). When it was too small, the content ended up a little taller than the screen, and at rest the last row, the move timeline, sat under the home indicator. A bottom padding of insets.bottom didn't help, because padding on a scroll view's content is at the end of the scroll: you only see it once you have scrolled down, not at rest.

So the screen measures it. The scroll content and the column grow to fill the screen (flexGrow: 1), and between the banner and the action bar sits a boardArea view that also grows. Its onLayout reports the height it ended up with:

src/app/projects/tic-tac-toe/index.tsxtsx
const insets = useSafeAreaInsets();

// below it, so a whole round fits on one screen. Only when that is too small
// (a short phone, landscape) does it keep MIN_BOARD and let the page scroll.
const [boardArea, setBoardArea] = useState(0);
const boardSize = Math.max(MIN_BOARD, Math.min(columnWidth, boardArea));

  • The size is a clamp. Math.min(columnWidth, boardArea) is as big as both the width and the free height allow; Math.max(MIN_BOARD, …) keeps it playable. Only when even 240 points don't fit (a short phone, landscape) does the area keep its minHeight and the page scroll.
  • Measured first. boardArea starts at 0 and the board renders only once it is positive, so it never flashes at a wrong size. Calling setBoardArea from onLayout is an event handler, not a setState in an effect body.
  • The board is an overlay. boardOverlay is StyleSheet.absoluteFill, and an absolutely positioned child takes no part in its parent's flex sizing. If the board were a normal child, its own height would become the area's minimum: the next onLayout would report the board's size back, and the area could grow but never shrink again (after a rotation back to portrait, say). As an overlay, the area's height comes from the free space alone. pointerEvents: "box-none" lets touches through to the squares, and the card itself has alignSelf: "center".
  • The safe area. The scroll view draws edge to edge, so the content container adds paddingBottom: insets.bottom + 16 from useSafeAreaInsets(): the inset itself, plus breathing room above it. That padding now works at rest because the content is exactly as tall as the screen: the padding takes its share of the height first and the board area gets what is left, instead of the padding hanging below the fold.

The column's gap is 12 points, and the column keeps its width at columnWidth so the controls line up with the widest the board can be.

Mode and difficulty as header icon buttons

A tap moves to the next value instead of opening a picker. Which value is next is a rule, so it lives with the other rules, as pure functions over the same Mode and Difficulty types:

src/projects/tic-tac-toe/utils/game.tsts
const MODES: readonly Mode[] = ["pvp", "cpu"];
const DIFFICULTIES: readonly Difficulty[] = ["easy", "medium", "hard"];

/** The header's mode button toggles: two players ↔ vs computer. */
export function nextMode(mode: Mode): Mode {
  return MODES[(MODES.indexOf(mode) + 1) % MODES.length];
}

/** The header's difficulty button cycles easy → medium → hard → easy. */
export function nextDifficulty(difficulty: Difficulty): Difficulty {
  return DIFFICULTIES[
    (DIFFICULTIES.indexOf(difficulty) + 1) % DIFFICULTIES.length
  ];
}

/** 1–3, for the difficulty bars. */
export function difficultyLevel(difficulty: Difficulty): 1 | 2 | 3 {
  return difficulty === "easy" ? 1 : difficulty === "medium" ? 2 : 3;
}

Wrapping with % length makes the last value go back to the first, and game.test.ts pins the whole cycle ("nextMode and nextDifficulty"). HeaderIconButton is just as dumb: an icon as children, an onPress, labels, and a popKey. It doesn't know what it cycles through; it only knows when the value changed, and acknowledges it with a quick pop (squash to 0.6, spring back):

src/projects/tic-tac-toe/components/HeaderIconButton.tsxtsx
const scale = useSharedValue(1);
const press = useSharedValue(1);
const previousKeyRef = useRef(popKey);

useEffect(() => {
  if (previousKeyRef.current === popKey) return;
  previousKeyRef.current = popKey;
  if (reduceMotion) return;
  scale.set(
    withSequence(
      withTiming(0.6, { duration: 90 }),
      withSpring(1, { damping: 9, stiffness: 260 }),
    ),
  );
}, [popKey, reduceMotion, scale]);

const iconStyle = useAnimatedStyle(() => ({
  transform: [{ scale: scale.get() * press.get() }],
}));
  • React to the value, not the tap. The pop runs when popKey changes, so it also plays when the value changes some other way, and the button never has to know whether its tap succeeded.
  • A ref skips the mount. previousKeyRef starts at the first popKey, so the effect returns early on the first render and the icons don't pop every time you open the screen. It is updated before the reduceMotion check, so turning Reduce Motion off later doesn't replay a stale change. This is the same pattern as the score tiles' bump and the haptics hook.
  • Two shared values, one transform. The pop (scale) and the press spring (press, 0.85 while held) are multiplied, like Square's press and win pulse, so they never fight over one property.

Changing either setting still goes through setMode / setDifficulty, which start a fresh round; the accessibility hint says so (see §9).

Why the rules live in the store

The store doesn't trust the UI. play(index) works out for itself whether the square is empty and the round is still running; undo and jumpTo refuse once there is a result. The screen does disable the board too, but only as a courtesy. The consequence is that a double tap, a stale timer, a test that calls play directly, or a future UI you haven't written yet can't put the game in an illegal state. The rule is enforced in one place, and that place is covered by gameStore.test.ts.

3 · Pure game rules

utils/game.ts imports nothing. It is plain TypeScript over a nine-element array, which makes it the easiest file in the slice to test and the one everything else builds on.

Types

src/projects/tic-tac-toe/utils/game.tsts
export type Player = "X" | "O";
export type SquareValue = Player | null;
export type Squares = SquareValue[];
export type Mode = "pvp" | "cpu";
export type Difficulty = "easy" | "medium" | "hard";
export type Line = readonly [number, number, number];

export type WinningLine = { winner: Player; line: Line };

/** Everything the screen needs about the board at `currentMove`. */
export type GameView = {
  squares: Squares;
  /** Whose turn it is (meaningless once `isOver`). */
  next: Player;
  win: WinningLine | null;
  isDraw: boolean;
  isOver: boolean;
};

/** In vs-computer mode the human always plays X and moves first. */
export const HUMAN: Player = "X";
export const CPU: Player = "O";

The board is SquareValue[], indexed 0 to 8 left to right, top to bottom. Line is a readonly tuple, so a winning line can't be mutated by accident and always has exactly three cells. Mode and Difficulty live here, not in the store, because statusText and canJumpTo need them and the rules must not import the store.

Finding a winner

src/projects/tic-tac-toe/utils/game.tsts
export const LINES: readonly Line[] = [
  [0, 1, 2],
  [3, 4, 5],
  [6, 7, 8],
  [0, 3, 6],
  [1, 4, 7],
  [2, 5, 8],
  [0, 4, 8],
  [2, 4, 6],
];

export function emptyBoard(): Squares {
  return Array<SquareValue>(9).fill(null);
}

export function opponent(player: Player): Player {
  return player === "X" ? "O" : "X";
}
src/projects/tic-tac-toe/utils/game.tsts
/** The first completed line, with who completed it, or null. */
export function findWinningLine(squares: Squares): WinningLine | null {
  for (const line of LINES) {
    const [a, b, c] = line;
    const mark = squares[a];
    if (mark && mark === squares[b] && mark === squares[c]) {
      return { winner: mark, line };
    }
  }
  return null;
}

/** Turns left to play, which is the number of empty squares. */
export function countRemainingTurns(squares: Squares): number {
  return squares.filter((square) => !square).length;
}

findWinningLine returns the line as well as the winner. The UI needs both: the winner for the banner and the score, the line for the WinLine overlay and for highlighting three squares. emptyBoard spells out Array<SquareValue>(9); a bare Array(9).fill(null) is typed any[] and would turn off checking for every board in the app.

Derived state: GameView

The store keeps only history (one board per move, starting with the empty board) and currentMove (an index into it). Everything else is a function of those two:

src/projects/tic-tac-toe/utils/game.tsts
/** X plays the even moves (0, 2, 4…), O the odd ones. */
export function nextPlayer(moveIndex: number): Player {
  return moveIndex % 2 === 0 ? "X" : "O";
}

export function deriveGame(history: Squares[], currentMove: number): GameView {
  const squares = history[currentMove] ?? emptyBoard();
  const win = findWinningLine(squares);
  const isDraw = !win && countRemainingTurns(squares) === 0;
  return {
    squares,
    next: nextPlayer(currentMove),
    win,
    isDraw,
    isOver: win !== null || isDraw,
  };
}

Whose turn it is falls out of the move number: X plays moves 0, 2, 4…, O the odd ones. There is no xIsNext boolean to forget to flip. A win is checked before a draw, so filling the ninth square with a winning move is a win, not a draw; game.test.ts has a case for exactly that board.

Text, labels and time travel

src/projects/tic-tac-toe/utils/game.tsts
/**
 * Time travel may land on any move between two players. Against the computer
 * only on the human's turns: landing on the CPU's turn would make it reply at
 * once and throw the rest of the timeline away.
 */
export function canJumpTo(move: number, mode: Mode): boolean {
  return mode === "pvp" || nextPlayer(move) === HUMAN;
}

/** Banner text. A win takes priority, even on the ninth square. */
export function statusText(view: GameView, mode: Mode): string {
  if (view.win) {
    if (mode === "cpu")
      return view.win.winner === HUMAN ? "You win!" : "Computer wins";
    return `${view.win.winner} wins!`;
  }

Types by inference

combine(initialState, actions) merges a state object with the object your creator returns, and infers the store type from both. You never write a GameState interface. play: one move, one set

  const result = deriveGame(nextHistory, nextHistory.length - 1);

  // a finished round can't be played, undone or rewound.

    nextTally = { ...tally, [winner]: tally[winner] + 1 };
  } else if (result.isDraw) {
    nextTally = { ...tally, draw: tally.draw + 1 };
  }
  const nextScores = { ...scores, [mode]: nextTally };

  set({
    history: nextHistory,
    currentMove: nextHistory.length - 1,
    scores: nextScores,
  });

Three things to read closely:

  • The guard. A finished round or a filled square is a no-op. This is why the board's disabled prop is only a courtesy.
  • Truncation. history.slice(0, currentMove + 1) keeps the past up to the current move and drops the rest. After a jump back, playing writes a new future.
  • Scoring in the same set. The result is computed from the board the move produces, and the current mode's tally, scores[mode], is updated in the same set as the move. Zustand's merge is shallow, so both levels are copied by hand: { ...tally, … } keeps the other two counts and { ...scores, [mode]: nextTally } keeps the other mode. There is no effect watching for "a win just happened", so there is no render in which the board shows a win and the score doesn't, and nothing that could count it twice. It can't be counted again later either: once isOver is true, play, undo and jumpTo all return early, so you can't step back into the round and win it again.

Scores per mode, and a versioned migration

The first version kept one shared tally. That mixed two different games: a two-player win by X showed up as "You" beating the CPU, and resetting one mode's score wiped the other's. So scores became Record<Mode, Scores>. That is a change to the stored shape, and every phone that already had a save would hydrate a flat { X, O, draw } object into a store that now reads scores[mode]: undefined, and a crash as soon as Scoreboard reads scores.X.

persist handles this with two options. version is saved next to the state. On hydration, when the stored version differs from the current one, the saved state goes through migrate(persistedState, storedVersion) first, and what it returns is merged. (With a different version and no migrate, Zustand logs an error and ignores the save, so the player loses it.)

src/projects/tic-tac-toe/stores/gameStore.tsts
/**
 * Upgrades a saved game to the current `version`. Version 1 kept one shared
 * tally; it can't be split by mode, so it moves to the mode that was active.
 */
export function migrateGame(persisted: unknown, version: number) {
  const state = (persisted ?? {}) as Record<string, unknown>;
  if (version < 2) {
    const mode: Mode = state.mode === "pvp" ? "pvp" : "cpu";
    const old = (state.scores as Scores | undefined) ?? noScores();
    const scores: ScoresByMode = { pvp: noScores(), cpu: noScores() };
    scores[mode] = old;
    return { ...state, scores };
  }
  return state;
}
  • Upgrade, don't guess. A shared tally can't be split after the fact, so it moves to the mode that was active when it was saved, and the other mode starts at zero.
  • Steps by version. if (version < 2) rather than === 1: when a version 3 comes, it adds its own if (version < 3) block below, and a version-1 save runs through both in order.
  • Treat the input as unknown. A save is old data from disk, so migrateGame takes unknown, reads fields defensively and falls back to noScores().
  • Exported and pure. It needs no store and no storage, so the test calls it directly with a version-1 object (see §10).

AsyncStorage is asynchronous, so the first render runs with initialState, and the saved game arrives a moment later. A tap in that window would be played on the default empty board, then overwritten by the saved one. The store exposes whether hydration has finished:

5 · The computer opponent

utils/ai.ts is pure too. Its one public entry point takes the board, which mark the computer plays, the difficulty, and a random-number source:

src/projects/tic-tac-toe/utils/ai.tsts
/**
 * The computer's move for `cpu`, or -1 when the board is full or already won.
 *
 * - easy: any empty square.
 * - medium: win if it can, else block the opponent's win, else any square.
 * - hard: minimax, unbeatable. Equally good moves are picked with `random`.
 *
 * `random` is injectable so tests can make the choice deterministic.
 */
export function pickMove(
  squares: Squares,
  cpu: Player,
  difficulty: Difficulty,
  random: () => number = Math.random,
): number {
  if (findWinningLine(squares)) return -1;
  const empty = emptySquares(squares);
  if (empty.length === 0) return -1;

  if (difficulty === "easy") return pickRandom(empty, random);

  if (difficulty === "medium") {
    const win = findImmediateWin(squares, cpu);
    if (win !== -1) return win;
    const block = findImmediateWin(squares, opponent(cpu));
    if (block !== -1) return block;
    return pickRandom(empty, random);
  }

  return pickRandom(bestMoves(squares, cpu), random);
}

Medium: one move ahead

/** The square that completes a line for `player` right now, or -1. */
export function findImmediateWin(squares: Squares, player: Player): number {
  for (const line of LINES) {
    const marks = line.map((i) => squares[i]);
    const own = marks.filter((mark) => mark === player).length;
    const gap = line.find((i) => !squares[i]);
    if (own === 2 && gap !== undefined) return gap;
  }
  return -1;
}

/** One item from `items`, picked with `random` (a number in [0, 1)). */
function pickRandom(items: number[], random: () => number): number {
  if (items.length === 0) return -1;
  const index = Math.min(items.length - 1, Math.floor(random() * items.length));
  return items[index];
}

findImmediateWin looks for a line with two of the player's marks and an empty third cell. Medium calls it for itself first (take the win) and then for the opponent (block). pickRandom clamps the index, so a random that returns something just under 1 still picks the last item.

Hard: minimax with depth

src/projects/tic-tac-toe/utils/ai.tsts
/**
 * Minimax score of `squares` from `cpu`'s point of view, with `turn` to move.
 * A win scores 10 - depth and a loss depth - 10, so faster wins and slower
 * losses rank higher. A draw scores 0.
 */
function score(
  squares: Squares,
  cpu: Player,
  turn: Player,
  depth: number,
): number {
  const win = findWinningLine(squares);
  if (win) return win.winner === cpu ? 10 - depth : depth - 10;
  if (countRemainingTurns(squares) === 0) return 0;

  let best = turn === cpu ? -Infinity : Infinity;
  for (const index of emptySquares(squares)) {
    squares[index] = turn;
    const value = score(squares, cpu, opponent(turn), depth + 1);
    squares[index] = null;
    best = turn === cpu ? Math.max(best, value) : Math.min(best, value);
  }
  return best;
}

/** Every move with the best minimax score for `cpu`. */
function bestMoves(squares: Squares, cpu: Player): number[] {
  const board = squares.slice();
  let best = -Infinity;
  let moves: number[] = [];
  for (const index of emptySquares(board)) {
    board[index] = cpu;
    const value = score(board, cpu, opponent(cpu), 1);
    board[index] = null;
    if (value > best) {
      best = value;
      moves = [index];
    } else if (value === best) {
      moves.push(index);
    }
  }
  return moves;
}

Minimax plays every remaining game out to the end. On the computer's turns it takes the move with the highest score, on the opponent's turns the lowest, on the assumption that the opponent plays perfectly. A finished game scores 10 - depth for a computer win, depth - 10 for a loss and 0 for a draw. The depth matters: without it, a win now and a win in three moves score the same, and the computer may dawdle past a winning move; with it, the faster win ranks higher, and when a loss can't be avoided it delays it as long as possible.

Tic-tac-toe has only 255,168 possible games, so the search needs no pruning or caching: the computer's first reply, with eight squares left, is the slowest and still well inside the 450 ms "thinking" delay. The search mutates one scratch board and undoes each move (squares[index] = null) instead of copying a board per node; bestMoves takes a copy first, so the caller's board is never touched.

Why it's unbeatable, and why it's still not boring

Perfect play from both sides in tic-tac-toe is a draw, and minimax is perfect play: it never picks a move that lets the opponent force a win, because that move would score below a drawing move. bestMoves keeps every move with the best score, not only the first, and pickRandom chooses between them. So Hard doesn't answer the same way every round; it picks among equally good moves at random. That randomness is injected (random: () => number = Math.random), which is how the tests replay the exact same choices.

Taking a turn: useCpuTurn

src/projects/tic-tac-toe/hooks/useCpuTurn.tsts
/** How long the computer "thinks" before it plays, in milliseconds. */
export const CPU_DELAY_MS = 450;

/**
 * Plays the computer's move after `CPU_DELAY_MS` whenever it is the CPU's turn.
 * The timer is cleared when the board, mode or difficulty changes, or on
 * unmount, so an undo or a new round never gets a stale move.
 *
 * Returns `thinking`, derived during render rather than kept in state.
 */
export function useCpuTurn(
  view: GameView,
  mode: Mode,
  difficulty: Difficulty,
  play: (index: number) => void,
): boolean {
  const { squares, next, isOver } = view;
  const thinking = mode === "cpu" && !isOver && next === CPU;

  useEffect(() => {
    if (mode !== "cpu" || isOver || next !== CPU) return;
    const timer = setTimeout(() => {
      const index = pickMove(squares, CPU, difficulty);
      if (index !== -1) play(index);
    }, CPU_DELAY_MS);
    return () => clearTimeout(timer);
  }, [squares, next, isOver, mode, difficulty, play]);

  return thinking;
}
  • The delay is for people. An instant reply feels like the board glitched. 450 ms is long enough to see your own mark land and the dots appear.
  • Cleanup is the whole design. Every dependency change clears the pending timer. Undo during the delay changes squares; a new round or a mode or difficulty switch changes squares, mode or difficulty; leaving the screen unmounts it. In each case the stale move is cancelled instead of being played onto a board it wasn't chosen for.
  • The move is chosen when the timer fires, from the squares the effect closed over, and handed to the store's play, which re-checks legality anyway.
  • thinking is derived, not stored. It is true exactly when the effect would schedule a move, so it is computed during render from the same three values. Keeping it in useState and setting it inside the effect would cost an extra render, could disagree with the board for a frame, and is the "setState in an effect body" pattern the React Compiler rules ask you to avoid.

Loops: the pulse and the dots

Looping animations need to be stopped. The Play again button pulses with withRepeat(withSequence(…), -1) while the round is over and cancels the loop when it isn't, or when the component unmounts:

  if (!roundOver || reduceMotion) {
    cancelAnimation(pulse);
    pulse.set(1);
    return;
  }
  pulse.set(
    withRepeat(
      withSequence(
        withTiming(1.05, { duration: 650 }),
        withTiming(1, { duration: 650 }),
      ),
      -1,
    ),
  );
  return () => cancelAnimation(pulse);
}, [roundOver, reduceMotion, pulse]);

}));

The three thinking dots in StatusBanner use the same loop, each started with withDelay(i * 120, …) so they bounce in a wave. Score tiles bump when their count changes (a quick withTiming up to 1.35, then withSpring back to 1, in a withSequence), and fade their border between the palette's border colour and the player's colour with interpolateColor.

Reduce Motion, threaded down as a prop

The screen calls useReducedMotion() once and passes the boolean to every component. Each one then picks the end state instead of an animation: shared values start at their final value, effects set the target directly, and layout animations are undefined. Nothing is lost: the marks still appear, the winning line is still drawn and the banner still changes; they just don't move. Passing it as a prop, rather than calling the hook in every component, keeps the components dumb and lets a test render either variant.

Checkpoint — Turn on Reduce Motion (iOS: Settings → Accessibility → Motion; Android: Remove animations) and play a round. Everything appears in its final state, and nothing is missing.

The launcher uses the app-wide theme. Tic-tac-toe has its own warm palette, a full set of colours for light and dark, chosen by a hook:

useColorScheme is the shared wrapper in src/shared/hooks/, which already narrows React Native's value (which can also be "unspecified") to "light" | "dark"; the comparison colorScheme === "dark" ? dark : light keeps the palette lookup safe either way. The screen reads the palette once and passes it down, so every colour in every component comes from one object, and a component never decides its own colours. There is no separate win-line colour: Board passes palette.x or palette.o.

The header is part of the screen too. A single-screen project doesn't own a layout, and Expo Router has no route-level options export, so the screen renders an inline Stack.Screen (listed in §2) that themes the header from the same palette (headerStyle, headerTintColor) and drops its bottom shadow (headerShadowVisible: false), so header and page read as one surface. The header icons take their colours from the palette too: palette.text for the mode icon, palette.o and palette.grid for the bars.

Never theme one project with Appearance.setColorScheme

It is process-wide: forcing a scheme for one project forces it for the launcher and every other project, and resetting it to "unspecified" leaves a stale scheme behind. A palette (or, for projects that use React Navigation's theme, their own ThemeProvider, like the journal's useJournalScheme) keeps the change local.

8 · Haptics

src/projects/tic-tac-toe/hooks/useGameHaptics.tsts
/** Haptics may be unavailable (simulator, low power): never let it throw. */
function fire(promise: Promise<void>) {
  promise.catch(() => {});
}

/**
 * Buzzes when the move count changes. One step forward is a move (a light tap,
 * success on a win, warning on a draw); anything else (undo, a timeline jump,
 * a new round, rehydration) is a selection tick. The first render is skipped
 * because the ref starts at the current count.
 */
export function useGameHaptics(
  enabled: boolean,
  moveCount: number,
  view: GameView,
): void {
  const previousRef = useRef(moveCount);
  const won = view.win !== null;
  const { isDraw } = view;

  useEffect(() => {
    const previous = previousRef.current;
    if (previous === moveCount) return;
    previousRef.current = moveCount;
    if (!enabled || Platform.OS === "web") return;

    if (moveCount - previous !== 1) {
      fire(Haptics.selectionAsync());
    } else if (won) {
      fire(Haptics.notificationAsync(Haptics.NotificationFeedbackType.Success));
    } else if (isDraw) {
      fire(Haptics.notificationAsync(Haptics.NotificationFeedbackType.Warning));
    } else {
      fire(Haptics.impactAsync(Haptics.ImpactFeedbackStyle.Light));
    }
  }, [enabled, moveCount, won, isDraw]);
}
  • One signal, the move count. A step of exactly +1 is a move, and the result of that move picks the feedback: Success on a win, Warning on a draw, a light impact otherwise. Any other change (undo, a timeline jump, a new round, a restore) gets a selection tick. The hook doesn't need to know which button was pressed.
  • The ref starts at the current count, so the first render doesn't buzz. The ref is updated even while haptics are off, so turning them back on (or finishing hydration) doesn't replay a stale difference.
  • Web is a no-op. expo-haptics has nothing to drive in a browser, so the hook returns early, and the screen hides the toggle there (onToggleHaptics is undefined on web).
  • Rejections are swallowed. The haptics calls return promises, and a device can refuse (a simulator, Low Power Mode on iOS). Feedback is decoration, so fire catches the rejection instead of surfacing an unhandled one.

The setting itself is part of the persisted store (hapticsEnabled), toggled by the switch in ActionBar.

And Reset scores asks for confirmation with an Alert on native, because it is the one destructive action on the screen; the message names the tally it clears ("This clears the vs CPU wins and draws."), since the other mode's survives. Disabled controls (an empty scoreboard's reset, locked or future timeline chips) are dimmed to 0.6 and 0.65 opacity, faint enough to read as unavailable but still legible. The exhaustive "never loses" test

src/projects/tic-tac-toe/__tests__/ai.test.tsts
/**
 * Plays every possible opponent line against hard and returns how many
 * finished games the opponent won. `hard` uses the seeded tie-break.
 */
function opponentWins(
  squares: Squares,
  turn: Player,
  cpu: Player,
  random: () => number,
): number {
  const win = findWinningLine(squares);
  if (win) return win.winner === cpu ? 0 : 1;
  const empty = emptySquares(squares);
  if (empty.length === 0) return 0;

  if (turn === cpu) {
    const move = pickMove(squares, cpu, "hard", random);
    expect(squares[move]).toBeNull();
    const nextSquares = squares.slice();
    nextSquares[move] = cpu;
    return opponentWins(nextSquares, opponent(turn), cpu, random);
  }

  let wins = 0;
  for (const index of empty) {
    const nextSquares = squares.slice();
    nextSquares[index] = turn;
    wins += opponentWins(nextSquares, opponent(turn), cpu, random);
  }
  return wins;
}

it.each([
  ["as O, opponent first", "O" as Player],
  ["as X, moving first", "X" as Player],
])("hard never loses %s", (_label, cpu) => {
  for (const random of [() => 0, () => 0.5, () => 0.99]) {
    expect(opponentWins(emptyBoard(), "X", cpu, random)).toBe(0);
  }
});

When it is the opponent's turn the helper branches into every empty square; when it is the computer's turn it asks pickMove for its one move. So it plays every game a human could possibly play against Hard, as O (the human opens) and as X (the computer opens), and counts the ones the human won. The answer must be zero. It runs with three fixed random sources, so the tie-breaks take the first, middle and last of the equally good moves. That is a proof, not a sample: there is no line of play the test didn't try.

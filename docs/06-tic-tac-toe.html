Building a game

You will build a small tic-tac-toe game during this tutorial, in TypeScript, running on React Native. It assumes existing React knowledge. The techniques here are fundamental to building any React app, and fully understanding it will give you a deep understanding of React and Zustand.

About this page

This is the official Zustand Tutorial: Tic-Tac-Toe with two ports applied on top of it: every JavaScript snippet converted to TypeScript, and every DOM element converted to a React Native component. Prose is from the original tutorial (which itself draws inspiration from React's tic-tac-toe tutorial); the code, the typing notes and the React Native notes are the port. Files are .tsx wherever JSX appears, .ts otherwise.

Snippets are labelled App.tsx to match the upstream tutorial. In this repo the finished screen lives at src/app/projects/tic-tac-toe/index.tsx — an Expo Router route, so the default export is the screen.

If you want the original DOM version — or you pasted the upstream code into an Expo app and hit a render error — jump to the appendix.

Why the upstream snippets cannot be pasted into React Native

The Zustand tutorial builds its board out of <button> and <div>. React Native has no DOM: a lowercase JSX tag is looked up as a native host component, and there is nothing registered under the name button, so the renderer throws View config getter callback for component "button" must be a function (received undefined). The fix is not a shim — it is using the platform's own primitives, which is what every snippet below does. The appendix explains the error in full.

The tutorial is divided into several sections:

  • Setup — the types you will use everywhere.
  • Overview — the fundamentals of React: components, props, and state.
  • Completing the game — the most common techniques in React development.
  • Adding time travel — a deeper insight into the unique strengths of React.

Learning objectives

By the end you will be able to:

  • Build a typed Zustand store with the combine middleware and read it with selector hooks.
  • Lift state up, keep Square and Board dumb, and derive values (xIsNext, the current board) instead of storing them.
  • Model time travel with immutable updates: one new board per move, currentMove as an index, and a truncated future after a rewind.
  • Translate DOM elements and CSS into React Native primitives and flexbox.
  • Move pure logic out of a route file into utils/game.ts and cover it with Jest tests.
  • Add screen-reader labels, roles and states, and register a single-route project in the launcher.

Prerequisites: basic React (components, props, useState) and TypeScript. The repo's npm run typecheck, npm run lint and npx jest --no-watchman commands are your checkpoints. Build in a scratch route first (src/app/projects/tic-tac-toe/index.tsx is the finished one), and compare against it at the end.

How the build is staged

Stages 1 to 7 follow the upstream tutorial in a single file (App.tsx in the snippets). Stage 8 (extract and test) and stage 9 (accessibility) are what turn that file into the version in this repo. Each stage ends with a Checkpoint telling you what you should see before moving on.

What are you building?

In this tutorial, you'll build an interactive tic-tac-toe game with React Native, Zustand and TypeScript. You can see what it will look like when you're finished here:

App.tsxtsx
import { Platform, Pressable, StyleSheet, Text, View } from 'react-native'
import { create } from 'zustand'
import { combine } from 'zustand/middleware'

type Player = 'X' | 'O'
type SquareValue = Player | null
type Squares = SquareValue[]
type Updater<T> = T | ((prev: T) => T)

const useGameStore = create(
  combine(
    {
      history: [Array<SquareValue>(9).fill(null)],
      currentMove: 0,
    },
    (set) => {
      return {
        setHistory: (nextHistory: Updater<Squares[]>) => {
          set((state) => ({
            history:
              typeof nextHistory === 'function'
                ? nextHistory(state.history)
                : nextHistory,
          }))
        },
        setCurrentMove: (nextCurrentMove: Updater<number>) => {
          set((state) => ({
            currentMove:
              typeof nextCurrentMove === 'function'
                ? nextCurrentMove(state.currentMove)
                : nextCurrentMove,
          }))
        },
      }
    },
  ),
)

type SquareProps = {
  value: SquareValue
  onSquareClick: () => void
}

function Square({ value, onSquareClick }: SquareProps) {
  return (
    <Pressable style={styles.square} onPress={onSquareClick}>
      <Text style={styles.squareText}>{value}</Text>
    </Pressable>
  )
}

type BoardProps = {
  xIsNext: boolean
  squares: Squares
  onPlay: (nextSquares: Squares) => void
}

function Board({ xIsNext, squares, onPlay }: BoardProps) {
  const winner = calculateWinner(squares)
  const remainingTurns = countRemainingTurns(squares)
  const player = xIsNext ? 'X' : 'O'
  const status = calculateStatus(winner, remainingTurns, player)

  function handleClick(i: number) {
    if (squares[i] || winner) return
    const nextSquares = squares.slice()
    nextSquares[i] = player
    onPlay(nextSquares)
  }

  return (
    <View>
      <Text style={styles.status}>{status}</Text>
      <View style={styles.board}>
        {squares.map((square, squareIndex) => (
          <Square
            key={`square-${squareIndex}`}
            value={square}
            onSquareClick={() => handleClick(squareIndex)}
          />
        ))}
      </View>
    </View>
  )
}

export default function Game() {
  const history = useGameStore((state) => state.history)
  const setHistory = useGameStore((state) => state.setHistory)
  const currentMove = useGameStore((state) => state.currentMove)
  const setCurrentMove = useGameStore((state) => state.setCurrentMove)
  const xIsNext = currentMove % 2 === 0
  const currentSquares = history[currentMove]

  function handlePlay(nextSquares: Squares) {
    const nextHistory = [...history.slice(0, currentMove + 1), nextSquares]
    setHistory(nextHistory)
    setCurrentMove(nextHistory.length - 1)
  }

  function jumpTo(nextMove: number) {
    setCurrentMove(nextMove)
  }

  return (
    <View style={styles.game}>
      <Board xIsNext={xIsNext} squares={currentSquares} onPlay={handlePlay} />
      <View style={styles.moves}>
        {history.map((_, historyIndex) => {
          const description =
            historyIndex > 0
              ? `Go to move #${historyIndex}`
              : 'Go to game start'

          return (
            <Pressable
              key={historyIndex}
              style={styles.moveButton}
              onPress={() => jumpTo(historyIndex)}
            >
              <Text style={styles.moveText}>{description}</Text>
            </Pressable>
          )
        })}
      </View>
    </View>
  )
}

function calculateWinner(squares: Squares): SquareValue {
  const lines = [
    [0, 1, 2],
    [3, 4, 5],
    [6, 7, 8],
    [0, 3, 6],
    [1, 4, 7],
    [2, 5, 8],
    [0, 4, 8],
    [2, 4, 6],
  ]

  for (let i = 0; i < lines.length; i++) {
    const [a, b, c] = lines[i]
    if (squares[a] && squares[a] === squares[b] && squares[a] === squares[c]) {
      return squares[a]
    }
  }

  return null
}

function countRemainingTurns(squares: Squares): number {
  return squares.filter((square) => !square).length
}

function calculateStatus(
  winner: SquareValue,
  remainingTurns: number,
  player: Player,
): string {
  if (!winner && !remainingTurns) return 'Draw'
  if (winner) return `Winner ${winner}`
  return `Next player: ${player}`
}

Setup: the four types

Everything in the port hangs off four declarations. Add them once at the top of the file and the rest of the tutorial needs almost no annotations — inference does the work.

types.tsts
type Player = 'X' | 'O'
type SquareValue = Player | null
type Squares = SquareValue[]
type Updater<T> = T | ((prev: T) => T)
  • Player is the turn owner: only ever 'X' or 'O', never an arbitrary string.
  • SquareValue adds the empty case. A square holds a player mark or nothing.
  • Squares is one board — nine SquareValues. The whole game history is then Squares[].
  • Updater<T> is the "value or updater function" shape that every Zustand setter in this tutorial accepts, mirroring React's setState API.
Why Updater<T> narrows correctly

Inside a setter, typeof nextSquares === 'function' narrows Updater<Squares> to the function branch, and the else branch to Squares. This works because the value branch (Squares, number, boolean) is never itself callable. If you ever store a function *as state*, this typeof trick collapses and you need a wrapper object or an explicit discriminator instead.

Do not use create<T>()(...) with combine

The Zustand TypeScript guide recommends the curried create<T>()(...) form so set and get infer properly. That advice does not apply here: combine *creates* the state, so the type is already inferred from the initial object plus the returned actions. Annotating it manually would be redundant — and would fight the inference. Same rule for the redux middleware.

Array(9).fill(null) infers any[]

The JavaScript original writes Array(9).fill(null). In TypeScript that infers any[], which silently disables type checking for the entire board. Pass the element type explicitly: Array<SquareValue>(9).fill(null) infers SquareValue[]. That single change is what makes history, squares, state.squares and every selector below type-safe with no casts.

The store is platform-agnostic

Nothing in these four types — or in the store, or in the three calculate* helpers — changes between web and React Native. That is worth noticing before you start: the React Native port touches only the components and the styles. State logic written with Zustand is portable by default, which is exactly why the same store drives both versions of this page.

Building the board

Let's start by creating the Square component, which will be a building block for our Board component. This component will represent each square in our game.

The Square component should take value and onSquareClick as props. It should return a <Pressable> — React Native's touch-handling primitive — styled to look like a square, with the value prop rendered inside a <Text>. When the square is pressed, it triggers the onSquareClick function passed in as a prop, allowing the game to respond to user input.

Here's the code for the Square component:

Square.tsxtsx
import { Pressable, StyleSheet, Text } from 'react-native'

type SquareProps = {
  value: string
  onSquareClick?: () => void
}

function Square({ value, onSquareClick }: SquareProps) {
  return (
    <Pressable style={styles.square} onPress={onSquareClick}>
      <Text style={styles.squareText}>{value}</Text>
    </Pressable>
  )
}

const SQUARE_SIZE = 40

const styles = StyleSheet.create({
  square: {
    width: SQUARE_SIZE,
    height: SQUARE_SIZE,
    alignItems: 'center',
    justifyContent: 'center',
    backgroundColor: '#fff',
    borderWidth: 1,
    borderColor: '#999',
  },
  squareText: {
    fontSize: 16,
    fontWeight: 'bold',
  },
})
Text has to be inside <Text>

On the web, <button>{value}</button> is enough. React Native refuses to render a bare string as the child of a View or Pressable — you get "Text strings must be rendered within a <Text> component". Every visible string in a React Native tree has a <Text> ancestor, no exceptions. That is also why styling splits in two: box styles (width, borderWidth, justifyContent) belong on the Pressable, text styles (fontSize, fontWeight) on the Text.

These prop types are temporary

At this step the board is static: it passes value="1" and no press handler, so value is a string and onSquareClick is optional. Two sections from now, once the store owns the board, SquareProps tightens to its final shape — value: SquareValue and a required onSquareClick: () => void. Letting the props start loose and tighten is normal; what matters is that the final version leaves no any behind.

Let's move on to creating the Board component, which will consist of 9 squares arranged in a grid. This component will serve as the main playing area for our game.

The Board component should return a <View> that lays its children out three-to-a-row. React Native's layout engine is flexbox only — there is no CSS Grid — so the 3×3 arrangement comes from flexDirection: 'row' plus flexWrap: 'wrap' on a container exactly three squares wide. Inside it, we place nine Square components, each with a value prop representing its position.

Board.tsxtsx
export default function Board() {
  return (

      <Square value="1" />
      <Square value="2" />
      <Square value="3" />
      <Square value="4" />
      <Square value="5" />
      <Square value="6" />

      <Square value="8" />

This Board component sets up the basic structure for our game board by arranging nine squares in a 3x3 grid. Note that nothing here needed annotating: a component that takes no props and returns JSX is fully inferred, and the object passed to StyleSheet.create is checked against React Native's ViewStyle / TextStyle for free — misspell flexDirection, or write flexWrap: 'wrapped', and you get an error at the declaration, which the JavaScript version would never have told you about.

Do not put a border on the board container

The web original draws a border around the grid as well as around each button. Try that here and the board collapses to two squares per row: React Native boxes are always border-box, so width: 120 with borderWidth: 1 leaves only 118px of content — one pixel short of three 40px squares, and flexWrap dutifully wraps. Keep the borders on the squares, keep the container's width an exact multiple of SQUARE_SIZE, and add padding or a border only on a wrapper View outside it.

Checkpoint 1: static board

Nine squares in a 3 by 3 grid, each showing its number, and npm run typecheck clean. If you see two squares per row, re-read the border warning above.

Lifting state up

Each Square component could maintain a part of the game's state. To check for a winner, the Board component would need to know the state of each of the 9 Square components. Although asking each child for its state is technically possible in React, we discourage it: the code becomes difficult to understand, susceptible to bugs, and hard to refactor. Instead, store the game's state in the parent, and let the parent tell each Square what to display by passing a prop.

To collect data from multiple children, or to have two or more child components communicate with each other, declare the shared state in their parent component instead.

Let's edit the Board component so that the state lives in a Zustand store holding an array of 9 nulls corresponding to the 9 squares:

App.tsxtsx
import { View } from 'react-native'
import { create } from 'zustand'
import { combine } from 'zustand/middleware'

type Player = 'X' | 'O'
type SquareValue = Player | null
type Squares = SquareValue[]
type Updater<T> = T | ((prev: T) => T)

const useGameStore = create(
  combine({ squares: Array<SquareValue>(9).fill(null) }, (set) => {
    return {
      setSquares: (nextSquares: Updater<Squares>) => {
        set((state) => ({
          squares:
            typeof nextSquares === 'function'
              ? nextSquares(state.squares)
              : nextSquares,
        }))
      },
    }
  }),
)

export default function Board() {
  const squares = useGameStore((state) => state.squares)
  const setSquares = useGameStore((state) => state.setSquares)

  return (
    <View style={styles.board}>
      {squares.map((square, squareIndex) => (
        <Square key={squareIndex} value={square} />
      ))}
    </View>
  )
}

Array<SquareValue>(9).fill(null) creates an array with nine elements, sets each of them to null, and types the result as SquareValue[]. Each entry corresponds to the value of a square. When you fill the board in later, the squares array will look like this:

squares.tsts
const squares: Squares = ['O', null, 'X', 'X', 'X', 'O', 'O', null, null]
The annotation is what catches typos

Without : Squares, that literal infers (string | null)[] and a typo like '0' (zero) instead of 'O' (letter) sails through. With it, TypeScript rejects anything that isn't 'X', 'O', or null. This is the whole payoff of declaring Player as a union of string literals rather than string.

Each Square will now receive a value prop that is 'X', 'O', or null for empty squares, so SquareProps tightens:

App.tsxtsx
type SquareProps = {
  value: SquareValue
  onSquareClick?: () => void
}

TypeScript will now flag the old static <Square value="1" /> usage as an error — that error is the type system telling you the refactor is complete. onSquareClick stays optional for one more step; it becomes required as soon as every square gets a handler.

value: SquareValue renders an empty square for free

<Text>{value}</Text> keeps working once value can be null: React Native renders null children as nothing, so an empty square is genuinely empty rather than showing the string "null". The square keeps its size because the size lives on the Pressable, not on the text.

Next, you need to change what happens when a Square component is pressed. Since state is private to the component that defines it, you cannot update the Board's state directly from Square. Instead, you'll pass a function down from Board to Square, and have Square call it when pressed. You'll call that function onSquareClick, and connect it to a handleClick function in Board via an inline function:

App.tsxtsx
<Square key={squareIndex} value={square} onSquareClick={() => handleClick(squareIndex)} />

Lastly, define the handleClick function inside the Board component to update the squares array holding your board's state. It takes the index of the square to update, creates a copy of the squares array (nextSquares), and adds X at the specified index if it is not already filled.

App.tsxtsx
export default function Board() {
  const squares = useGameStore((state) => state.squares)
  const setSquares = useGameStore((state) => state.setSquares)

  function handleClick(i: number) {
    if (squares[i]) return
    const nextSquares = squares.slice()
    nextSquares[i] = 'X'
    setSquares(nextSquares)
  }

  return (
    <View style={styles.board}>
      {squares.map((square, squareIndex) => (
        <Square
          key={squareIndex}
          value={square}
          onSquareClick={() => handleClick(squareIndex)}
        />
      ))}
    </View>
  )
}

Note how in handleClick, you call .slice() to create a copy of the squares array instead of modifying the existing array. handleClick(i: number) is the only annotation needed here: parameters of a plain function declaration are never inferred, while squares.slice() already returns SquareValue[] and nextSquares[i] = 'X' is checked against it.

Checkpoint 2: state in the store

Pressing an empty square puts an X in it; pressing it again does nothing. Every press creates a new array (slice()), never a mutation.

Taking turns

It's now time to fix a major defect in this tic-tac-toe game: the 'O's cannot be used on the board. You'll set the first move to be 'X' by default, tracked by another piece of state in the useGameStore hook:

App.tsxts
const useGameStore = create(
  combine(
    { squares: Array<SquareValue>(9).fill(null), xIsNext: true },
    (set) => {
      return {
        setSquares: (nextSquares: Updater<Squares>) => {
          set((state) => ({
            squares:
              typeof nextSquares === 'function'
                ? nextSquares(state.squares)
                : nextSquares,
          }))
        },
        setXIsNext: (nextXIsNext: Updater<boolean>) => {
          set((state) => ({
            xIsNext:
              typeof nextXIsNext === 'function'
                ? nextXIsNext(state.xIsNext)
                : nextXIsNext,
          }))
        },
      }
    },
  ),
)
xIsNext: true infers boolean, not true

combine infers the state type from the initial object, and an object property initialised to true widens to boolean — which is what you want. But if you ever wrap the initial state in as const, or declare it with satisfies on a narrower type, xIsNext becomes the literal type true and setXIsNext(false) stops compiling. Let the widening happen.

Each time a player moves, xIsNext will be flipped to determine which player goes next. Update the Board's handleClick function to flip the value of xIsNext:

App.tsxtsx
export default function Board() {
  const xIsNext = useGameStore((state) => state.xIsNext)
  const setXIsNext = useGameStore((state) => state.setXIsNext)
  const squares = useGameStore((state) => state.squares)
  const setSquares = useGameStore((state) => state.setSquares)
  const player = xIsNext ? 'X' : 'O'

  function handleClick(i: number) {
    if (squares[i]) return
    const nextSquares = squares.slice()
    nextSquares[i] = player
    setSquares(nextSquares)
    setXIsNext(!xIsNext)
  }

  return (
    <View style={styles.board}>
      {squares.map((square, squareIndex) => (
        <Square
          key={squareIndex}
          value={square}
          onSquareClick={() => handleClick(squareIndex)}
        />
      ))}
    </View>
  )
}

const player = xIsNext ? 'X' : 'O' needs no annotation: a conditional over two string literals infers 'X' | 'O', which *is* Player. Resist the urge to annotate what inference already gets right — every unnecessary annotation is a place that can drift out of sync.

Presses alternate X, O, X. Nothing yet stops play after three in a row.

Declaring a winner or draw

Now that the players can take turns, you'll want to show when the game is won or drawn. Add three helper functions: calculateWinner takes an array of 9 squares and returns 'X', 'O', or null; countRemainingTurns returns the number of turns left, which is the count of empty squares; and calculateStatus builds the status string from the winner, the remaining turns, and the current player.

App.tsxts
function calculateWinner(squares: Squares): SquareValue {
  const lines = [
    [0, 1, 2],
    [3, 4, 5],
    [6, 7, 8],
    [0, 3, 6],
    [1, 4, 7],
    [2, 5, 8],
    [0, 4, 8],
    [2, 4, 6],
  ]

  for (let i = 0; i < lines.length; i++) {
    const [a, b, c] = lines[i]
    if (squares[a] && squares[a] === squares[b] && squares[a] === squares[c]) {
      return squares[a]
    }
  }

  return null
}

function countRemainingTurns(squares: Squares): number {
  return squares.filter((square) => !square).length
}

function calculateStatus(
  winner: SquareValue,
  remainingTurns: number,
  player: Player,
): string {
  if (!winner && !remainingTurns) return 'Draw'
  if (winner) return `Winner ${winner}`
  return `Next player: ${player}`
}
Why the return type is SquareValue and not Player | null

They are the same type — SquareValue *is* Player | null — but naming it once means the "a square may be empty" idea has a single definition. It also keeps calculateWinner's return assignable straight into calculateStatus(winner, …) without a cast, because TypeScript compares structure, not names. lines needs no annotation: it infers number[][], and destructuring const [a, b, c] = lines[i] gives three numbers.

One flag changes this file: noUncheckedIndexedAccess

With noUncheckedIndexedAccess: true in your tsconfig.json, lines[i] becomes number[] | undefined and squares[a] becomes SquareValue | undefined, so this function needs guards (or as const tuples for lines). The tutorial code assumes the flag is off, which is the default and what expo's and vite's TypeScript templates ship. If you turn it on, expect to add a if (!line) continue and to handle history[currentMove] possibly being undefined later.

You will use the result of calculateWinner(squares) in handleClick to check if a player has won, at the same time you check whether the square is already taken. Return early in both cases:

App.tsxts
function handleClick(i: number) {

Adding time travel

As a final exercise, let's make it possible to "go back in time" and revisit previous moves.

If you had directly modified the squares array, implementing time travel would be very difficult. However, since you used slice() to create a new copy after every move, treating it as immutable, you can store every past version of the squares array and navigate between them.

export default function Game() {
  const history = useGameStore((state) => state.history)
  const setHistory = useGameStore((state) => state.setHistory)
  const currentMove = useGameStore((state) => state.currentMove)
  const setCurrentMove = useGameStore((state) => state.setCurrentMove)
  const xIsNext = currentMove % 2 === 0
  const currentSquares = history[currentMove]

  function handlePlay(nextSquares: Squares) {
    const nextHistory = [...history.slice(0, currentMove + 1), nextSquares]
    setHistory(nextHistory)
    setCurrentMove(nextHistory.length - 1)
  }

  function jumpTo(nextMove: number) {
    setCurrentMove(nextMove)
  }

  return (
    <View style={styles.game}>
      <Board xIsNext={xIsNext} squares={currentSquares} onPlay={handlePlay} />
      <View style={styles.moves}>
        {history.map((_, historyIndex) => {
          const description =
            historyIndex > 0
              ? `Go to move #${historyIndex}`
              : 'Go to game start'

          return (
            <Pressable
              key={historyIndex}
              style={styles.moveButton}
              onPress={() => jumpTo(historyIndex)}
            >
              <Text style={styles.moveText}>{description}</Text>
            </Pressable>
          )
        })}
      </View>
    </View>
  )
}

You no longer need the xIsNext state declaration or the calls to setXIsNext — delete setXIsNext from the store too, and the compiler will point you at every remaining call site. Now there's no chance for xIsNext to get out of sync with currentMove.

Create src/projects/tic-tac-toe/utils/game.ts. It exports the types, the helpers, and one new helper for stage 9. LINES moves to module scope so it is built once.

src/projects/tic-tac-toe/utils/game.tsts
export type Player = 'X' | 'O'
export type SquareValue = Player | null
export type Squares = SquareValue[]

const LINES = [
  [0, 1, 2],
  [3, 4, 5],
  [6, 7, 8],
  [0, 3, 6],
  [1, 4, 7],
  [2, 5, 8],
  [0, 4, 8],
  [2, 4, 6],
]

export function calculateWinner(squares: Squares): SquareValue {
  for (let i = 0; i < LINES.length; i++) {
    const [a, b, c] = LINES[i]
    if (squares[a] && squares[a] === squares[b] && squares[a] === squares[c]) {
      return squares[a]
    }
  }

  return null
}

/** Turns left to play, which is the number of empty squares. */
export function countRemainingTurns(squares: Squares): number {
  return squares.filter((square) => !square).length
}

export function calculateStatus(
  winner: SquareValue,
  remainingTurns: number,
  player: Player,
): string {
  if (!winner && !remainingTurns) return 'Draw'
  if (winner) return `Winner ${winner}`
  return `Next player: ${player}`
}

/** Screen-reader label for square `index` (0-8), e.g. "Row 2, column 3, X". */
export function squareLabel(index: number, value: SquareValue): string {
  const row = Math.floor(index / 3) + 1
  const column = (index % 3) + 1
  return `Row ${row}, column ${column}, ${value ?? 'empty'}`
}

Why these particular cases

Each one pins a rule that is easy to break while refactoring. The "winner on the last square" case guards the order of the checks in calculateStatus: if the draw check ran without the !winner guard, a winning final move would read Draw. The full-board no-winner case guards the opposite. Both are the same edge seen from either side.

  • The move buttons need no accessibilityLabel: their text child (Go to move #2) already reads well. selected tells the user which move is showing.
  • The status line is a ThemedText, not a plain Text. A plain Text defaults to black, so in dark mode it disappears against the dark screen background. ThemedText picks its colour from the scheme (and styles.status gains fontSize: 14, lineHeight: 17). The squares and move buttons keep plain Text, because they sit on a fixed #fff background where black always reads.

How it sits in the launcher

This is the one single-route project. Its route file is src/app/projects/tic-tac-toe/index.tsx, and it has no _layout.tsx, no stores/ folder and no providers. Three places know it exists:

  • The registry, src/shared/config/projects.ts: { slug: 'tic-tac-toe', title: 'Tic-Tac-Toe', route: '/projects/tic-tac-toe', singleScreen: true }. The launcher list is rendered from this array and has no hardcoded knowledge of the project.
  • The root Stack, src/app/_layout.tsx: it generates one Stack.Screen per project. Because singleScreen is set, this one is declared as projects/tic-tac-toe/index with the registry title as its header, since there is no inner layout to supply a header.
  • The slice, src/projects/tic-tac-toe/: only utils/game.ts and __tests__/game.test.ts. Isolation rules apply: nothing in it imports another project, and no other project imports it.

One launcher-driven change to the tutorial code: the launcher supports dark mode, so the status line uses the shared ThemedText (see Stage 9) instead of the plain Text shown in earlier stages.

The store itself stays in the route file as a module-scope useGameStore, so it lives as long as the JS runtime does. Leaving the screen and coming back keeps the game; there is no persistence, so a cold launch starts fresh.

Appendix: if you came from the web tutorial

The upstream Zustand tutorial targets the browser. If you paste its Square straight into an Expo app, the very first render throws:

Render Errortext
View config getter callback for component `button` must be a function
(received `undefined`). Make sure to start component names with a capital letter.

  at invariant (node_modules/invariant/browser.js:38)
  at get (react-native/Libraries/Renderer/shims/ReactNativeViewConfigRegistry.js:103)
  at completeWork (react-native/Libraries/Renderer/implementations/ReactFabric-dev.js)

Why it happens

In React, a lowercase JSX tag means "host component" — something the renderer provides rather than something you wrote. On the web that is a DOM element. Under React Native's Fabric renderer, the name is looked up in ReactNativeViewConfigRegistry, which only knows the components the native side registered: RCTView, RCTText, RCTImage and friends, exposed to you as View, Text, Image. Nothing registers a view config under the name button, so the getter returns undefined and the invariant fires while React is completing that fiber.

Three consequences worth internalising:

  • The trailing advice about capital letters is React's generic guess. Renaming <button> to <Button> only changes the error — you need a real component, not a capital letter.
  • <button> is just the first tag the renderer reaches. <div>, <ol> and <li> would each throw the same invariant in turn.
  • It is a runtime error, not a compile error: @types/react ships the JSX definitions for every DOM element, so tsc is perfectly happy with <button> in a React Native file. Nothing in the type system tells you the tag can't exist on device.

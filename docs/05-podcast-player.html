05 · Podcast Player & Release Pipeline

Background audio with lock-screen controls and offline downloads — plus the half of app development nobody teaches: EAS Build, EAS Update channels, staged rollouts, rollback, e2e tests, and CI/CD.

Ship-it tier EAS + CI ~4 weeks Core skill: audio session + release engineering
Why this one last

Two reasons. First, audio is the hardest media type to get right — interruptions, route changes, remote commands, and background sessions all have to work or the app is unusable. Second, by now you have four apps and zero release experience. This project is where you learn to ship: build profiles, over-the-air updates, percentage rollouts, rollback, and the runtime-version rules that decide whether an OTA update is even legal.

UI design & screens

Design language

  • Tone: dark, artwork-driven. The episode art defines the accent colour of the now-playing screen (extract a dominant colour and animate the gradient when the track changes).
  • The mini-player is permanent. It docks above the tab bar, is always visible when something is loaded, and expands with a drag or tap.
  • Playback controls must be reachable one-handed and forgiving — skip buttons at least 56pt, scrubber with a large hit slop.
  • Download state is visible everywhere an episode appears: not-downloaded, queued, downloading (with progress), downloaded, failed.

The mini-player docking above the tab bar and the lock-screen surface are the two pieces that make this feel like a real audio app.

Interaction details worth building properly

  • Mini → full transition: drag up on the mini-player and the artwork grows, the tab bar slides away, and the background gradient fades in — all interpolated from one shared value tied to the drag.
  • Scrubber: dragging must not fight the player's own position updates. Track a "seeking" flag; while seeking, the UI owns the position.
  • Skip buttons show the configured interval (15/30/45 s) inside the icon.
  • Sleep timer with an "end of episode" option and a fade-out over the last 10 seconds.
  • Queue reordering with a drag handle and haptic feedback on pickup and drop.
  • Chapter markers rendered as ticks on the scrubber; tapping one seeks.

Architecture

The player must live outside React

Design rule

A player owned by a component unmounts when you navigate. Own it in a module-scope singleton (or a native service) and let React subscribe to its state. Every component reads from a store fed by the player's events; nothing else holds a reference to it.

          ┌───────────────────────────────┐
          │  playbackService (singleton)  │
          │  · queue        · rate         │
          │  · position     · sleep timer  │
          │  · load/play/pause/seek/skip   │
          └──────┬─────────────────┬──────┘
        events   │                 │  commands
                 ▼                 ▲
        ┌────────────────┐   ┌─────┴────────┐
        │ playerStore    │   │ UI (mini +   │
        │ (zustand)      │──►│ full player) │
        └────────┬───────┘   └──────────────┘
                 │
      ┌──────────┼──────────────┐
      ▼          ▼              ▼
  progress   now-playing    resume-position
  persistence  metadata      writes to SQLite
                (lock screen)   (throttled 5s)

Audio session model

Configure the session once, early, and understand each flag rather than copying a snippet:

ConcernSettingWhat it decides
Silent switchplaysInSilentModeWhether iOS's mute switch silences you. A podcast app must be true.
BackgroundshouldPlayInBackground + the expo-audio plugin's enableBackgroundPlaybackPlayback continues when the app is backgrounded. Needs the audio background mode in Info.plist — the plugin adds it.
MixinginterruptionMode: doNotMix / duckOthers / mixWithOthersWhether you stop the user's music or share the output. Podcasts use doNotMix.
Lock screenplayer.setActiveForLockScreen(true, metadata)Shows artwork, title, artist and wires the remote controls.
RecordingallowsRecordingNot needed here, but note that enabling it changes output routing on iOS.

Events you must handle

INTERRUPTION BEGAN     (phone call, Siri, alarm, another app)
   → pause, remember that it was system-initiated

INTERRUPTION ENDED     (with a "should resume" hint)
   → resume ONLY if you paused it, and only if the hint says so

AUDIO ROUTE CHANGED    (headphones unplugged, Bluetooth disconnect)
   → pause immediately. Never blast audio out of the speaker.

BECAME NOISY (Android)
   → same rule

REMOTE COMMAND         (lock screen / car / headphone button)
   → play, pause, next, previous, seek, skip forward/back

APP TERMINATED
   → progress must already be persisted; nothing to save here

Test each of these physically. Call yourself mid-episode. Yank the headphones out. Get in a car. These are not edge cases for an audio app — they're the main path.

Download manager

QUEUE MODEL
  episodes[] with state: idle | queued | downloading | paused | done | failed
  max N concurrent (2–3), FIFO with a user-priority bump
  each item: resumable handle + bytes written + total bytes

RESUMABILITY
  createDownloadResumable(url, fileUri, options, onProgress)
    .downloadAsync()   start
    .pauseAsync()      → returns a resumable snapshot — PERSIST IT
    .resumeAsync()
  On app relaunch: rehydrate snapshots from storage and resume.

POLICY (make these user settings)
  · Wi-Fi only        → check network type before starting
  · Auto-download new episodes for subscribed shows
  · Storage cap       → evict oldest played episodes when exceeded
  · Auto-delete after N days / after played
  · Retry with exponential backoff, cap attempts, then mark failed

STORAGE
  documents/podcasts/<showId>/<episodeId>.mp3
  DB row holds the relative path, not an absolute uri
    ← absolute container paths CHANGE between app launches on iOS
The iOS absolute-path trap

The app container UUID changes across reinstalls and some updates. If you store file:///var/mobile/Containers/Data/Application/<UUID>/… in your database, every downloaded file appears missing after an update. Store paths relative to the documents directory and resolve them at read time. This bug is extremely common and extremely confusing when it hits.

Release engineering

This half of the project has no UI. It's the part that turns "an app on my phone" into "an app I can ship on a Tuesday and fix on a Wednesday."

Channels, branches, and runtime versions — the mental model

BUILD  ──has──►  channel  (baked into the binary at build time: "production")
                    │
                    │ mapped by EAS (mutable, server-side)
                    ▼
                 branch    ("release-1.4")
                    │
                    │ contains ordered updates
                    ▼
                 update    (a JS bundle + assets)

An update is only delivered to a build whose RUNTIME VERSION matches.
  runtimeVersion = the native contract.
  Change native code / add a native module / bump the SDK
       → runtime version MUST change
       → old builds stop receiving new updates (correctly!)

Policies: "appVersion" | "sdkVersion" | "fingerprint" | explicit string.
  fingerprint is the smartest: it hashes your actual native inputs.
The one rule that prevents disaster

An OTA update may only contain JS and assets. If your update expects a native module that isn't in the installed binary, the app crashes on launch for everyone who receives it. Runtime versioning exists precisely to make that impossible — respect it, and use the fingerprint policy so it's computed rather than remembered.

Rollout and rollback drill

1. eas update --branch release-1.4 --message "fix scrubber jump"
2. Start a rollout at 10%   → observe crash-free rate + errors
3. Bump to 50%              → observe again
4. Bump to 100%             → done
   ── or ──
   Something's wrong:
   · eas update:rollback / republish the previous known-good update
   · users get the good bundle on their next launch check
5. Verify on a device: relaunch twice (once to download, once to apply)

Update-check UX

Default behaviour downloads on launch and applies on the next launch. Decide deliberately:

  • Silent (default) — fine for most fixes.
  • Prompt to restart — for user-visible fixes; show a small banner: "Update ready · Restart".
  • Force-apply — reloadAsync() immediately; jarring, use only for critical fixes.
  • Add a dev-only "channel surfing" screen that overrides the channel header so you can test staging bundles from a production build.

CI pipeline

on pull_request
  → install, typecheck, lint, unit tests, maestro smoke on an emulator

on push to main
  → eas update --branch staging   (OTA to internal testers)

on tag v*
  → eas build --profile production --platform all
  → eas submit --profile production
  → upload source maps to the crash reporter
  → create a GitHub release with the changelog

nightly
  → fingerprint check: has the native contract drifted from the last build?

Build order

M1 Feeds & catalog

Goal: real content in the app.
  • Podcast search via an index API; subscribe/unsubscribe.
  • RSS parsing into typed episodes; handle the messy real world (missing durations, weird enclosures, HTML in show notes).
  • SQLite for shows, episodes, and progress.
  • Incremental refresh that doesn't re-insert everything.
Checkpoint — Subscribe to five real podcasts with different feed quirks. All parse without crashing.

M2 Playback core

Goal: audio plays, correctly, from anywhere in the app.
  • Singleton playback service; Zustand store fed by its events.
  • Play, pause, seek, skip ±15 s, playback rate.
  • Position persistence throttled to ~5 s; resume where you left off.
  • Queue with add-next / add-last, reorder, and auto-advance.
Checkpoint — Start an episode, navigate across every tab and into three detail screens. Audio never stutters and the player never remounts.

M3 Background & lock screen

Goal: the app disappears and the audio doesn't.
  • Audio mode configured; expo-audio plugin with background playback enabled.
  • Lock-screen metadata and remote commands.
  • Interruption handling: calls, Siri, alarms, other apps.
  • Route-change handling: headphones out → pause.
  • Android media notification with the right actions.
Checkpoint — Play, lock the phone, take a phone call, hang up. Playback resumes. Unplug the headphones — it pauses. Both behaviours correct, no manual intervention.

M4 Player UI

Goal: the interaction polish.
  • Mini-player docked above the tabs, present across all routes.
  • Drag-to-expand into the full player with an interpolated transition.
  • Scrubber with seek-lock, chapter ticks, and buffered range.
  • Artwork-derived gradient that animates on track change.
  • Sleep timer with fade-out; speed picker; skip-interval settings.
Checkpoint — Drag the mini-player halfway up and release. It settles naturally in both directions, and audio is unaffected throughout.

M5 Downloads

Goal: full offline listening.
  • Resumable downloads with persisted snapshots; resume after relaunch.
  • Concurrency limit, queue, retries with backoff.
  • Wi-Fi-only rule, storage cap with eviction, auto-delete policies.
  • Relative-path storage (avoid the container-UUID trap).
  • Playback prefers the local file when present.
Checkpoint — Download three episodes, kill the app at 50%, relaunch, and they resume from where they stopped. Then go into airplane mode and play all three.

M6 EAS Build

Goal: you can produce every kind of build on demand.
  • Three profiles configured; credentials managed by EAS.
  • A local production build and a cloud production build — compare timing and output.
  • Internal distribution to a second device via a QR code.
  • eas submit to TestFlight / Play internal testing.
  • Version and build-number strategy (autoIncrement).
Checkpoint — Someone else installs your preview build from a link and it runs against staging.

M7 EAS Update

Goal: ship a fix without a store review.
  • Configure expo-updates, channels, and the fingerprint runtime-version policy.
  • Publish an update to staging; verify a build receives it.
  • Custom update UX: check, download, and prompt to restart.
  • Run a staged rollout to production: 10% → 50% → 100%.
  • Practise a rollback. Publish a deliberately broken (but non-crashing) change, roll it back, verify recovery.
  • Prove the safety rail: change the native contract, confirm the runtime version changes and old builds correctly stop receiving updates.
Checkpoint — Fix a typo in production without touching the app stores, watch it roll out to a fraction of devices, then roll it back. If you can do this, you can operate a real app.

M8 CI/CD & store readiness

Goal: the pipeline does the work.
  • GitHub Actions (or EAS Workflows): typecheck, lint, test, Maestro smoke on PR.
  • Auto OTA to staging on merge; build + submit on tag.
  • Source-map upload to the crash reporter.
  • iOS privacy manifest and Android data-safety declarations.
  • Screenshots (consider generating them from Maestro), store listing, review notes.
  • Phased release configuration.
Checkpoint — Push a tag. Walk away. A build appears in TestFlight with symbolicated crash reporting wired up, and you touched nothing manually.

Failure modes to experience deliberately

  1. Player owned by a component. Navigate away and audio stops. The lesson that forces the singleton design.
  2. Silent-mode surprise. Ship without playsInSilentMode and get "no sound" bug reports from users whose mute switch is on.
  3. Resuming after every interruption. Resume when the interruption hint says not to, and your podcast starts playing during someone's next phone call.
  4. Speaker blast. Don't handle route change; headphones come out and the episode plays out loud on a train.
  5. Scrubber fight. The player's position updates overwrite the user's drag every 200 ms. Track a seeking flag.
  6. Absolute paths in the DB. Described above. Reinstall and watch every download "vanish".
  7. Update with a missing native module. Add a native dependency, publish a JS-only OTA to old builds, and crash them all on launch. Do this on a test channel to understand exactly why runtime versions exist.
  8. Channel/branch confusion. Publish to a branch no channel points at, then wonder why nobody got the update. Learn to read eas channel:view.
  9. Forgotten source maps. A production crash report you can't read.
  10. Unbounded storage. Auto-download 200 episodes and fill the user's device.

Stretch goals

  • CarPlay / Android Auto — a genuinely native surface requiring your own module and entitlements. Combines everything from Project 04 with this one.
  • Transcripts & search — on-device speech-to-text over downloaded audio, then FTS search across transcripts (reuses Project 01's search skills).
  • Skip silence / volume boost via audio processing — real DSP work.
  • Cross-device sync of playback position and queue.
  • Watch app for playback control.
  • Chapter support from podcast namespace tags plus embedded ID3 chapters.

Write one final document — what surprised you, what you'd architect differently, and which five bugs cost you the most time. That document is worth more than any of the apps.

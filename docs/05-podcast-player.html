How to use this brief

This page is a tutorial: read a section, build the matching milestone yourself in src/projects/podcast-player/ and src/app/projects/podcast-player/, then compare with the working code. Every milestone ends with a checkpoint (what you should observe) and a verify line (a command or a file to open). Pair it with the quiz bank in docs/training/ to practise finding the answers in the real code, and with the release runbook for the exact commands.

Why this one is the capstone of the release tier

Two reasons. First, audio is the hardest media type to get right — interruptions, route changes, remote commands, and background sessions all have to work or the app is unusable. Second, by now you have four apps and zero release experience. This project is where you learn to ship: build profiles, over-the-air updates, percentage rollouts, rollback, and the runtime-version rules that decide whether an OTA update is even legal.

Learning objectives

By the end of this project you can: keep audio playing across navigation, backgrounding and interruptions; persist listening position and a queue without hammering the database; download large files resumably and survive a killed app; parse messy real-world RSS defensively; and take a JS fix from a pull request to a tester's phone without a store review, knowing exactly when an OTA is and isn't legal.

UI design & screens

Design language

  • Tone: dark, artwork-driven. The episode art defines the accent colour of the now-playing screen. The built app derives the accent deterministically from the artwork URL (utils/color.ts accentFromSeed, no image-colour library) and animates the gradient when the track changes. Same artwork, same colour, every launch.
  • The mini-player is permanent. It docks above the tab bar, is always visible when something is loaded, and expands with a drag or tap.
  • Playback controls must be reachable one-handed and forgiving — large skip buttons with a hitSlop, and a scrubber with a generous vertical hit slop.
  • Download state is visible everywhere an episode appears: not-downloaded, queued, downloading (with progress), downloaded, failed.

Interaction details worth building properly

  • Mini → full transition: drag up on the mini-player and the artwork scales, the sheet translates and the gradient fades in, all interpolated from one Reanimated shared value (expand, 0 to 1) tied to the drag. When the spring settles at 1, the router pushes /player, presented as a transparentModal with no animation for from=drag, so the handover is invisible.
  • Scrubber: dragging must not fight the player's own position updates. Keep two pieces of local state: scrub while the finger is down and settling after release until the player confirms the seek. Display scrub ?? settling ?? position.
  • Skip buttons show the configured interval (15/30/45 s) inside the icon.
  • Sleep timer with an "end of episode" option and a fade-out over the last 10 seconds.
  • Queue reordering with a drag handle, swipe-to-remove, and haptic feedback on pickup and drop (expo-haptics).
  • Chapter markers rendered as ticks on the scrubber; tapping one seeks.
  • Small layout and navigation details. A horizontal ScrollView inside a flex column grows to fill it, which stretches the Discover genre chips into tall pills; OptionChips sets style={{ flexGrow: 0 }}. Every Switch gets an accessibilityLabel, or VoiceOver and TalkBack announce only "switch". The project stack gives the (tab) group title and headerBackTitle "Podcasts", otherwise screens pushed over the tabs show "(tab)" as the back label. Because the root stack hides its header for the project, the tab layout adds a headerLeft button back to the launcher.

Architecture

The player must live outside React

Design rule

A player owned by a component unmounts when you navigate. Own it in a module-scope singleton (or a native service) and let React subscribe to its state. Every component reads from a store fed by the player's events; nothing else holds a reference to it.

MiniPlayerHost mounts in your layout, not the root

The mini-player should persist across this project's screens and stop existing the moment the user backs out to the launcher. Mounting it in src/app/_layout.tsx would leave a podcast player floating over the store's checkout. Wrap your project's <Stack /> instead. The service singleton is module-scope and survives regardless; that is the point of separating them.

Data model (SQLite, one migration)

The podcast database is its own file, opened lazily by db/client.ts because the playback service, the download manager and the background task all run with no React tree. migrate() enables WAL and foreign keys, then applies forward-only steps keyed on PRAGMA user_version, each inside a transaction. Append new steps; never edit one that has shipped.

TableHoldsDetail worth copying
podcastsFeed, subscription flag, auto-download flagetag / last_modified validators for conditional GET; partial index on subscribed rows.
episodesParsed items, chapters (JSON)UNIQUE (podcast_id, guid) and a content_hash so an unchanged row is never rewritten.
progressPosition, duration, playedSeparate from episodes, so a feed refresh can never reset listening state.
downloadsState machine, attempts, next_attempt_at, snapshot (JSON)relative_path only, "NEVER an absolute URI".

User preferences are the exception: they live in a persisted Zustand store (stores/settingsStore.ts, AsyncStorage key podcast-player/settings) because they are tiny and the singletons need a synchronous getSettings(). The price is that it returns defaults until hydration finishes, so the headless background task awaits ensureSettingsHydrated() first, and so does PlaybackService.loadEpisode(), which needs the Default speed for resolveStartRate() even when an episode loads right after launch.

withTransactionAsync is not a lock

On the one shared connection, expo-sqlite's withTransactionAsync() is a plain BEGIN … COMMIT, and any query started elsewhere while it is open joins that transaction. Here a feed upsert, a queue save and a batched download update can all fire at once from different singletons. When two overlap, the second BEGIN fails ("cannot start a transaction within a transaction"), and that call's ROLLBACK then undoes the first one's writes. db/queries.ts therefore routes every write transaction through writeTransaction(), which runs them one at a time on a createSerialQueue() from utils/serial.ts. The alternative, withExclusiveTransactionAsync(), opens a separate connection (native only, not web), and competing writes then fail with "database is locked" rather than waiting, so you would still need to retry or queue them.

Query keys and live state

Every TanStack Query key starts with "podcast" (utils/queryKeys.ts) because the app has exactly one QueryClient. Keys nest (["podcast","show",id,"episodes"]), so invalidating podcastKeys.shows() refreshes the show, its episodes and its flags in one call. High-frequency data does not go through the query cache: download progress goes to downloadStore.live, merged with the persisted row by mergeDownload() in utils/downloadView.ts, and rendered through a connected LiveEpisodeRow so only the row that is downloading re-renders.

Events you must handle (and who handles them)

INTERRUPTION BEGAN     (phone call, Siri, alarm, another app)
   → expo-audio pauses natively and remembers which players it paused

INTERRUPTION ENDED     (with a "should resume" hint)
   → expo-audio resumes only those players, and only if the OS hint says so

AUDIO ROUTE CHANGED    (headphones unplugged, Bluetooth disconnect)
   → iOS: expo-audio pauses natively
   → Android "becoming noisy": NOT handled by expo-audio 57 (known gap)

REMOTE COMMAND         (lock screen / car / headphone button)
   → play, pause, seek, skip: act on the player natively

APP TERMINATED
   → progress must already be persisted; nothing runs on termination

None of these fire a JavaScript event. What JS can see is the status stream: the player stops or starts without you having asked. playback/interruptions.ts solves this with an intent tracker: the service calls command() every time it plays or pauses on the user's behalf, and observe() labels any unexplained transition as externalPause or externalPlay (ignoring buffering flips and a 1.2 s window after your own command; didJustFinish always gets through). On externalPause the service flushes progress and sets pausedExternally so the UI can say "Paused by the system". This keeps your model of what the user wants in sync, and means you never auto-resume after a pause made from the lock screen.

Test each of these physically. Call yourself mid-episode. Yank the headphones out. Get in a car. These are not edge cases for an audio app, they are the main path.

Progress, resume and the sleep timer

  • Throttled position writes. Status ticks arrive every 500 ms (updateInterval: 500). createProgressWriter() saves at most every 5 s while playing and flush()es immediately on pause, seek, track change, app backgrounding and external pause (it skips a write within 0.5 s of the last saved value).
  • Resume rule. resolveResumePosition() starts over if the episode is played or under 5 s in; otherwise it returns position - 2. An episode counts as played within min(30, duration × 5% + 5) seconds of the end.
  • Play after the end. When an episode finishes, the player stays parked at its end, and both native players ignore play() there, so the button does nothing. The service sets finished on the finish event, and play() checks it (or isAtEnd(position, duration), within AT_END_EPSILON_SEC = 0.5 s of the end): it seeks to 0 and only then plays.
  • Swapping sources. expo-audio's native replace() resumes on its own when the old item was playing, so the new episode would play from 0:00 until the resume seek lands. replaceSource() pauses first, then replaces and sets the rate; onStatus starts playback after the pending seek.
  • Start rate. resolveStartRate() in playback/rate.ts: a restored session's rate, then a speed picked this run, then the Default speed setting. status.rate is deliberately not an input: it always holds a number (1 initially), so falling back from it would never reach the setting.
  • Rapid taps. Each load() takes a token (++loadSeq) and loadEpisode() returns after any await once a newer load exists. Flushing the old episode's progress happens only after the last await, so a superseded load never flushes or resets the episode that is actually playing.
  • Sleep timer. Options include "end of episode", with a 10 s volume fade. The finish handler captures the timer option before awaiting the progress save and consults sleepFired, so a timer that expires just before the finish event cannot start the next queued episode.

Download manager

QUEUE MODEL
  downloads.state: queued | downloading | paused | done | failed
  max N concurrent (default 2), priority then FIFO
  each row: attempts, next_attempt_at, snapshot (JSON), relative_path

RESUMABILITY  (expo-file-system, SDK 57 object API)
  const task = new DownloadTask(url, new File(resolveUri(relativePath)), { onProgress })
  await task.downloadAsync()     → File when finished, null if paused first
  await task.pauseAsync()        → task is now paused
  const snap = task.savable()    → only valid while paused; PERSIST IT as JSON
  DownloadTask.fromSavable({ ...snap, fileUri }, { onProgress }).resumeAsync()
  On relaunch: rehydrate rows, rebuild tasks from snapshots, continue from the same byte.

POLICY  (pure functions in downloads/policy.ts, tested without a network)
  · Wi-Fi only        → networkDecision(): ok | offline | waitingForWifi
  · Auto-download     → at most 2 new episodes per show per refresh, never on the first sync
  · Storage cap       → default 2 GiB; evict PLAYED episodes only, oldest first
  · Auto-delete       → after N days, or when played
  · Retry             → equal-jitter backoff: 2 s × 2^(n-1), capped at 5 min; 5 attempts, then failed

STORAGE
  documents/podcasts/<showId>/<episodeId>.mp3
  DB row holds the relative path, not an absolute uri
    ← absolute container paths CHANGE between app launches on iOS

Lifecycle you must get right

  1. Pause is not failure. A paused downloadAsync() resolves with null. The manager keeps a stopReason to tell a user pause (row stays paused) from a Wi-Fi drop (row returns to queued and resumes by itself).
  2. Checkpoint on background. When the app goes to background or inactive, checkpointAll() pauses each active task, saves savable() with the file URI turned into a relative path, then resumes it. A deferred (checkpoint) tells run() (the transfer body that start() calls once it has claimed a concurrency slot) this was not a real pause. It resumes only when the task is still paused and has no stopReason: a user pause or a Wi-Fi drop that lands during the checkpoint resolves the deferred with null, so the download stays paused instead of being silently restarted.
  3. Rehydrate on launch. rehydrate() turns downloading rows back into queued, requeues done rows whose file vanished, applies auto-delete, and registers the network listener (expo-network). failed and paused rows wait for an explicit retry or resume.
  4. Throttle the noise. Progress is pushed to the live store only when the whole percent changes and written to SQLite at most every 3 s.
  5. Capacity before bytes. ensureCapacity() checks free space and the cap before starting. If everything stored is unplayed, the download fails with a clear message instead of deleting something the user has not heard.
  6. Never delete the file under the player. "Remove download" on the episode that is playing from its file first calls playbackService.releaseLocalFile(), which swaps the source to the stream URL at the same position (keeping it playing if it was), and removeMany() skips any id the player still reads locally (nowPlaying.isLocal).
The iOS absolute-path trap

The app container UUID changes across reinstalls and some updates. If you store file:///var/mobile/Containers/Data/Application/<UUID>/… in your database, every downloaded file appears missing after an update. Store paths relative to the documents directory and resolve them at read time (resolveRelativePath() refuses a scheme, a leading / or ..; toRelativePath() can recover a path from an old container's URI). The same rule applies to the pause snapshot's fileUri. This bug is extremely common and extremely confusing when it hits.

Background refresh (not background transfer)

downloads/task.ts defines a periodic task with expo-task-manager and registers it with expo-background-task (BGTaskScheduler on iOS, WorkManager on Android, minimumInterval: 60 minutes as a hint). It refreshes subscriptions, then asks the download manager to start whatever is queued. The OS grants a short window and decides when to run it. It is not a background-transfer service: if the process dies, the snapshot and rehydrate path picks the download up on the next launch.

Release engineering

This half of the project has no UI. It is the part that turns "an app on my phone" into "an app I can ship on a Tuesday and fix on a Wednesday." The exact commands are in docs/05-release.html; this section is the mental model.

Channels, branches, and runtime versions: the mental model

BUILD  ──has──►  channel  (baked into the binary at build time: "production")
                    │
                    │ mapped by EAS (mutable, server-side)
                    ▼
                 branch    (same name by default; "release-1.4" if you repoint it)
                    │
                    │ contains ordered updates
                    ▼
                 update    (a JS bundle + assets)

An update is only delivered to a build whose RUNTIME VERSION matches.
  runtimeVersion = the native contract.
  Change native code / add a native module / bump the SDK / edit app config
       → runtime version MUST change
       → old builds stop receiving new updates (correctly!)

Policies: "appVersion" | "sdkVersion" | "fingerprint" | explicit string.
  This repo uses runtimeVersion: { policy: "fingerprint" } in app.config.ts:
  a hash of your actual native inputs (native deps, config plugins, app config).
The one rule that prevents disaster

An OTA update may only contain JS and assets. If your update expects a native module that isn't in the installed binary, the app crashes on launch for everyone who receives it. Runtime versioning exists precisely to make that impossible. Respect it, and use the fingerprint policy so it is computed rather than remembered.

Publishing needs the same APP_VARIANT as the builds

eas.json's env applies to builds only. Because the app config (bundle id, name) feeds the fingerprint, an eas update run without the matching APP_VARIANT is stamped with the development runtime version and reaches nobody. release.yml sets APP_VARIANT: preview on the publish step for exactly this reason, and publishes with --channel preview rather than a hardcoded --branch, so the update always lands on the branch the channel reads.

                                          republishes the previous group, or the embedded bundle)
   · mid-rollout: eas update:revert-update-rollout
   · whole-branch canary: eas channel:rollout production
5. Verify on a device: relaunch twice (once to download, once to apply)

Users outside the rollout keep getting the previous latest update on the branch. Check which branch a channel reads with eas channel:view <channel> before every manual publish.

Update-check UX

app.config.ts sets updates.checkAutomatically: "ON_LOAD" and fallbackToCacheTimeout: 0, so launch never waits for the network: the update downloads after launch and applies on the next cold start. Decide deliberately:

  • Silent (default) — fine for most fixes.
  • Prompt to restart — what this app adds in lib/updates.ts: it also checks when the app returns to the foreground (rate-limited to once per 10 minutes), and the Home tab shows UpdateBanner ("Update ready · Restart", reloadAsync()) when useUpdates().isUpdatePending is true.
  • Force-apply — reloadAsync() immediately. Deliberately not used: reloading mid-episode would interrupt playback.
  • Channel surfing — in Settings, non-production variants can call Updates.setUpdateRequestHeadersOverride({ "expo-channel-name": … }) to test another channel's bundles. It only works between builds with the same runtime version: app.config.ts changes the bundle id per APP_VARIANT, so each variant has its own fingerprint, and a production build never accepts a preview update. Settings also shows the build's channel, runtime version and whether it launched the embedded bundle or an update id.

Build order

M1 Feeds & catalog

Goal: real content in the app.
  • Register the project in src/shared/config/projects.ts, create the route layout and the slice. The launcher and root Stack need no other change.
  • Podcast search via an index API (iTunes search and top charts here); subscribe/unsubscribe.
  • RSS parsing into typed episodes with fast-xml-parser: keep every value a string (parseTagValue: false) and parse numbers and durations yourself. Handle the messy real world (BOMs, missing durations, video enclosures, duplicate guids, HTML in show notes).
  • SQLite for shows, episodes, and progress with PRAGMA user_version migrations.
  • Incremental refresh: conditional GET (If-None-Match / If-Modified-Since, accept 304) plus an upsert that skips rows whose content_hash is unchanged.
Checkpoint — Subscribe to five real podcasts with different feed quirks. All parse without crashing, and refreshing twice in a row writes nothing.

Verify: npx jest --no-watchman src/projects/podcast-player/__tests__/parse.test.ts against the XML fixtures; add one fixture per quirk you meet.

M2 Playback core

Goal: audio plays, correctly, from anywhere in the app.
  • Singleton playback service created with createAudioPlayer(); a Zustand store fed by its playbackStatusUpdate events.
  • Play, pause, seek, skip back/forward, playback rate.
  • Position persistence throttled to ~5 s with flushes at the moments that matter; resume where you left off.
  • Queue as pure functions (add-next, add-last, move, take-next), with auto-advance on didJustFinish.
Checkpoint — Start an episode, navigate across every tab and into three detail screens. Audio never stutters and the player never remounts.

Verify: queue.test.ts and playbackRules.test.ts (start rate, isAtEnd) pass with no player; after an episode ends, play restarts it; open playback/service.ts and confirm nothing outside it holds an AudioPlayer.

M3 Background & lock screen

Goal: the app disappears and the audio doesn't.
  • setAudioModeAsync configured; expo-audio plugin with enableBackgroundPlayback: true (new build required).
  • Lock-screen metadata and remote commands via setActiveForLockScreen.
  • Interruption handling through the intent tracker: calls, Siri, alarms, other apps.
  • Route-change behaviour: headphones out → pause (native on iOS; note the Android gap).
  • Android media notification driven by the same lock-screen call.
Checkpoint — Play, lock the phone, take a phone call, hang up. Playback resumes only if the OS says it should. Unplug the headphones on iOS and it pauses. No manual intervention.

Verify: on a real device build (not Expo Go); read the header comment of playback/interruptions.ts for what is native and what is yours.

M4 Player UI

Goal: the interaction polish.
  • MiniPlayerHost in the project layout, docked above the tabs, present across all routes, hidden while /player is on top.
  • Drag-to-expand into the full player with one shared value driving every animated style.
  • Scrubber with scrub / settling seek-lock and chapter ticks (tap a tick to seek).
  • Artwork-derived gradient that animates on track change.
  • Sleep timer with fade-out; speed picker; skip-interval settings.
Checkpoint — Drag the mini-player halfway up and release. It settles naturally in both directions, and audio is unaffected throughout.

Verify: sleepTimer.test.ts passes; with React DevTools or a render log, confirm a position tick re-renders only the progress bar.

M5 Downloads

Goal: full offline listening.
  • Resumable DownloadTask downloads with persisted snapshots; resume after relaunch.
  • Concurrency limit, queue, retries with equal-jitter backoff.
  • Wi-Fi-only rule, storage cap with played-only eviction, auto-delete policies.
  • Relative-path storage (avoid the container-UUID trap).
  • Playback prefers the local file when the row is done and the file exists.
  • Live progress through a separate store and a connected row wrapper.
Checkpoint — Download three episodes, kill the app at 50%, relaunch, and they resume from where they stopped. Then go into airplane mode and play all three.

Verify: downloads.test.ts (policy, paths, "the container-UUID trap").

M6 EAS Build

Goal: you can produce every kind of build on demand.
  • Profiles in eas.json and a variant-aware app.config.ts; credentials managed by EAS.
  • A local production build (--local) and a cloud production build; compare timing and output.
  • Internal distribution to a second device via a link or QR code.
  • eas submit to TestFlight / Play internal testing.
  • Version and build-number strategy (autoIncrement with appVersionSource: remote).
Checkpoint — Someone else installs your preview build from a link, and it shows preview as its channel in Settings.

Verify: install the .dev and .preview builds side by side on one device.

M7 EAS Update

Goal: ship a fix without a store review.
  • Configure expo-updates, channels, and the fingerprint runtime-version policy.
  • Publish an update to the preview channel (with APP_VARIANT=preview, so the runtime version matches); verify a preview build receives it.
  • Custom update UX: check on foreground, download, and prompt to restart.
  • Run a staged rollout to production: 10% → 50% → 100%.
  • Practise a rollback. Publish a deliberately broken (but non-crashing) change, roll it back, verify recovery.
  • Prove the safety rail: change the native contract, confirm the runtime version changes and old builds correctly stop receiving updates.
Checkpoint — Fix a typo in production without touching the app stores, watch it roll out to a fraction of devices, then roll it back. If you can do this, you can operate a real app.

Verify: eas channel:view preview shows the branch and latest update; Settings on the device shows the same update id.

M8 CI/CD & store readiness

Goal: the pipeline does the work.
  • GitHub Actions (or EAS Workflows): typecheck, lint, test and a two-platform bundle on PR; Maestro on Maestro Cloud for PRs labelled e2e.
  • Auto OTA to the preview channel on merge to main; build + submit on a v* tag; a nightly fingerprint-drift check.
  • iOS privacy manifest required-reason APIs (ios.privacyManifests in app.config.ts) and Android data-safety answers.
  • Screenshots (generated from Maestro's takeScreenshot), store listing, review notes.
  • Phased release configuration (App Store phased release, Play staged rollout).
Checkpoint — Push a tag. Walk away. A build is submitted to TestFlight and you touched nothing manually.

Failure modes to experience deliberately

Each one has a symptom you can reproduce and a place in the finished code that prevents it.

  1. Player owned by a component. Shows up as: audio stops when you navigate. Handled by: the module-scope playbackService; UI only sends commands and reads usePlayerStore.
  2. Silent-mode surprise. Shows up as: "no sound" reports from users whose mute switch is on. Handled by: playsInSilentMode: true in PlaybackService.doInit().
  3. Resuming after every interruption. Shows up as: the podcast starts during someone's next phone call, or after a lock-screen pause. Handled by: native resume only with the OS hint, plus the intent tracker so the service never auto-resumes on its own.
  4. Speaker blast. Shows up as: headphones out and the episode plays out loud on a train. Handled by: native pause on iOS; Android "becoming noisy" is a known gap in expo-audio 57 (see the runbook), so test it and decide whether you need a native listener.
  5. Scrubber fight. Shows up as: the thumb jumps back to the old position right after you release. Handled by: scrub while dragging and settling until position is within 1.5 s of the target (with a timeout fallback).
  6. Absolute paths in the DB. Shows up as: after a reinstall every download "vanishes". Handled by: relative paths only, resolveRelativePath(), tested in downloads.test.ts.
  7. Update with a missing native module. Shows up as: a crash on launch for everyone who got the OTA. Handled by: the fingerprint runtime version. Prove it on a test channel: add a native dependency, publish, and watch old builds not receive it.
  8. Channel/branch confusion. Shows up as: "nobody got the update". Handled by: publishing with --channel in CI and reading eas channel:view before any manual --branch publish.
  9. Publishing with the wrong APP_VARIANT. Shows up as: the update succeeds but no build receives it. Handled by: setting the variant on the publish step.
  10. Settings read before hydration. Shows up as: a headless background run ignoring Wi-Fi-only and the storage cap. Handled by: await ensureSettingsHydrated() at the top of the task, and in PlaybackService.loadEpisode() before it picks the start rate.
  11. Sleep timer racing the finish event. Shows up as: the next episode starts after the user asked to sleep. Handled by: capturing the option before the awaited save, plus sleepFired.
  12. Forgotten source maps. Shows up as: a production crash report you can't read. Not handled yet: add the upload step once you choose a crash reporter.
  13. Unbounded storage. Shows up as: a full device after subscribing to a 500-episode show. Handled by: at most 2 auto-downloads per show per refresh, none on the first sync, and a cap that evicts only played episodes.
  14. Play does nothing after an episode ends. Shows up as: the episode finishes (queue empty), the user taps play and nothing happens. Handled by: play() in service.ts rewinds to 0 first when finished is set or isAtEnd() says the playhead is parked at the end; covered in playbackRules.test.ts.
  15. Overlapping SQLite transactions. Shows up as: intermittent "cannot start a transaction within a transaction", and queue or download writes that silently disappear because the failed call's ROLLBACK undid another transaction. Handled by: writeTransaction() in db/queries.ts, serialized by createSerialQueue() (serial.test.ts).
  16. Deleting the file that is playing. Shows up as: playback errors or stops the moment the user removes the current episode's download. Handled by: releaseLocalFile() moving playback to the stream at the same position before downloadManager.remove(), and removeMany() skipping a file the player still reads.
  17. A Maestro selector matching your own input. Shows up as: the smoke flow "taps the result" but lands on the search box. Handled by: the result-row regex "Syntax.* by .*" in .maestro/podcast-smoke.yaml.

Architecture decisions

These decisions shape the code. Make them early and the milestones stay small.

  • Containers vs components. Components receive plain data and callbacks. The few files that must subscribe on their own live in containers/: MiniPlayerHost (player store + service), LiveEpisodeRow and LiveTransferRow (per-row download subscription). The folder makes the rule checkable: nothing in components/ imports a store or a service. High-frequency values (playback position) are passed as a slot (progressBar holding NowPlayingProgress) so only the bar re-renders.
  • Mini-player host in the project layout. Scopes it to the project and hides it under the launcher. Because it sits outside the tab layout, the tab bar height is a shared constant (constants/layout.ts) and the host uses useSegments() to dock above the tabs or above the safe area.
  • Pure core, thin I/O shell. queue.ts, progress.ts, rate.ts, sleepTimer.ts, interruptions.ts, utils/serial.ts, downloads/policy.ts, downloads/paths.ts and feeds/parse.ts have no native imports, so Jest covers them. service.ts and manager.ts only execute their decisions.
  • Lazy database instead of a provider. The playback service, download manager and background task have no React tree, so db/client.ts exposes getDb() (cached promise, cleared on failure so the next call retries) instead of SQLiteProvider.
  • Root-level download task. A project layout only loads when the user opens the project, but the OS can launch the app headless to run a background task. So src/app/_layout.tsx imports downloads/task.ts, whose module-scope defineTask must exist on every JS load. Registration, which persists across launches, stays in the project layout so people who never open the podcast project are never woken for it.
  • Query keys and cache hygiene. One shared QueryClient, so the "podcast" prefix is what stops a blanket invalidation touching another project.

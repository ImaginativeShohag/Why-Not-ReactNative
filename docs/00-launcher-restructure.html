Why this came before everything else

The store app used to be the whole repo — its routes sat at the top of src/app/ and its code sat directly in src/components, src/hooks, src/stores, etc. Projects 01, 02, 04 and 05 from the learning path needed the same top-level slot the store occupied. Rather than bolt each new project on awkwardly, the repo was restructured once: one launcher Home screen, and every exercise — including the store — became a self-contained sibling module underneath it.

Original state (before the move)

Kept for reference — this is what the repo looked like when this plan was written.

Everything under src/ was implicitly "the store app." There was no concept of a second project:

src/app/ ├── index.tsx splash → auto-redirects to /store/main ├── _layout.tsx root Stack, hardcodes "store/…" screen names └── store/ ├── main/(tab)/{index,categories,bag,_layout}.tsx ├── orders/orders.tsx ├── place-order/place-order.tsx ├── product-details/[productId].tsx ├── products/[categoryId].tsx └── profile/profile.tsx src/{api,components,constants,hooks,models,providers,stores,utils}/ → a flat mix of store-specific code (cart, product, orders) and a few generic bits (theme, themed-text/view, QueryProvider, icon-symbol) with no boundary between the two.

Two things made that the right moment to fix it: src/app/index.tsx already auto-redirected away from a placeholder screen (easy to repurpose into a real launcher), and no second project existed yet to have grown its own conflicting conventions.

Target shape

  • Home (src/app/index.tsx) renders a list of exercises. Each row shows a title, one-line description, and a status dot (Available / Planned).
  • Tapping an Available row pushes into that project's own navigation stack. Tapping a Planned row opens a lightweight "not built yet" screen instead of doing nothing.
  • Each project is a vertical slice: its routes, components, hooks, stores, api calls and models all live under one project-named directory. Nothing about Project X's cart, auth, or models is importable from Project Y.
  • A small shared layer holds only what is genuinely generic across all projects: theming, the two themed primitives already used outside the store, the axios instance, the query provider, and the SF-Symbol/empty-state UI primitives.
  • Projects map 1:1 onto the docs in this folder — store ↔ 03, offline-journal ↔ 01, camera-social ↔ 02, fitness-tracker ↔ 04, podcast-player ↔ 05, and tic-tac-toe ↔ the Zustand tutorial port.

The registry — one source of truth for the list

src/shared/config/projects.ts exports a typed PROJECTS array describing every entry: emoji, title, subtitle, available, and route (an expo-router Href). The Home screen maps over this array — it has no hardcoded knowledge of "store" or any other project. Flipping a project from planned to available is a one-line change in this file plus replacing its stub.

Screen options come from the layout, never from a route-level export

Expo Router does not read export const options from a route file. The supported ways to set screen options are the parent layout's <Stack.Screen name="…" options={…} />, an inline <Stack.Screen options={…} /> rendered inside the route component, or navigation.setOptions() in an effect.

A file under src/app/ is a route whether you declare it or not

Routes are derived from the file tree, not from your Stack.Screen declarations. Omitting a declaration doesn't hide a screen — it only leaves it with a path-derived header title. So a non-route component must live outside src/app/ entirely, not merely go undeclared.

Back navigation is free: because each project is pushed onto the root Stack from Home rather than being the initial route, the OS back-gesture / header back-button already returns to the launcher list without extra code — just don't set any project as initialRouteName.

Rules for keeping projects isolated

These outlive the restructure — they govern every project added from here on.

  1. No cross-project imports. Nothing in src/projects/camera-social/ may import from src/projects/store/, ever. If two projects seem to need the same thing, that thing belongs in src/shared/, decided deliberately — not copy-pasted, not reached across.
  2. Shared stays small. Only promote a file to src/shared/ when a second project actually needs it. Don't pre-emptively share something because it looks generic — content-unavailable-view is the one exception since it was already written with zero store-specific knowledge.
  3. Each project owns its own query keys, its own Zustand stores, its own API endpoint files. There is no shared queryKeys.ts — each project's key factory only ever needs to disambiguate within itself.
  4. Components stay dumb (existing repo rule) — a component never assumes it's running inside a specific project's provider tree unless it's declared to live in that project.
  5. src/app/ is routes only. Anything that isn't a destination — a sheet body, a list row, a helper — belongs in a project slice or shared. Leaving it under src/app/ creates a real, reachable route. Currently bent only by Tic-Tac-Toe (accepted).
  6. Mount QueryProvider exactly once. Nesting a second instance creates a second independent QueryClient cache, so data fetched on one side of the boundary is invisible on the other.

Failure modes — what actually bit

Kept as a checklist for the next large move. The verdicts are from the final audit.

  1. Stale route strings. Never bit. Grep across src/ for "/store/, href="/store, (/store/ and `/store/ returns zero hits. Expo Router's typed routes only catch some of these, so re-grep after any further move rather than trusting TypeScript alone.
  2. Two copies of a moved file. Bit once, resolved. A duplicate use-theme-color.ts lingered under src/projects/store/hooks/, orphaned but contributing 2 type errors. The successor risk is duplicated logic, which also happened: two login paths (a mutation and a query) coexisted until the query was deleted.
  3. Metro cache showing ghosts. Standing advice. After large directory moves, clear the Metro cache (npx expo start -c) before trusting that a red-screen import error is real.
  4. Root _layout.tsx screen-name drift. Resolved by convention. The <folder>/index.tsx convention makes each route path equal its folder path, which removed the old orders/orders footgun outright. Verify a Stack.Screen name= against a fresh listing of the route tree — a stale listing produced a false drift report during one audit.
  5. Screen options that silently do nothing. Bit. A route-level export const options is ignored by Expo Router, so the splash screen looked configured while inheriting the layout default and showing a header. Fixed by setting headerShown: false on the root layout's Stack.Screen; the dead export is still there to delete.
  6. Back button landing in the wrong place. Fine by construction. No initialRouteName is set anywhere, and each project is pushed onto the root Stack from Home. The store enters via router.replace from splash to login, which is the kind of thing that can eat a back entry — worth re-testing whenever that chain changes.
  7. A non-route component parked under src/app/. Bit. The profile sheet lived at src/app/projects/store/profile/index.tsx and was imported as a component into the home tab's BottomSheetModal. Because routes come from the file tree, /projects/store/profile existed anyway — and hitting it crashed, since useBottomSheetModal() throws "'BottomSheetModalContext' cannot be null!" outside a BottomSheetModalProvider, which only the tab layout mounts. Fixed by moving the file to src/projects/store/components/sheet/ProfileSheet.tsx. Not declaring a route is not the same as not having one.

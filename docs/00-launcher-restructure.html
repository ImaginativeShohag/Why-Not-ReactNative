00 · Build the Launcher & Multi-Project Structure

Turn a single-app Expo repo into a home screen that lists every exercise, where each exercise lives in its own isolated vertical slice and opens from a registry-driven list. You build the skeleton once, so every later project has a slot and a set of rules.

Prerequisite Structural only — no new features Expo Router TypeScript
Why do this before anything else

Six exercises will share one repo, one Metro bundle and one native app. If the first project owns the top of src/app/ and dumps its code into flat src/components, src/hooks and src/stores, every later project either collides with it or gets bolted on awkwardly. Decide the shape once: a launcher at /, one directory per project, a small deliberate shared layer, and lint rules that make the boundaries real. Everything in Projects 01–06 assumes this skeleton.

Learning objectives

  • Design a repo where several independent apps share one Expo Router tree without sharing code by accident.
  • Drive a list screen and a root navigator from one typed registry, so adding a project is a data change.
  • Know what belongs in src/app/ (routes only), in a project slice, and in src/shared/.
  • Enforce isolation with an ESLint no-restricted-imports rule instead of good intentions.
  • Understand which side effects must start at the root layout because a project layout may never load (cold launch, background task, notification tap).
  • Namespace deep links under /projects/<slug>/… and rewrite external URLs in +native-intent.tsx.

The target shape

  • Home (src/app/index.tsx) renders a list of exercises. Each row shows an emoji, a title and a one-line subtitle.
  • Tapping a row pushes onto the root Stack and opens that project's own navigator. The OS back gesture returns to the list.
  • Each project is a vertical slice: routes under src/app/projects/<slug>/, everything else (components, hooks, stores, api, models, db) under src/projects/<slug>/. Nothing from Project X is importable from Project Y.
  • A small shared layer holds only what is generic: theme tokens, the themed primitives, the axios defaults, the query provider, the launcher registry and row.
  • Projects map 1:1 onto the docs in this folder: offline-journal ↔ 01, camera-social ↔ 02, store ↔ 03, fitness-tracker ↔ 04, podcast-player ↔ 05, tic-tac-toe ↔ 06.

Architecture

Routes (src/app/ — Expo Router owns this tree)

src/app/ ├── _layout.tsx root providers, root-level side effects, one Stack.Screen per project ├── index.tsx Home: maps over the registry ├── +native-intent.tsx rewrites external URLs onto namespaced routes ├── +not-found.tsx └── projects/ ├── store/ _layout.tsx + (auth) (app) onboarding -> Project 03 ├── offline-journal/ _layout.tsx + (tab) entry lock ... -> Project 01 ├── camera-social/ _layout.tsx + (tab) camera editor ... -> Project 02 ├── fitness-tracker/ _layout.tsx + (tab) workout settings -> Project 04 ├── podcast-player/ _layout.tsx + (tab) player episode ... -> Project 05 └── tic-tac-toe/index.tsx -> Project 06 (single route)

A screen is <folder>/index.tsx, so a route path equals its folder path. A project with several screens owns a _layout.tsx that declares its inner navigator.

Feature code (src/projects/ — everything that is not a route)

src/projects/<slug>/ ├── api/ components/ hooks/ models/ stores/ utils/ constants/ ├── db/ (projects with their own SQLite file) └── __tests__/ unit tests live here, never under src/app/

Create only the subfolders a project needs. Do not scaffold empty ones.

Shared infra (src/shared/ — used by more than one project, or by the launcher itself)

src/shared/ ├── api/axios.ts timeout + headers only, no baseURL, no interceptors ├── components/ │ ├── themed-text.tsx / themed-view.tsx │ ├── project-list-item.tsx the launcher row (pure presentation) │ └── ui/ icon-symbol(.ios), content-unavailable-view ├── config/projects.ts the registry ├── constants/ theme.ts, env.ts ├── hooks/ use-color-scheme(.web), use-theme-color └── providers/QueryProvider.tsx mounted ONCE, in the root layout

src/ itself should read as exactly app/ assets/ projects/ shared/ types/. A reviewer must be able to guess what every top-level folder is for, with no "misc" folder anywhere. Two folders live outside src/ because Expo tooling looks for them at the repo root: modules/ (local Expo Modules) and plugins/ (config plugins), both used by Project 04.

One scrollable list. Every row is tappable and pushes that project's route.

The registry — one source of truth

Create src/shared/config/projects.ts exporting a typed PROJECTS array. Each entry has a slug (also the folder name), an emoji, title, subtitle, a route typed as expo-router's Href, and an optional singleScreen flag for a project that is one route file rather than a stack. Home maps over the array, and so does the root layout. Neither has hardcoded knowledge of "store" or any other project, so adding a seventh project means one new entry plus its folders.

Routing strategy

  • The root _layout.tsx renders one Stack.Screen per registry entry, generated with PROJECTS.map: projects/<slug> with headerShown: false for a project stack, or projects/<slug>/index with the registry title as header for a singleScreen project. Each project's own _layout.tsx then owns its inner Stack, tabs and modals.
  • Home is / with no auto-redirect, and no initialRouteName is set anywhere. Because each project is pushed from Home, back navigation returns to the launcher for free.
  • Deep links are namespaced because the launcher owns the root: whynotreactnative://projects/<slug>/….
  • src/app/+native-intent.tsx exports redirectSystemPath, which tries a list of pure per-project rewriters (universal links such as /p/<id>, share-extension callbacks) and returns the first match, or the original path. It never throws on a malformed URL. Keep each rewriter in its own slice so it can be unit-tested.
Screen options come from the layout, never from a route-level export

Expo Router does not read export const options from a route file. Set options from the parent layout's <Stack.Screen name="…" options={…} />, an inline <Stack.Screen options={…} /> rendered inside the route component, or navigation.setOptions().

A file under src/app/ is a route whether you declare it or not

Routes are derived from the file tree, not from your Stack.Screen declarations. Omitting a declaration does not hide a screen; it only leaves it with a path-derived header title. A non-route component must live outside src/app/.

Never import @react-navigation/*

Since SDK 56, expo-router fails the bundle (not tsc) if app code imports it. Use expo-router/react-navigation for themes and useHeaderHeight, and expo-router for useIsFocused and useFocusEffect.

Root-level side effects

A project's _layout.tsx only loads when the user opens that project. Anything that must exist on a headless or cold launch is therefore started from the root layout, as module-scope imports and calls:

  • TaskManager.defineTask modules (journal sync, fitness tracking, podcast downloads). A background task wakes JS with no screen mounted; if the definition lives in a project layout, the task finds nothing registered.
  • Notification-tap listeners that only listen and buffer a route, because a tap on a cold start opens the launcher and the project layout never loads. Permission requests stay in the owning project.
  • A pending-action replay for Live Activity or notification actions that were parked while JS was dead.
  • ShareIntentProvider and an inbound-share routing hook, because the OS can hand the app shared media while the user is on the launcher.

expo-notifications is process-global: every payload carries a project discriminator, and each project's router ignores payloads that are not its own. The root layout is the one place allowed to import a single entry point from each project (the composition root); ESLint exempts it.

Rules for keeping projects isolated

  1. No cross-project imports. Nothing in src/projects/camera-social/ may import from src/projects/store/. If two projects need the same thing, promote it to src/shared/ deliberately: not copy-pasted, not reached across. Enforce it in eslint.config.js with one no-restricted-imports block per slug, generated from the folders in src/projects/, plus a block stopping src/shared/ from importing any project.
  2. Shared stays small. Promote a file only when a second project actually needs it.
  3. Each project owns its query keys, Zustand stores, database and API endpoint files. Query keys are prefixed with the project root (["store", …], ["podcast", …]). The shared axios instance has defaults only; projects derive their own with axiosInstance.create({ baseURL }) and install their own interceptors.
  4. Components stay dumb. They take plain data and callbacks, never a store or view model, and never assume a project's provider tree unless they live in that project.
  5. src/app/ is routes only. Sheets, rows, helpers and tests belong in a slice or shared.
  6. Mount QueryProvider exactly once, at the root. It also wires the process-global focusManager (AppState) and onlineManager (expo-network) for every project.

Build order

Five milestones. If you start from a single-app repo (all code flat under src/components, src/hooks, src/stores and routes under src/app/store/), you move things; if you start from a fresh Expo template, you create the same folders. Either way, run typecheck and lint after each milestone.

M1 Carve out src/shared/

Goal: move the generic 20% first, so everything later imports from a stable foundation.
  • Create src/shared/{api,components,components/ui,config,constants,hooks,providers}.
  • If you start from a single-app repo, move the generic files: themed-text, themed-view, ui/icon-symbol(.ios), ui/content-unavailable-view, the colour-scheme and theme-colour hooks, constants/theme.ts, QueryProvider, and axios.ts. Everything that mentions a cart, product or order stays behind for M2.
  • Strip the axios module down to project-agnostic defaults: timeout and headers only.
  • Fix importers with the @/src/... alias.
Checkpoint — The app still boots with no import errors, and npm run typecheck is clean.

M2 Move the first project's feature code into a slice

Goal: relocate non-route code into src/projects/<slug>/.
  • Create only the subfolders you need: api, components, hooks, stores, models, constants, utils.
  • Move that project's query keys into utils/queryKeys.ts with a root prefix of its own.
  • A bottom-sheet body, list row or helper that used to sit beside routes becomes a component in the slice.
Checkpoint — Nothing remains under the old flat src/{components,hooks,stores,api,models,constants,utils}/; those directories no longer exist.

M3 Move the routes under src/app/projects/<slug>/

Goal: namespace every route and fix every reference.
  • Move the project's route tree to src/app/projects/<slug>/, naming each screen <folder>/index.tsx.
  • Add (or move) that project's _layout.tsx, which owns its inner Stack.
  • Grep for old route strings ("/store/, href="/store, template-literal forms) and rewrite them to /projects/<slug>/…. Typed routes only catch some of them.
  • Clear the Metro cache (npx expo start -c) before trusting any red-screen import error after a big move.
Checkpoint — Every button inside the project navigates to the right screen, and opening whynotreactnative://projects/<slug> (for example with xcrun simctl openurl booted on the iOS simulator) lands on it.

M4 Build the launcher

Goal: Home becomes a data-driven list and the root layout stops knowing project names.
  • Write src/shared/config/projects.ts with the Project type and the PROJECTS array.
  • Write ProjectListItem in shared/components as a pure component, then render src/app/index.tsx by mapping the registry to it with router.push(item.route).
  • In src/app/_layout.tsx generate the Stack.Screen entries from PROJECTS, branching on singleScreen. Declare index with headerShown: false.
  • Mount QueryProvider, gesture root, safe-area and theme providers once here.
  • Add +native-intent.tsx with an empty rewriter list; each project registers its rewriter when it needs one.
Checkpoint — Cold-launching shows the list, not a project. Tapping a row opens that project; back returns to the list every time. Adding a dummy registry entry with a stub route makes a new row appear without touching index.tsx or the root Stack.

M5 Enforce the boundaries and verify

Goal: make the isolation rules fail the build when broken.
  • In eslint.config.js, read the folder names under src/projects/ and emit a no-restricted-imports block per slug covering both src/projects/<slug>/** and src/app/projects/<slug>/**. Add a second block for src/shared/** that forbids importing any project.
  • Prove it: temporarily import one project from another and confirm npm run lint fails with your message. Then confirm the root layout is not flagged.
  • Run npm run typecheck, npm run lint and npx expo export --platform ios --output-dir /tmp/out; the export catches what tsc cannot (for example @react-navigation/* imports).
  • Delete unused template leftovers rather than parking them in shared, and confirm there is exactly one QueryProvider and no duplicated hook files.
  • Write the structure rules into AGENTS.md and verify every path it names exists on disk.
Checkpoint — Lint, typecheck and a bundle export all pass; src/app/ contains routes only; a reviewer can predict the contents of every top-level folder.

Library hints

  • Routing: expo-router (file-based routes, typed routes, Stack.Screen, +native-intent, Stack.Protected later).
  • Server state: @tanstack/react-query v5 with focusManager and onlineManager wired to AppState and expo-network.
  • Client state: zustand v5, one store directory per project.
  • HTTP: axios, derived per project with create({ baseURL }).
  • Lint: eslint flat config with defineConfig, eslint-config-expo/flat and the core no-restricted-imports rule.
  • Providers: react-native-gesture-handler, react-native-safe-area-context, expo-status-bar.
  • Config: a dynamic app.config.ts with APP_VARIANT; install packages with npx expo install.

Failure modes to experience deliberately

Provoke each one on purpose in a scratch branch. Seeing the failure once makes the rule stick.

  1. Stale route strings. Move a route folder and leave one router.push("/store/…") behind. Typed routes catch some references, not template strings. Learn to grep for the old prefix after every move.
  2. Two copies of a moved file. Leave a duplicate hook in the old and new location. It orphans, adds type errors, and eventually diverges. The logic-level version is two login code paths (a mutation and a query) that coexist until one is deleted.
  3. Metro cache showing ghosts. After a large move, run with and without npx expo start -c and compare which red screens survive.
  4. Screen options that silently do nothing. Add export const options = { headerShown: false } to a route file. Nothing changes: Expo Router has no such convention, and the header keeps showing until the layout's Stack.Screen sets it.
  5. Route-name drift. Name a route orders/orders.tsx and declare name="projects/store/orders". The path is orders/orders, so the declaration does not apply. Use <folder>/index.tsx, and compare declarations against a fresh listing of the tree.
  6. A non-route component parked under src/app/. Put a bottom-sheet body at src/app/projects/store/profile/index.tsx and import it as a component. The route /projects/store/profile exists anyway; opening it crashes with 'BottomSheetModalContext' cannot be null! because it renders outside the modal provider. Not declaring a route is not the same as not having one. Move it into the slice.
  7. An @react-navigation/* import. Import useHeaderHeight from @react-navigation/elements. tsc is happy, the bundle fails. Switch to expo-router/react-navigation.
  8. A second QueryProvider. Mount one in a project layout. That creates a second QueryClient, so data fetched on one side of the boundary (a login screen outside the tab layout, say) is invisible on the other, and the focus and online managers may be wired twice.
  9. A background task defined in a project layout. Move a TaskManager.defineTask import from the root layout into a project layout and trigger the task from a cold, headless launch. Nothing is registered, so nothing runs. The same applies to a notification-tap listener: a cold-start tap lands on the launcher and is lost.
  10. A cross-project import. Import one slice from another. Without the lint rule it works and quietly couples two projects; with it, npm run lint fails with "No cross-project imports".
  11. Process-global state shared by accident. Send a push payload without a project field and watch every project's notification router try to handle it. Add the discriminator and make each router ignore foreign payloads.
  12. Back button landing in the wrong place. A router.replace inside a project's entry chain can eat a back entry. Re-test back navigation to the launcher whenever that chain changes.

Stretch goals

  • Registry-derived checks — a unit test that asserts every registry slug has a folder under both src/projects/ and src/app/projects/, and every route string resolves.
  • Per-project theming — let a registry entry carry an accent colour used by the row and the project header, without importing anything from a project.
  • Launcher search and favourites — filter the list and persist pinned projects in a Zustand store under src/shared/.
  • Lazy slices — measure cold-start time with and without the root-level imports of each project, and decide which side effects genuinely must be eager.
  • Dependency graph report — script that prints which slices import from shared, to spot candidates that should not have been promoted.
